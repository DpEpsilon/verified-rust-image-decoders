# Fallible allocation: specification delta (READY FOR OWNER FREEZE, not frozen; tenth revision 2026-11-12, build-input inventory completeness claim corrected; ninth revision, contract narrowed: gate F1 PASSED only as a feasibility gate for a fail-closed transitive allocation audit, with known prototype defects the production tool must fix (§8); F2 and F3 passed as prototype feasibility gates, F2 on x86_64 only; no assurance claim is permitted yet; see §8 and `REVIEW-SOL.md`)

This delta makes every heap allocation that the four verified cores (DIB, TGA, ICNS, ICO) make on their production call paths fallible. Each main crate exports only verified `try_*` entry points returning `TryError { Format(Error), OutOfMemory(..) }`; a failed reservation yields `Err(OutOfMemory)`, which sits **outside** every frozen error list. The frozen function names (`decode`, `parse`, `combine` and the rest) are **removed** from the main crates (decision D1), so no main crate contains a function that aborts on allocation failure. Their verified API theorems are retired and replaced by the `try_*` theorems, with no wrapper in between (§1.2). Aborting entry points, if anyone wants them, live in separate optional and unverified `<core>_abort_shim` crates outside the main crates' proof and audit boundary (§1.3). The public API is explicitly unstable, so these breaking changes need no compatibility gate (decision D9). No frozen spec, vector or hash file changes, and no `THEOREMS.md`/`THEOREMS-DRAFT.md` manifest is edited. The new obligations live in `THEOREMS-ALLOC-DELTA.md`. User-facing behaviour per integration is in `TABLE.md`.

Every frozen `Safe` definition conditions on allocation success: DIB `THEOREMS.md` line 3 and T1, frozen DIB 1.1 R17, TGA `THEOREMS.md` line 15 and R17, ICNS `THEOREMS.md` line 17, and ICO `THEOREMS.md` line 3 on `origin/main` ("Safety conditions exclude allocator exhaustion"). This delta removes that antecedent for the `try_*` entry points only. The remaining antecedents are an ordinary stack, an allocator that honours the `GlobalAlloc` contract (it returns null or a valid block for the requested `Layout`), and the trusted std contract A-STD (§3).

Source locations: DIB, TGA and ICNS refer to the `dib-policy` working tree. ICO refers to `origin/main:ico/ico_verus/src/{ico.rs,lib.rs,witnesses.rs}`; the `dib-policy` worktree carries only the `*.m4b` milestone snapshots of ICO, but the implementation (303 verified obligations, `origin/main:ico/README.md`) is tracked on `main`.

## 1. The outcome and the API

Each core gains, in its `alloc_guard` module (§3):

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct OutOfMemory { site: AllocSite, elements: usize }   // fields private to alloc_guard
impl OutOfMemory {
    #[verifier::when_used_as_spec(site_spec)]     pub fn site(&self) -> (s: AllocSite) ensures s == self.site_spec();
    #[verifier::when_used_as_spec(elements_spec)] pub fn elements(&self) -> (n: usize) ensures n == self.elements_spec();
    pub closed spec fn site_spec(&self) -> AllocSite;   // body: self.site
    pub closed spec fn elements_spec(&self) -> usize;   // body: self.elements
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum TryError { Format(Error), OutOfMemory(OutOfMemory) }
```

- `Error` is the frozen enum, unchanged. `TryError::name()` returns the frozen spelling for `Format(e)` and `"OutOfMemory"` otherwise. It is `'static` and never allocates.
- `AllocSite` is a closed per-core enum naming each reservation site (§4). `elements` is the element count of the failed request; its byte size is `elements * size_of::<T_site>()` for the site's element type, so at every `u8` site the count is the byte count.
- Code outside `alloc_guard` cannot construct an `OutOfMemory`: its fields are private, and the only constructors are the guard's reservation functions, which return one only from the `Err` arm of `try_reserve_exact` (§2, §3). ICO has one more constructor, `import_dib` in ICO's `alloc_guard/sites.rs`, which consumes DIB's returned log, appends its events to ICO's log, and wraps a DIB `OutOfMemory` (§3.1). There is no `from_dib`.
- `site()` and `elements()` carry `#[verifier::when_used_as_spec]` spec counterparts, so `ensures` clauses in this and other crates can name them: `o.site()` in spec position resolves to `site_spec`. The counterparts are `pub closed spec fn site_spec(&self)` and `elements_spec(&self)`, associated functions in the **same `impl` block** as the exec accessors, with the same `&self` parameter. Verus forces all three properties: an `open` body that reads a private field is rejected outside the owning module ("field expression for an opaque datatype"), so the counterparts must be `closed`, which is the sealing §2 wants; `when_used_as_spec` requires a sibling impl item with the exec function's parameters, so a receiver-less free `site_spec(o: OutOfMemory)` is rejected (gate F3, §8).
- `OutOfMemory` is not a byte-format error. No vector file gains it, and the Python oracles do not model it.

### 1.2 Frozen names removed; theorems retired

The frozen names are deleted from the main crates, not wrapped. Consequences:

- **The verified API theorems on the frozen names are retired.** This covers DIB T1, T3, T9–T13 and the policy delta's T1, T3, T9–T13 on `decode`/`decode_with_steps`/`decode_with_policy`; TGA T1, T7–T11 on `decode`; ICNS T1, T3–T8 and T10–T13 on `parse`/`decode_rgb`/`decode_mask`/`combine`; ICO T1–T11 on `parse`/`parse_with_steps`/`decode_entry`/`decode_entry_with_steps` and their witnesses. Theorems stated on internal helpers (DIB T2, T4–T8; TGA T2–T6; ICNS T2 and T9 on `rle_decode`) remain verified, retargeted where a helper's return type gains `TryError`.
- **The verified `try_*` theorems replace them directly** (`THEOREMS-ALLOC-DELTA.md` §1–§4). A main crate has no wrapper, so there is no inheritance argument and no unverified source in its proof report; its trust items are A-STD, the guard binding and the audit allowlist.
- **Under allocation success** nothing changes for a migrated caller: `fmt_part` of the `try_*` result satisfies the frozen predicate `Eq_f` (§2, clause 1), so mapping `Format(e)` to `e` reproduces the frozen result exactly.
- **Under allocation failure** the `try_*` function returns `OutOfMemory`. Nothing in a main crate terminates the process on allocation failure; the audit makes every aborting allocation path a finding (§6).

Inside the verified code, a failed request is never retried and never converted into a format error.

### 1.3 Optional abort shim crates

Aborting entry points, if wanted, live in a separate crate per core: `dib_abort_shim`, `tga_abort_shim`, `icns_abort_shim`, `ico_abort_shim`. Each depends on its main crate; no main crate depends on a shim. A shim crate is unverified, outside the main crate's proof and call-graph audit, and its documentation says: "aborts the process on allocation failure; for callers who don't care about recovery and don't need API stability." Building any of them is optional. Each function is at most five lines:

```rust
// dib_abort_shim/src/lib.rs (unverified, not audited)
pub fn decode(b: &[u8], mode: Mode) -> Result<Decoded, Error> {
    match dib_verus::try_decode(b, mode) {
        Ok(d) => Ok(d),
        Err(TryError::Format(e)) => Err(e),
        Err(TryError::OutOfMemory(o)) => abort_oom(o),
    }
}
```

`abort_oom(o)`, defined in each shim crate, computes `Layout::array::<T_site>(o.elements())` for the site's element type: `u8` at every site except the `EntryList` sites, whose element type is the core's public `Entry`. On `Ok(layout)` it calls `std::alloc::handle_alloc_error(layout)`; on `Err` (excluded by the site caps, but nothing here is verified) it calls `std::process::abort()`. `o.elements() >= 1` always, because zero-element reservations never fail (§3), so the layout is never zero-sized. The `_with_steps` shims pass the `Ghost<nat>` through unchanged.

What a shim does, argued by review of its text and not by Verus: whenever `g(x)` returns, its result is `fmt_part(try_g(x))`, which satisfies `Eq_f(x, ·)`, the predicate the retired theorem stated on `g` (for `decode_with_policy` the shim passes `r.1` through, giving all three frozen postconditions). If a reservation fails, the process terminates. DIB, TGA and ICO reserve at the same program point and size as today's `vec!`/`Vec::with_capacity`, so a shim's abort point and requested size match today's frozen functions. ICNS differs: `try_parse` reserves the entry list once before its loop, where today `Vec::new()` allocates nothing until the first `push` and each `type_hex` `String` allocates after its entry's checks. So under allocation failure `icns_abort_shim::parse` can abort on a malformed file where today `parse` returns `InvalidEntryLength`, for example a 16-byte file whose first entry declares length 7, and the failing request sizes differ because today's list, string and mask growth make several small requests where the delta makes one exact request.

The exact message and signal are promised only under these conditions: the pinned std and target (§3), std's default alloc-error hook, and no `-Zoom=panic`. Then stderr shows `memory allocation of <N> bytes failed` and the process gets SIGABRT. Under any other configuration a shim promises only that it does not return normally. The shim crate's own test checks this (`THEOREMS-ALLOC-DELTA.md` §5). These shims are unrelated to the C-API shims of decision D3 (`TABLE.md`), which write a fixed non-allocating message and call `process::abort()` directly.

## 2. Semantics

Fix a core and a `try_*` entry point `f`, where `x` stands for the input (`b`, plus `mode`, `bm`, `policy`, `E` and indices as applicable). DIB policies are quantified over every value of the `Policy` record type, not only the named profiles; this includes the records reachable only through `cfg(test)` `try_decode_custom_policy`.

**Result relations.** An equation `r == lift(M(x))` does not type-check in Verus: the executables return `Vec`/`Decoded` values, the models return `Seq`s and tuples, and ICNS's parse model has its own error enum (`MpError`, `icns/icns_verus/src/model.rs:321`, mapped by `exec_err`). The frozen proofs already bridge each gap with an executable-to-model predicate, so the delta states every functional clause through those predicates and never through an equation. For a `try_*` result `r` that is not `OutOfMemory`, `fmt_part(r)` is the frozen-typed result: `Ok(v) ↦ Ok(v)`, `Err(Format(e)) ↦ Err(e)`. The relation `Eq_f(x, r)` is:

| Entry point | `Eq_f(x, r)` (frozen predicate, unchanged) |
|---|---|
| DIB `try_decode`, `try_decode_with_steps`, `try_decode_with_steps_logged` | `decode_mp_eq(fmt_part(r), b, mode)` (`dib.rs:6780`, against `model::mp`, `model.rs:5501`) |
| DIB `try_decode_policy_tracked` (record `p`) and `try_decode_with_policy` (`p = profile_policy(profile)`) | `decode_policy_mp_eq(fmt_part(r.0), b, bm, p) ∧ decode_policy_alpha_eq(fmt_part(r.0), b, bm, p) ∧ r.1 == recovered_policy(b, bm, p)` (`dib.rs:7998`, `:8015`; the three postconditions of `decode_with_policy`, `:8179–8184`) |
| TGA `try_decode` | `decode_eq(fmt_part(r), b)` (`tga.rs:281`) |
| ICNS `try_parse` | `parses_to(b, fmt_part(r))` (`model.rs:1166`: `MpError` through `exec_err`, entries through `entries_eq_models`/`entry_eq_fields`, retargeted to `hex_str` in §4) |
| ICNS `try_rle` (helper) | `rle_result_eq(fmt_part(r), mr(s, n))` (`model.rs:3461`) |
| ICNS `try_decode_rgb`, `try_decode_mask`, `try_combine` | `rgb_decoded_eq`, `mask_decoded_eq`, `combine_decoded_eq` on `fmt_part(r)` (`model.rs:3642`, `:3581`, `:3711`) |
| ICO `try_parse`, `try_parse_with_steps` | `parse_eq(b, fmt_part(r))` (on `r.0` for the steps variant) (`origin/main:ico/ico_verus/src/model.rs:218`) |
| ICO `try_decode_entry`, `try_decode_entry_with_steps` | `md_eq(b, E, i, fmt_part(r))` (ICO `model.rs:949`) |

`fmt_part` is a spec function in each core's `try` module, outside the guard. Every kill claim in `THEOREMS-ALLOC-DELTA.md` §6 that names "clause 1" or `Prog` as its gate assumes `Eq_f` is exactly the frozen predicate listed here. If a conjunct is dropped (for example `decode_policy_alpha_eq`), those kill claims are void and the mutations must be re-run.

**Two traces.** The *logical reservation trace* `L` is the sequence of guard calls a run actually makes, each with its result: `Seq<(AllocSite, nat, bool)>`, the `bool` being whether that reservation returned `Ok`. The *physical allocator-event trace* is the sequence of `GlobalAlloc` calls the run makes. The theorems speak only about `L`. The relation between the two is a tested property of the pinned std, not a proved one (§3, `THEOREMS-ALLOC-DELTA.md` §5). `req(L)` drops the `bool`.

**The log is sealed.** `L` lives in a `tracked` value of type `alloc_guard::AllocLog`, whose single ghost field is private to `alloc_guard`. Rust privacy, which Verus enforces in ghost and proof code as well, means code outside the module can neither construct a log with entries nor edit one. The only operations are `new_log()` (empty) and the guard's reservation functions, each of which appends exactly one entry whose `bool` equals `r is Ok` for that call's result. Each `try_*` function creates its log once, at entry, and returns it from a `*_logged` variant; the public `try_*` is that variant with the log discarded. `Tracked::assume_new`, `assume` and `admit` are excluded by the existing no-assumption rule, and the audit reads ghost code for them (§6). Because the source audit strips ghost code for its allocation checks, nothing about `L` rests on the audit.

**Request model.** `Req(x)` is a spec function written in model terms (frozen `MH`/`MP`/`walk`/`MR`/`H`/`MD`), not by reading executable code: the ordered `(site, elements)` requests that `f` issues on `x` when every reservation succeeds. §4 gives it per core.

**Graceful-failure theorem shape.** For all `x`, with `r` the result and `L` the final log:

1. `r = Ok(_)` or `r = Err(Format(_))` implies `Eq_f(x, r)`, `req(L) = Req(x)`, and every entry of `L` is `Ok`.
2. `r = Err(OutOfMemory(o))` implies `L` is non-empty, `req(L)` is a prefix of `Req(x)`, every entry but the last is `Ok`, the last entry is **not** `Ok`, and its `(site, elements)` equals `(o.site(), o.elements())`.
3. Every `(s, k)` in `Req(x)` has `k` within the site's maximum (§4), proved from checked values before the guard call.

Clauses 1–2 tie **every** `OutOfMemory` return to a reservation that actually failed and that was the last one issued. An implementation that returns `OutOfMemory` after `try_reserve_exact` returned `Ok` fails clause 2, since the last entry would be `Ok`; one that swallows a failure and returns a format error or `Ok` fails clause 1. Neither check depends on the audit.

**Progress.** If every entry of `L` is `Ok`, then `r` is not `OutOfMemory`, `Eq_f(x, r)` and `req(L) = Req(x)`. This is the contrapositive of clause 2 combined with clause 1. Each core states it as a named theorem, so that a mutation that weakens either clause still leaves a failing target.

**Where the `bool` comes from.** The guard sets an entry's `bool` to `r is Ok`, and the guard body returns `Ok` exactly from the `Ok` arm of `try_reserve_exact` (or for a zero-element request, §3). That body is verified against vstd, but vstd's `try_reserve_exact` spec does not constrain its result, so the binding "`Err` from the guard iff `Err` from `try_reserve_exact`" holds by the guard's hash-pinned text (§3), not by an `ensures`. The fault-injection test checks it at runtime (mutation A2).

**Pre-allocation predicate.** `PreAlloc(x)` holds iff `Req(x) = []`, and `Reach(x)` is its negation. Each core proves the named corollary `PreAlloc(x) ⇒ r is not OutOfMemory ∧ Eq_f(x, r) ∧ L = []`, so errors detected before the first reservation are never `OutOfMemory`. That is not the same set as "header errors": ICNS `try_parse` reserves its entry list after R2–R4 and before the entry loop, so a file with one complete entry followed by a partial entry header can return `OutOfMemory` in place of `TruncatedEntryHeader` (displaced errors, below). `Reach` is defined by the code's actual reachability of the first guard call, restated in model terms, not by a looser model condition:

- **DIB, `decode` family.** `Reach(b, mode)` iff `mh(b, mode)` is `Ok`.
- **DIB, policy.** `Reach(b, bm, p)` iff either the complete path reaches `alloc_output` (`mh_policy(b,bm,p) = Ok(m)` and `¬gdk_rgb_reject(b,m,p)`, `dib.rs:8590–8600`), or the Blank second pass reaches `alloc_output_n` (`dib.rs:8268`). The second pass runs only after the first header pass has failed with `TruncatedMasks` or `TruncatedPalette` under `incomplete_metadata = Blank` (`:8424–8427`); it then revalidates and returns the original error at four points: `|b| > MAX_INPUT` (`:8243`), `bmp_prefix_policy` error (`:8249`), `dib_fields` error (`:8255`), and missing masks with a header size other than 40 or 64 (`:8258`). The required lemma is that the conjunction of passing all four equals `mh_partial(b,bm,p) is Some` (`model.rs:8829`). In that case the reservation is followed only by `fill_blank` and `Ok`, so `OutOfMemory` is the sole alternative to success.
- **TGA.** `Reach(b)` iff `MH(b)` is `Ok`.
- **ICNS.** `try_parse`: R2–R4 pass. Decoders: index and type checks pass and `rle_decode` is entered (colour) or the mask length check passes (mask).
- **ICO.** `try_parse`: `H(b)` is `Ok`. `try_decode_entry`: `MD` reaches the DIB call, and then DIB's own `Reach` on the selected slice in `IcoEntryDibSlack` mode.

**Displaced errors.** An input that the model rejects *after* the first reservation may yield `OutOfMemory` instead of its format error. DIB `TruncatedPixels`, TGA `TruncatedImageId` (TGA reserves before the ID check, which frozen R6 permits) and every ICNS in-loop parse error are examples. The ICNS case is new with this delta: the entry list is reserved once, after R2–R4 and before the loop, so a 16-byte file whose first entry declares length 7 can return `OutOfMemory` before `InvalidEntryLength`. The owner accepts this (decision D5), including when enough memory would remain to report the format error: under memory pressure, reporting `OutOfMemory` in place of a malformed-entry error is acceptable.

**Partial work, no partial output.** `OutOfMemory` may be returned after earlier reservations succeeded and after work was done (ICNS `try_combine` decodes the colour entry before it reserves the mask; ICNS `try_rle` reserves three channels in turn). On every path:

- An `Err(OutOfMemory)` carries no pixels, no entry list and no `recovered` flag. `try_decode_with_policy` returns `recovered = false` with `OutOfMemory`.
- No API has a `&mut` output parameter, so there is no partially written caller buffer.
- Every vector created before the failure is dropped on return by ordinary ownership. The production call graph contains no `mem::forget`, `Box::leak`, `ManuallyDrop`, `Rc` or `Arc` (audit, §6).

**Work bound.** DIB T12 (`steps <= 16*(|b|+N)`, `N` the validated `w*h`, or 0 on a failed header) and ICO T9 hold **for every outcome**, including `OutOfMemory`, with the same counter and `N`; this is the required bound. The guard takes no step counter: the caller charges the `4N` initialisation after the guard returns `Ok`, so the `OutOfMemory` branch carries no initialisation charge. `steps_OOM <= 16*|b|` stays an optional strengthening (decided, O5); it would need the pre-allocation work, including the Blank path's failed first pass and revalidation, charged within `16*|b|`. TGA and ICNS have no step counter and keep only termination.

**Termination.** No core retries a reservation. Each guard call sits at a fixed program point outside any loop. The ICNS entry list is reserved once before its loop, and the three ICNS channels are three straight-line calls.

## 3. Reservation primitive, vstd gap and A-STD

vstd `0.0.0-2026-11-01-0251` (`std_specs/vec.rs:133–145`) specifies `try_reserve` and `try_reserve_exact` with only `final(vec)@ == old(vec)@`. It relates `Ok`/`Err` to nothing and models no capacity. `push` (`:149`), `resize` (`:329`), `extend_from_slice` (`:171`) and `from_elem`/`vec!` (`:414`) specify only the resulting view. So Verus treats every reservation as possibly failing, which is the property this delta wants, and Verus **cannot** prove that a later `push` does not allocate. vstd has no `String::try_reserve*` or `String::with_capacity`, so a `String` cannot be built fallibly in verified code without a new `assume_specification`, which ICNS's boundary forbids.

**The guard module.** `alloc_guard/mod.rs` is identical text in every core, and its SHA-256 is recorded and checked (decision D6). The hash authenticates the text only: it shows the module is the reviewed text, and says nothing about its correctness beyond what verification and review establish. A per-core child module `alloc_guard/sites.rs` (separately hashed and reviewed) declares `AllocSite`, the element types, the per-target layout facts (below) and, in ICO only, `import_dib` (§3.1). Rust privacy lets the child module see the parent's private fields, and nothing else can. The guard is the only place where production code may construct, grow or fill a `Vec`.

**Reference implementation.** The verified prototype of gate F3 is the reference text for the guard: `proto/guard_proto/src/alloc_guard/{mod.rs,sites.rs}` (DIB-shaped core, 44 verified, 0 errors) and `proto/guard_proto_dep/src/alloc_guard/{mod.rs,sites.rs}` (ICO's second sealed log and the cross-crate `import_dib`, 22 verified, 0 errors), on rustc 1.99.1 and Verus `0.0.0-2026-11-01-0251` (`proto/NOTES.md`, `proto/RUNLOG.tsv` runs 135/136, re-confirmed by 143/144).
```rust
// alloc_guard/mod.rs. Fields private. #[inline(never)] on every exec fn.
pub tracked struct AllocLog { ghost ev: Seq<(AllocSite, nat, bool)> }
impl AllocLog { pub closed spec fn view(self) -> Seq<(AllocSite, nat, bool)> { self.ev } }
pub proof fn new_log() -> (tracked l: AllocLog) ensures l.view() == Seq::<(AllocSite, nat, bool)>::empty();

pub struct Reserved<T> { v: Vec<T>, room: Ghost<nat> }      // invariant: v@.len() <= room <= v.capacity() (A-STD-1)

pub fn try_zeroed(site: AllocSite, n: usize, Tracked(log): Tracked<&mut AllocLog>) -> (r: Result<Vec<u8>, OutOfMemory>)
    requires 1 <= n <= MAX_BYTES,                           // MAX_BYTES = 67,108,864
    ensures final(log).view() == old(log).view().push((site, n as nat, r is Ok)),
            r is Ok  ==> r->Ok_0@ == Seq::new(n as nat, |_i| 0u8),
            r is Err ==> r->Err_0.site_spec() == site && r->Err_0.elements_spec() == n;
pub fn try_copy(site: AllocSite, s: &[u8], Tracked(log): Tracked<&mut AllocLog>) -> (r: Result<Vec<u8>, OutOfMemory>)
    requires 1 <= s.len() <= MAX_BYTES,
    ensures /* log as above with s.len() */, r is Ok ==> r->Ok_0@ == s@, ...;
pub fn try_with_room<T>(site: AllocSite, n: usize, Tracked(log): Tracked<&mut AllocLog>) -> (r: Result<Reserved<T>, OutOfMemory>)
    requires n <= MAX_ROOM,                                 // MAX_ROOM = 4,096
             1 <= size_of::<T>(), n * size_of::<T>() <= isize::MAX,
    ensures /* log as above */, n == 0 ==> r is Ok,
            r is Ok ==> r->Ok_0.view() == Seq::<T>::empty() && r->Ok_0.room() == n;
impl<T> Reserved<T> {
    pub fn push(&mut self, x: T) requires old(self).view().len() < old(self).room(), ...;
    pub fn into_vec(self) -> (v: Vec<T>) ensures v@ == self.view();
}
```

Each body is `Vec::new()`; then, if `n == 0`, `Ok` without calling `try_reserve_exact`; otherwise `try_reserve_exact(n)`, returning `Err(OutOfMemory { site, elements: n })` from its `Err` arm, and from its `Ok` arm either a `push(0)` loop to length `n` (`try_zeroed`), a `push` loop over `s` (`try_copy`) or nothing (`try_with_room`). Every arm that returns appends exactly one log entry, `proof { log.ev = log.ev.push((site, n as nat, ok)); }` with `ok` the literal `true` or `false` of that arm, immediately before the return. The fill uses `push` only, so A-STD rests on documented guarantees (decision D4). `resize`/`extend_from_slice` may be adopted later only if a measurement shows the push loop matters, and then A-STD gains a clause for them.

**`tracked`-struct mechanics.** Three spellings are required; gate F3 found each one by a rejected alternative:

- A reservation function takes the log as `Tracked(log): Tracked<&mut AllocLog>`, destructured in the parameter list. With a named `log: Tracked<&mut AllocLog>` parameter, `old(log)` and `final(log)` are ill-formed (`E0308: expected &mut _, found Tracked<..>`), and the function can neither write the log nor pass the reference on.
- The private field is written only inside a `proof { .. }` block. A bare `log.ev = ..` in the exec body is rejected ("cannot mutate through a spec-mode mutable reference").
- The append is repeated as one `proof` statement in each reservation function; there is no shared append helper. A helper taking `Tracked(log): Tracked<&mut AllocLog>` cannot be called with the caller's destructured reference (`E0308`), and a helper taking `&mut AllocLog` cannot touch the proof-mode place ("cannot access proof-mode place in executable context").

**`OutOfMemory` literals.** The struct literal `OutOfMemory { .. }` may appear only in `alloc_guard/mod.rs` and its child `sites.rs`; anywhere else it is a build error (`disallowed: constructor for an opaque datatype`, prototype negative check `neg1`). A proof outside the guard that needs to name a returned `OutOfMemory` takes the value as a parameter and states its shape through `site_spec`/`elements_spec`.

The `size_of::<T>()` precondition is discharged at each call site from a Verus `global layout` declaration for the concrete element type (`icns::Entry`, `ico::Entry`) in the core's `sites.rs`, which rustc checks as a static assertion: a wrong declaration fails the build with `E0080: evaluation panicked: does not have the expected size`. The axiom a `global layout` declaration introduces is usable **only inside the declaring module**. Every other module and crate gets the numbers through a `pub proof fn` exported from `sites.rs`, `lemma_entry_layout() ensures size_of::<Entry>() == S, align_of::<Entry>() == A` (one conjunct pair per element type), and the reservation call site calls that lemma before `try_with_room`. On x86_64 gate F2 measured and declared `size == 28, align == 4` for the D2-shaped ICNS `Entry` and `size == 44, align == 4` for ICO's `Entry` (its `EntryStatus` is 12 bytes), so the largest entry-list reservations are 4,096 × 28 = 114,688 B and 1,024 × 44 = 45,056 B, both proved below `isize::MAX` from the lemma with `nonlinear_arith`. These are prototype struct shapes: when each core's step lands, its `sites.rs` declares the layout of the real `Entry` and rustc re-checks it. The monomorphic `try_with_room_entry` fallback (size fixed by a static assertion in `sites.rs`) was not needed on x86_64 and stays available. `size_of::<Entry>()` can differ between 32- and 64-bit targets, so the declaration states a size per target. The x86_64 byte bounds above are frozen with the delta; no i686 bound is frozen until the declaration is instantiated and checked on i686, which needs that target's std (§6, *Targets*).

**A-STD**, the one trusted std contract, is stated for the concrete types the cores use: `Vec<u8>`, `Vec<icns::Entry>` and `Vec<ico::Entry>` with the `Global` allocator, both element types non-zero-sized. It is documented behaviour, tested at runtime and not proved:

- **A-STD-1** (`Vec::try_reserve_exact`, "Errors" and capacity docs). On an empty `Vec<T>` with `n >= 1` and `n * size_of::<T>() <= isize::MAX`, `Ok` implies `capacity() >= n`.
- **A-STD-2** (`Vec` "Guarantees": `push` "will never (re)allocate if the reported capacity is sufficient"). `push` does not allocate while `len < capacity`.
- **A-STD-3** (`try_reserve_exact` "Errors": capacity overflow or allocator failure). Under the size precondition above, capacity overflow cannot occur, so an `Err` means the allocator reported failure (returned null). This clause is used only to interpret `OutOfMemory` in documentation and tests; no theorem depends on it, and `OutOfMemory` means "the reservation returned `Err`".

Proof reports name the pinned toolchain (rustc 1.99.1, commit `58cf8f9c3`, 2026-10-13, the version Verus `0.0.0-2026-11-01-0251` pins, with its std) and the allocator under test (std `System`, glibc `malloc` on `x86_64-unknown-linux-gnu`, and on `i686-unknown-linux-gnu` once that target's std is installed, §6). The counting-allocator test (`THEOREMS-ALLOC-DELTA.md` §5) is a regression check of A-STD on that toolchain, not a proof of it.

### 3.1 ICO: importing DIB's log

DIB's guard keeps its own sealed log, of type `dib_verus::alloc_guard::AllocLog` with elements `(dib::AllocSite, nat, bool)`. ICO's log has elements `(ico::AllocSite, nat, bool)` with `ico::AllocSite = EntryList | Dib(dib::AllocSite)`. ICO's decode path reserves nothing of its own, so without an import its log would stay empty when DIB returns `OutOfMemory`, and A-ICO-2 clause 2 could not be established. ICO's `alloc_guard/sites.rs` therefore defines one verified exec function, which is part of the hashed and reviewed guard text:

```rust
// ico/ico_verus/src/alloc_guard/sites.rs (verified; hashed with sites.rs)
pub open spec fn map_dib(s: Seq<(dib::AllocSite, nat, bool)>) -> Seq<(AllocSite, nat, bool)> {
    Seq::new(s.len(), |j| (AllocSite::Dib(s[j].0), s[j].1, s[j].2))
}

pub fn import_dib(
    s: &[u8],                                       // the slice b[a..z] that ICO passed to DIB
    r: Result<dib::Decoded, dib::TryError>,
    Tracked(dlog): Tracked<dib::alloc_guard::AllocLog>,   // consumed: a tracked value is linear
    Tracked(log): Tracked<&mut AllocLog>,
) -> (out: Result<Result<dib::Decoded, dib::Error>, OutOfMemory>)
    requires
        old(log).view() == Seq::<(AllocSite, nat, bool)>::empty(),
        dib::dib::log_tied(r, dlog.view()),
        dib::dib::g_logged(s, r, dlog.view()),      // A-DIB-8: DIB's G on (slice, IcoEntryDibSlack)
    ensures
        final(log).view() == map_dib(dlog.view()),
        match r {
            Ok(d)                         => out == Ok(Ok::<_, dib::Error>(d)),
            Err(dib::TryError::Format(e)) => out == Ok(Err::<dib::Decoded, _>(e)),
            Err(dib::TryError::OutOfMemory(o)) => out is Err
                && out->Err_0.site_spec() == AllocSite::Dib(o.site_spec())
                && out->Err_0.elements_spec() == o.elements_spec()
                && final(log).view().last() == (AllocSite::Dib(o.site_spec()), o.elements_spec() as nat, false),
        },
        g_dib_arm(s, out, final(log).view()),       // A-ICO-2 G and Prog for the DIB arm,
        prog_dib_arm(s, out, final(log).view()),    // over out and the final log only
```

`dib::dib::log_tied(r, L)` is the log part of DIB's `G` clauses 1–2, exported by DIB with A-DIB-8: `r` is `OutOfMemory(o)` ⇒ `L` is non-empty, all entries but the last are `Ok`, and the last is `(o.site(), o.elements(), false)`; otherwise every entry is `Ok`. Given that `requires`, the `OutOfMemory` arm's last conjunct follows from `map_dib` and needs no further proof at the call site. The body's ghost part sets `log.ev = map_dib(dlog.view())` in a `proof` block, which it may do because `sites.rs` is a child of ICO's `alloc_guard` and the field is private to that module; reading `dlog.view()` needs only DIB's `pub closed spec fn view` and DIB's `ensures`, not the field. The exec part matches on `r` and, in the `OutOfMemory` arm, builds `OutOfMemory { site: Dib(o.site()), elements: o.elements() }`; that literal exists only here, in ICO's `sites.rs`.

**Why `import_dib` carries the A-ICO-2 shape itself.** `import_dib` consumes both `r` and the linear `Tracked` DIB log, so after the call `try_decode_entry_impl` can no longer cite DIB's `G` on them. Everything A-ICO-2 needs from the DIB arm must therefore be an `ensures` of `import_dib`, stated over `out` and `final(log).view()` alone: `g_dib_arm`/`prog_dib_arm` are ICO's `G` and `Prog` with `Eq = decode_mp_eq(fmt_part(·), s, IcoEntryDibSlack)` and `Req = map_dib(Req_DIB(s, IcoEntryDibSlack))`, defined in ICO's `sites.rs`. `try_decode_entry_impl` combines them with `MD`'s pre-DIB part to get A-ICO-2. The proof goes **arm by arm**: one `proof fn` per arm of DIB's result (`lemma_g_ico_ok`, `lemma_g_ico_format`, `lemma_g_ico_oom` in the prototype), each called in the corresponding `match` arm; the single-shot proof did not go through. `lemma_g_ico_oom` takes the already-built `out` as a parameter and states its shape through `site_spec`/`elements_spec`, because only `sites.rs` may build the literal. The prototype (`proto/guard_proto_dep/src/alloc_guard/sites.rs`) uses a toy DIB input and returns ICO's `TryError` directly, with a stand-in `map_err` for `Error::Dib(_)`; the production signature keeps the nested result above, which leaves the format-error wrapping to ICO's existing code.

Usage is fixed: `try_decode_entry_impl` calls `dib_verus::try_decode_with_steps_logged` once and passes its result and log straight to `import_dib`, which is the only route from a DIB result to an ICO result. The `requires old(log).view() == []` excludes a second import into a non-empty log, and the linear `Tracked` argument excludes importing one DIB log twice. The ghost-reading audit checks one call each (§6).

**Memory and timing.** Today `vec![0u8; n]` uses `alloc_zeroed`, which on Linux gets lazily zeroed pages. `try_zeroed` uses `alloc` and then pushes `n` zero bytes, so the 64 MiB maximum now costs one byte-wise fill and commits its pages at reservation time. DIB T12 already charges `4N` for this initialisation. Stable Rust has no fallible zeroed `Vec` constructor without `unsafe`.

**When `OutOfMemory` is observed.** With the size caps, a reservation fails only when the allocator returns null (A-STD-3): under `RLIMIT_AS` (glycin's sandbox sets one, see `TABLE.md`), `vm.overcommit_memory=2`, 32-bit address-space exhaustion or a failing custom allocator. Under Linux's default heuristic overcommit, a request of at most 64 MiB almost always succeeds, and real exhaustion surfaces later as the OOM killer, which no user-space code can turn into an error. A zero-element reservation never fails and never reaches the allocator.

- Changing a public field's type breaks the API, which is acceptable (decision D9). Version note, not a gate (O3): `icns_verus` 0.1.0 → 0.2.0, DIB 0.3.0 → 0.4.0, ICO 0.1.0 → 0.2.0. The conformance test (`tests/conformance.rs:83`) compares through `std::str::from_utf8(&a.type_hex)`. glycin-icns changes `legacy_kind(&str)` (`glycin-icns/src/lib.rs:55`) to take `&[u8; 8]` and match byte-string literals (`b"69733332"` …), and its call at `:104` and the test helper `side_of` (`tests/vectors.rs:48`, `:135`, `:154`) change the same way.

## 5. Deliberately infallible (not covered by `OutOfMemory`)

- **Ghost and spec values.** `Seq`, `Ghost<_>`, `Tracked<_>` and the `AllocLog` are erased at compile time and allocate nothing.
- **Stack.** Locals are fixed-size, and no core recursion depends on the input (frozen T1/T10 review). Stack exhaustion stays outside `Safe` and cannot be reported.
- **Panic-path allocation.** The cores contain no reachable panic (T1). In glue code the panic machinery boxes its payload and formats the message, so that allocation is infallible. A caught panic in the gdk-pixbuf module becomes `GDK_PIXBUF_ERROR_FAILED`. An out-of-memory abort is not a panic, and `catch_unwind` does not catch it.
- **Host-library allocation.** GLib's `g_malloc`/`g_slice` in gdk-pixbuf glue (`GError`, the `GdkPixbuf` GObject instance) abort by GLib's design. So do glycin's D-Bus, zbus and memfd code and the `png`/`image` crates on glycin-icns's unverified PNG path. `TABLE.md` lists each site.
- **Error-path strings in glue.** glycin's `ProcessError` messages (`format!`, `to_string`) are small and allocate only on a path that is already failing.
- **Abort shim crates.** They terminate on `OutOfMemory` by design and sit outside this delta's guarantee (§1.3).
- **Physical memory.** A successful reservation does not guarantee resident pages; see §3.
- **Deallocation.** It cannot fail.

## 6. Audit (per core, mandatory, run before every proof report)

Verus sees only what the guard signatures promise; it cannot see an allocation that bypasses the guard. The audit's job is to establish that no such allocation is reachable on any call path. A typed call-graph analysis is the only mechanism considered that could do that, and it does so only if every incoming path to an allocation-capable instance is checked (*Authorisation on every path*, below); a reachability walk that records one parent per instance does not. Text regexes cannot decide whether `.clone()` is on a `Copy` type, cannot follow user helpers or transitive callees, and cannot see allocations inside trait impls; an rlib's LLVM IR shows only external declarations for calls into precompiled std. So the gate is the call-graph audit below. The source lint, binary scan and runtime tests are falsification gates: a hit fails the gate, and a pass proves nothing.

**1. Call-graph audit (the gate).** The gate is `tools/alloc_audit`, a `rustc_driver` program built against the pinned rustc 1.99.1's `rustc-dev` component (installed for `x86_64-unknown-linux-gnu`; `#![feature(rustc_private)]`, built with `RUSTC_BOOTSTRAP=1` because 1.99.1 is a stable release). Cargo invokes it as `RUSTC_WORKSPACE_WRAPPER` on the core crate only. The prototype is `proto/alloc_audit/` (`src/{main.rs,walk.rs,allowlist.rs,report.rs}`, notes in `proto/alloc_audit/NOTES.md`). It is the reference for the edge resolution and the every-path enumeration below: its walk records the whole edge set, and a post-pass (`authorize_allocations`) judges every simple root-to-entry path. It is **not** the reference for node identity, build-input detection or the absent-allowlist case, where it has known defects that the production tool must fix (§8, *Known prototype defects*). Where this section states what "the tool" does, it states the production requirement; what the prototype does is stated separately.

*Mechanism.* The tool implements `rustc_driver::Callbacks::after_analysis`. With the `TyCtxt`, it:

1. Takes as roots `Instance::mono(tcx, def_id)` for every `pub` non-generic function the crate exports (the `try_*` functions and the `*_logged` exports; a main crate exports nothing else). No core exports a generic function; the tool fails if it finds one.
2. Runs a worklist over `Instance`s. For each instance with MIR available (`tcx.is_mir_available` for items, `tcx.instance_mir` for shims), it instantiates the body with the instance's generic arguments (`instantiate_mir_and_normalize_erasing_regions` under `TypingEnv::fully_monomorphized()`), which is the post-monomorphisation MIR, and walks every basic block:
   - `TerminatorKind::Call`/`TailCall` whose `func` operand has type `FnDef(def_id, args)`: resolve with `Instance::try_resolve`; the result is an edge to a concrete `Instance` (an impl method, a closure body, a shim). `Ok(None)` or `Err` fails closed.
   - `TerminatorKind::Drop { place }`: an edge to the drop glue for the place's monomorphic type, resolved through the `DropGlue` lang item with `Instance::try_resolve` (not `resolve_drop_glue`, which aborts the compiler on failure; a resolution failure is a finding). The glue shim's MIR is walked in turn, so `Drop` impls and field drops are reached.
   - `TerminatorKind::Assert`, and `Call`s to the `panic_*` lang items: an edge to the panic entry point (`core::panicking::panic_bounds_check`, `panic_const_*`, …). These paths allocate in std's panic handler.
   - Function pointers created in the body (`CastKind::PointerCoercion(ReifyFnPointer | ClosureFnPointer)`, `fn` items as constants): an edge to the pointed-to instance, so its body is audited even though the call through it cannot be resolved.
   - `Rvalue`s and constants that mention a `dyn` vtable (unsizing to `dyn Trait`): edges to every vtable method instance.
   - `InlineAsm`, `GlobalAsm`, `MonoItem::Static` with a function-pointer initialiser: fail closed.
3. Records **every** edge `(caller instance, callee instance, span)`, not one parent per callee, and reports the reachable set with every edge's source span.

*Authorisation on every path.* Monomorphised instances are shared: the one `Vec::<u8>::try_reserve_exact` instance is reached from `try_zeroed` and from any other function in the crate that calls it. An allowlist entry that admits an allocation-capable instance only from named callers is therefore satisfied only if **every** reachable incoming path to that instance passes through an admitted caller. The tool evaluates this over the full edge set: for each allocation-capable instance, every reachable caller instance must be either an admitted caller or itself reached only through admitted callers; any incoming path that leaves the admitted set fails the audit and is reported with its full root-to-instance path. A tool that cannot establish this for some instance fails closed on it. Checking one representative path, such as the first BFS parent, is not sufficient: an unapproved helper calling the same instance as the guard would be authorised through the guard's path.

The F1 prototype realises this rule as follows. For each allocator entry point reached, it enumerates every simple (non-repeating) root-to-entry path and judges each one by the last allocation-capable item on it and the nearest function before that item that is defined in the audited crate (`DefId::is_local`, so free functions, impl methods and closures all count). The tool consults every `alloc` entry that names that item, and the path passes only if one of them has an `allow` naming that crate function; a path with no crate function before the item passes only under `allow = "*"`. The entry is `OK` only if every path passes; otherwise each failing path is reported as `unauthorized-alloc-path`. Enumeration is bounded at 20,000 paths per root and depth 80; past either bound the tool emits a `path-bound` finding and fails. Std functions between the crate function and the item are not judged, because the pinned commit, not the allowlist, fixes them (*What the audit cannot see*, below).

*Caller and item identity.* The production tool MUST key every graph node, edge and path by `Instance` (and so by `DefId` plus generic arguments), never by a printed string. Printed def-paths are for display and for writing allowlist entries only. Each allowlist `item` and `allow` value is resolved once, before the walk, to the set of `DefId`s it names; a value that resolves to no `DefId` is a finding, and a value that resolves to more than one `DefId` (for example a local module `guard` and an external crate `guard` that both contain `try_zeroed`) is an `allowlist-ambiguous` finding, never a match on either. The audited crate's own items are written with a leading `crate::` and external items with their crate name, so no local value is spelt like an external one. Matching is then `DefId` equality, with the generic-argument rule below.

The prototype does not meet this requirement. It keys the visited set, edges and paths by the string `tcx.def_path_str(def_id)` plus printed generic arguments (`instance_label`, `proto/alloc_audit/src/walk.rs:1186–1202`; used at `:83–95`, `:446–457`), and `def_path_str` prints a local item without a crate prefix but an external one with it. A local `guard::try_zeroed` and `try_zeroed` in an external crate named `guard` therefore print identically: the walk merges them into one node, and `judge_path` (`walk.rs:1096–1122`) with `caller_matches` (`allowlist.rs:480–523`) admits the external function under `allow = "guard::try_zeroed"`. The prototype's def-path identity holds only in the single-crate toy setting of its controls, where no external crate shares a path with a local item. The string rule below is the prototype's and is stated so that its controls can be read; in the production tool it applies only to how a value is written before resolution to `DefId`s:

- An entry value `v` (an `allow` or an item) matches a def-path `p` the tool prints for an instance iff `v == p`, or the shorter of the two is a prefix of the longer and the remainder is exactly one balanced `<...>` group running to the end of the string (the trailing generic-argument list). No suffix, substring or reverse-suffix match exists. Because the remainder must begin with `<` and end the string, the match respects component boundaries: `alloc_guard::try_zeroed` matches neither `not_alloc_guard::try_zeroed` nor a crate-root `try_zeroed`, nor `alloc_guard::try_zeroed_extra`, nor `alloc_guard::try_zeroed<T>::f`. Generic parameters inside the path (the `<A>` of `RawVecInner::<A>::reserve_exact`) are ordinary path text and must be written as the tool prints them.
- On the `allow` side a leading `crate::` is stripped before comparison; nothing else is normalised.
- Generic arguments are optional in an entry. An entry that writes them (`…::reserve_exact<std::alloc::Global>`) matches that instantiation only; an entry that omits them matches every instantiation of the item reached from its admitted caller, so its contract must hold for each one (in the guard, `T ∈ {u8, Entry}`). The tool does not require generic arguments.
- `allow = "*"` is the only wildcard.
- Entries are per (item, `allow`). An item may carry several `[[entry]]` blocks, one per admitted caller, and the tool consults all of them: several admitted callers of one shared instance (in the guard, `try_zeroed` and `try_copy` both reach `Vec::<u8>::push`) each get their own entry, and every path to the instance must match one of them. An admitted caller never admits a caller it does not name.
- An `allow` value that names no function in the crate admits nothing, so the paths it was meant to cover fail with `unauthorized-alloc-path`. The tool does not report such an unused entry by itself (post-freeze hardening, §8).

Controls (F1, §8), each archived in `proto/alloc_audit/reports/`: `n12_suffix_lookalike` (`unapproved_guard::try_zeroed`, whose def-path ends with the admitted `guard::try_zeroed`, calls the same `reserve_exact` instance) and `n13_root_lookalike` (a crate-root `try_zeroed` does the same) each fail with 6 `unauthorized-alloc-path` findings naming the lookalike while the real guard's path stays `OK`; each would pass under the earlier two-way `ends_with` predicate. `c2_two_guards` (two admitted guards, one entry each, calling the same `reserve_exact<Global>` instance) passes, and fails with 6 findings if either entry is deleted; `n14_two_guards_plus_third` adds an unapproved third caller of that instance and fails with 6 findings naming it. A fragment in another module whose path is neither a suffix nor the crate root (`guard_extra::try_zeroed`) has no dedicated control; the rule excludes it by construction (no prefix relation holds). These controls are all single-crate. **Required control for the production tool** (no prototype control exists, and the prototype would pass it wrongly): `x1_extern_namesake`, a local module `guard` with an admitted `guard::try_zeroed` plus a dependency crate named `guard` whose `try_zeroed` reaches the same allocation-capable instance; the run must fail, with `allowlist-ambiguous` for an `allow` written `guard::try_zeroed` and, with the entry written `crate::guard::try_zeroed`, with `unauthorized-alloc-path` naming the external function's path, and the report must show the two functions as distinct nodes.

*Unresolved edges fail closed.* An edge the tool cannot follow to a body is a **leaf**, and a leaf passes only if it is an allowlist entry. That rule covers every case below:

- Precompiled std bodies without exported MIR (non-`#[inline]` functions, such as `alloc::raw_vec::handle_error`, `core::panicking::panic_fmt` and `panic_nounwind_fmt` on DIB release): leaf; allowed only by an allowlist entry whose contract says what the item allocates. The set is determined by the toolchain's inlining and MIR-export decisions, not fixed by this spec: `alloc::raw_vec::finish_grow`, which earlier drafts named here, has MIR and is walked in every configuration F1 ran, but becomes a leaf in any configuration where std ships its instantiation precompiled. The pinned commit is what fixes the set.
- Calls through a function pointer (`FnPtr` callee) or a trait object (`InstanceKind::Virtual`): fail. No core uses either; a justified exception would need the full set of possible targets listed in the allowlist, and none is planned.
- Intrinsics (`InstanceKind::Intrinsic`): leaf; allowed per intrinsic by name (`size_of`, `copy_nonoverlapping`, …). An unlisted intrinsic fails.
- Compiler-generated panic paths: leaf at the panic entry point; allowed only with the justification "unreachable by Verus T1/`Safe'` on this function", citing the verified theorem. The audit records one leaf per (function, panic kind) and prints the per-function list, so a new panic edge shows up as a diff between reports. The production allowlist enumerates the citation per function, so that a changed function re-opens exactly its own citation. (Making a new edge a hard failure rather than a diff line is post-freeze hardening, §8.)
- Compiler-generated allocation paths (`exchange_malloc` for `Box::new`, `alloc::alloc::*`): leaf; allowed only from the callers in the allocation-capable list below.
- FFI (`extern` items, `ForeignItem`): fail. The cores have none.
- `-Zshare-generics`: if enabled, generic std instantiations would come from upstream crates instead of being instantiated locally. `share_generics()` defaults to true for `-Copt-level=0/1/2/s` and false for `-Copt-level=3`, so the release profile disables it and a debug build has it on. The tool checks `tcx.sess.opts.share_generics()` and fails if it is on; a debug-profile run therefore fails for a reason unrelated to the code (*Targets* below).

*The allowlist* is a manually reviewed, per-(target, profile), hash-recorded transitive contract: `tools/alloc_audit/allowlist/<target>/<profile>/<core>.toml`. Each entry names a resolved item by def-path and generic arguments, states what the item and everything it calls can allocate (`none`, or the exact allocation events), and cites the evidence (std documentation clause, std source at the pinned commit, or the Verus theorem for panic edges). The file's `[meta]` records the rustc commit hash (`58cf8f9c3`), the vstd version, the target triple, the **profile**, the **`source_hash`** and the **named reviewer** who signed it. The tool computes the file's SHA-256 and prints it in the audit report, and the proof report records that hash. Any change of rustc/std commit, vstd version, target, profile or audited source invalidates the file, and it must be re-reviewed before the audit can pass again. The tool enforces this. **A proof-report run requires an allowlist file**: the production tool, run without one or with an empty path, fails with `allowlist-absent` and its report header says `diagnostic: no allowlist`; such a run is a diagnostic (it prints the reachable set, leaves and allocator entry points for drafting an allowlist) and never a pass. The prototype does not do this: with no allowlist it substitutes `Allowlist::empty()` (`walk.rs:101–105`), skips every provenance check (`:123–313`), and `passed()` (`report.rs:153–159`) can return `Pass` for a crate with no leaves and no allocator entry point. Prototype runs without an allowlist are diagnostics only, and none of the statements below about required fields applies to them. **Within a run that has an allowlist, every `[meta]` field is required**: a missing or empty field is its own fail-closed finding, never a skipped check (`allowlist-commit-missing`, `allowlist-target-missing`, `allowlist-profile-missing`, `allowlist-source-hash-missing`, `allowlist-vstd-missing`; a missing or empty `reviewer` is `allowlist-reviewer`). Each check below fails the run closed with its own finding:

- `rustc_commit` must equal the commit token in the running compiler's version string (`58cf8f9c3`) or its full 40-hex hash (read from `<sysroot>/bin/rustc -vV`), or be a prefix of that full hash at least 12 hex characters long. The comparison runs one way only: a recorded value longer than the full hash, or of which the running hash is a prefix, is refused (`allowlist-commit`).
- `vstd_version` must equal the version of vstd the build links. The production tool binds it to the linked artifact: it takes the `vstd` crate in the crate graph, reads that crate's on-disk rlib path from `used_crate_source`, and checks the path, the version and the source checksum against the locked resolution (`Cargo.lock` entry and the package's `.cargo-checksum.json` or git revision); it records the rlib's SHA-256 in the report. The `ALLOC_AUDIT_VSTD_VERSION` override is prohibited in proof-report runs: the production tool refuses to run without `--prototype` when the variable is set (`vstd-override-forbidden`). The prototype decides whether vstd is linked from the crate graph (a loaded crate named `vstd`) and reads the version string from the audited crate's `Cargo.lock` (found through `CARGO_MANIFEST_DIR`), or from the override when that is set, and it does not refuse the override. Its vstd controls (`c3_vstd_ok`, `c3_vstd_change`, `c3_vstd_missing`) all set the override, so they test the parsing and comparison of the recorded value, not the identity of the linked vstd. A recorded version that differs is `allowlist-vstd`; vstd linked but its version not determinable is `allowlist-vstd-undetermined`. A crate that does not link vstd must declare `vstd = "none"` (or `vstd_version = "none"`), else `allowlist-vstd-not-declared-none`; a crate that links vstd and declares `none` fails with `allowlist-vstd`. A vstd change invalidates the allowlist like a rustc change, because vstd's specs determine which std items the verified code calls.
- `target` must equal the session's target triple (`allowlist-target`).
- `profile` must equal, character for character, the profile the tool detects from the session, written `opt-level=<n>,debug-assertions=<on|off>,share-generics=<on|off>` (`allowlist-profile`). The report header prints the detected profile on every run, with or without an allowlist. A release allowlist run against a debug build fails on both `share-generics` and `allowlist-profile`.
- `source_hash` must equal the hash the tool recomputes from the source map (`allowlist-source-hash`, which prints the actual value): the SHA-256 of the lexicographically sorted SHA-256 hashes of the text of every source file in the compilation's source map outside the sysroot. It pins that text and does not depend on the checkout path. It binds **only** source-map text, and the report header says so on every run (`source-hash scope: source-map text only`): it does not bind `include_bytes!`/`include_str!` payloads, environment variables read by `env!`/`option_env!`, other build inputs (features, `RUSTFLAGS`, `--cfg`), `build.rs` output, proc-macro output or the proc-macro and other dependency crates themselves. The report header prints each file's hash and the combined value. The inputs the hash does not bind are handled by the **build-input inventory** rule below, which the proof-report process enforces.
- **Build-input inventory (proof-report process).** The proof report lists every build input of the audited compilation, each with a content hash: every source-map file; every file read by `include_bytes!`/`include_str!`/`include!`; every environment variable read by `env!`/`option_env!`, with its value; the exact rustc command line (features, `--cfg`, `-C` flags, `RUSTFLAGS`); for a `build.rs`, the hash of the script's source and of every file it emits into `OUT_DIR` plus its `cargo:` output lines; for every dependency crate, including proc-macro and Verus macro crates, the hash of the linked artifact and its locked source checksum, and for every `path` or `git` dependency a hash of its source tree's content; for every build unit cargo actually executed (each rustc invocation, each build-script run), its exact command line, environment and outputs; every file and environment variable read by a build script or proc macro. For a core with none of a kind, the list says so explicitly ("no `build.rs`", "no `include_*!`", "no `env!`"). The proof-report process also captures an **independent inventory** without the audit tool's detection code, and no single source in it is complete. rustc's dep-info for the same invocation (`--emit=dep-info`) names only the file and macro-environment dependencies rustc **tracks**: source-map files, `include_*!` targets, and one `# env-dep:NAME=value` line per `env!`/`option_env!` or tracked proc-macro environment access. A build script or proc macro that reads a file or environment variable through ordinary I/O (`std::fs`, `std::env`) leaves no dep-info entry. `cargo build -v` prints command lines, not the reads they perform; `cargo metadata` describes packages, not the build units cargo executed or the outputs they generated; `Cargo.lock` content-hashes neither a mutable `path` dependency nor an already-built dependency artifact. The process therefore captures or prohibits every other read: it runs cargo, its build scripts and rustc (which hosts the proc macros) under sandboxed read tracing that records every file opened and every environment variable read, with the environment reduced to the declared variables and any unrecorded read denied (for example, a sandbox that permits only declared paths and an interposed `getenv` that logs each name); it records the actual build-unit command lines and outputs from cargo (the traced `exec` calls and cargo's `--message-format=json` artifact messages, not `cargo metadata`), hashes every linked artifact, and hashes the source tree of every `path` or `git` dependency. The report fails when any input cannot be accounted for. The proof-report process compares the report's list mechanically with this captured inventory; any input present in one and missing from the other, or any hash that differs, blocks the proof report. That comparison checks the report against the captured inventory; it does not by itself prove either complete, since two incomplete lists can agree. Completeness rests on the capture: on rustc's dep-info for the rustc-tracked dependencies, tested by the `x2` controls (`include_bytes!` after a `"https://…"` string literal, a renamed `include_bytes` import, a `macro_rules!` macro expanding to an include), and on the read tracing with denial for build scripts and proc macros, tested by `x9_build_script_untracked_read` and `x10_proc_macro_untracked_read` (*Required controls*, below). The audit tool's build-input detection (next bullet) is a second, independent check, not the inventory.
- **Build inputs** outside the source-map text must be declared in the allowlist. Each declaration names its exact input. The wildcard `*` is accepted **only** for allocation-caller authorisation (`allow = "*"` on an `alloc` entry, *Caller and item identity*), never as the `item` of a `build-script`, `proc-macro` or `include` declaration, where the production tool rejects it (`allowlist-wildcard-build-input`). The production tool must detect build inputs from compiler-resolved information, not from a text scan: `include_*!` sites from the expanded crate (the spans whose expansion is an `include_bytes`/`include_str`/`include` built-in, or the files the session loaded, `sess.source_map()` plus the dep-info file list), the build script from cargo's unit metadata, and proc-macro crates by `CrateType::ProcMacro`/`tcx.crate_kind` rather than by dylib presence. It admits Verus's macro crates by binding the actual crates (their crate names **and** the artifact hashes of the pinned Verus release, recorded in the allowlist), not by a name prefix. It fails closed on every undeclared input it detects (`undeclared-build-script`, `undeclared-proc-macro`, `undeclared-include`).

  The prototype detects three inputs, prints each in the report header, and fails on an undeclared one **among those it detects**; its detection omits real inputs (below and *What the audit cannot see*), so for the prototype "an undeclared input fails the audit" does not hold in general:
  - a build script, detected by `OUT_DIR` being set in the compilation's environment, which cargo does only for a crate with a `build.rs`: declare `kind = "build-script"`, `item = "build.rs"`, else `undeclared-build-script`. A hand-driven compilation has no `OUT_DIR` and a `build.rs` would go unseen. The control `bs_build_script` sets `OUT_DIR` on a toy crate that has no build script; no control runs a real `build.rs` under cargo;
  - a foreign proc-macro crate, detected as a crate in the crate graph whose source is a dylib (so any dylib dependency is reported): declare `kind = "proc-macro"`, `item = "<crate>"`, else `undeclared-proc-macro`. `vstd` and **every crate whose name begins with `verus`** are admitted without an entry (`allowlist.rs:617–625`), so a crate named `verus_evil` is admitted;
  - an `include_bytes!`, `include_str!` or `include!` site found by a text scan of the crate's own source, other than `include!` of a `.rs` file: declare `kind = "include"`, `item = "<macro>!<argument>"` (for example `include_str!payload.txt`), else `undeclared-include`. A non-literal argument is recorded as `(non-literal)`. The scan blanks everything after the first `//` on a line, inside a string literal too (`strip_line_comments`, `allowlist.rs:645–659`, `:673–685`), so `let u = "https://x"; include_bytes!("p.bin")` hides the include.

  The prototype also accepts `item = "*"` in all three declaration kinds (`Allowlist::declares`, `allowlist.rs:335–342`, used at `:300–309`, `:709–713`), so one wildcard entry admits every detected build input.

  A declaration admits the input's presence; it does not bind its content, which the build-input inventory above binds.
- `reviewer` must be non-empty and must not be the literal `prototype-fixture` (`allowlist-reviewer`). The literal is accepted only when the run sets `--prototype` (`ALLOC_AUDIT_PROTOTYPE`), and the report header then prints `mode: PROTOTYPE`. An audit run for a proof report does not set the flag, so a report whose header carries `mode: PROTOTYPE` cannot back a proof report.

The F1 prototype implements the commit, target, profile, `source_hash` and reviewer checks above, and the vstd check only as a comparison of version strings; it does not implement `allowlist-absent`, `DefId` keying, `allowlist-ambiguous`, the refusal of `*` in build-input declarations, compiler-resolved build-input detection, binding of the Verus macro crates, the vstd artifact binding or the override refusal (§8, *Known prototype defects*). Its controls (`proto/alloc_audit/allowlist/`, reports in `reports/`; this list is the 38 archived at the eighth revision, and controls added in `proto/` since then are not counted): mismatch fixtures for commit, target, profile (release allowlist on a debug build, and a recorded opt-level that differs), `source_hash` and reviewer (empty, and `prototype-fixture` without `--prototype`), with `c1_named_reviewer.toml` as the accepting case; missing-field fixtures `c1_commit_missing`, `c1_target_missing`, `c1_profile_missing` and `c3_vstd_missing`; commit-length fixtures `c1_commit_toolong` (the full hash plus two hex digits) and `c1_commit_short` (6 hex digits); vstd fixtures `c3_vstd_ok` (passes), `c3_vstd_change` and `c1_vstd_undeclared`; build-input fixtures `n15_include` and `bs_build_script`. Two fields have no missing-field fixture: an absent `source_hash` (the code path `allowlist-source-hash-missing` exists but no control runs it) and an absent `reviewer` key (only the empty value is tested). No archived control exercises `allowlist-vstd-undetermined` or `undeclared-proc-macro`.

*What the audit cannot see.* The tool audits the MIR rustc hands it, and these gaps remain by construction:

- Const-eval and static-initialiser allocations: not a MIR `Call` in a root body, so not reported. No DIB root has one; a core that gains one needs a separate static-initialiser pass.
- Panic-path allocation: std's panic machinery allocates its payload. A panic edge passes only by a reviewer's T1/`Safe'` citation that it is unreachable; the tool does not analyse the handler, so for each panic edge the citation, not the tool, carries the "no allocation outside the guard" claim.
- Precompiled std bodies without MIR: leaves whose contracts are human assertions, and which items are leaves depends on the toolchain. Only the pinned commit hash in the allowlist fixes that set.
- Indirect calls: for a `fn`-pointer call the tool recovers candidate targets from casts in the same body and audits them, and for a `dyn` call whose unsizing it sees it follows the vtable, but it cannot prove either candidate set complete, so both fail closed.
- Allocator identity: the tool sees `__rust_alloc` reached, not which `GlobalAlloc` is installed. A-STD and the proof report's named allocator tie `__rust_alloc` to the allocator under test.
- Path-enumeration bound: the every-path check enumerates at most 20,000 simple paths per root, to depth 80. A call graph past either bound fails the audit with `path-bound`; it never passes quietly, but the report then does not name every path, and such a core cannot pass until the graph shrinks or the bound is raised. Restricting to simple paths loses nothing for reachability: a node reached through a cycle is also reached by the simple path that first enters it.
- Source hash scope: `source_hash` covers the text of the source files in the audited compilation's source map outside the sysroot, and nothing else. It does not bind `include_bytes!`/`include_str!` payloads, `env!`/`option_env!` values or other build inputs (features, `RUSTFLAGS`, `--cfg`), `build.rs` output, proc-macro output, or proc-macro and other dependency crates. Std and the rest of the sysroot are pinned by the recorded rustc commit, not by a hash. A `path` dependency's text is covered only if that dependency is audited in its own right and its hash recorded (the dependency-contract rule above, ICO admitting DIB); the prototype does not implement that check. Each unbound input is bound by the proof report's build-input inventory, checked against an independently captured inventory (rustc dep-info for rustc-tracked dependencies, read tracing with denial for build scripts and proc macros, build-unit records, artifact and source-tree hashes; *The allowlist*, above); without that inventory no proof report is issued.
- Build-input detection by the audit tool sees an input's presence, never its content, and does not detect `env!`/`option_env!`, features, `RUSTFLAGS` or `--cfg`; those rest wholly on the inventory. The production tool's detection is compiler-resolved (*Build inputs*, above). The **prototype's** detection is heuristic, covers three inputs, and both over- and under-reports:
  - the build script is seen only through `OUT_DIR`, so only under cargo; within cargo it over-reports (any `build.rs` sets it). Its control injects `OUT_DIR` into a crate with no build script;
  - proc-macro crates are seen as dylibs in the crate graph, so a non-proc-macro dylib dependency is also reported (over-report); Verus's macros are admitted by name prefix (`vstd`, `verus*`), so any crate whose name begins with `verus`, such as `verus_evil`, is admitted without an entry (under-report);
  - `include_*!` sites are found by a text scan that blanks everything after the first `//` on each line, **including a `//` inside a string literal**, so `let u = "https://x"; include_bytes!("p.bin")` hides the include (under-report). It also misses a renamed import (`use core::include_bytes as ib; ib!(..)`) and a `macro_rules!` macro from another crate that expands to `include_*!` (under-report), and reports a macro name inside a block comment or string literal as a site (over-report);
  - one `item = "*"` declaration admits every detected input of its kind.
- vstd version source: the prototype reads a version string from `Cargo.lock`, which does not distinguish two vstd trees with the same version string, and the `ALLOC_AUDIT_VSTD_VERSION` override takes precedence and is checked against nothing. Recording an override's value cannot show which vstd was linked, so the override is prohibited in proof-report runs, and the production tool binds the version to the linked rlib and its locked source checksum (*The allowlist*, above).
- Node identity: the prototype keys nodes by printed def-path string, so a local item and an external item with the same printed path merge (*Caller and item identity*). This is a prototype defect, not a limit of the design; the production tool keys by `Instance`.
- Authorisation scope: a path is judged by the nearest function defined in the audited crate, so the allowlist constrains that crate's callers only. A std function that calls the same allocation-capable instance is not matched against any `allow` value. The audit therefore establishes "no allocation outside the guard in this crate"; an `OK` line does not mean that no std caller reaches the instance.

i686 is **unaudited** (above); the gaps listed here are the x86_64 audit's.
