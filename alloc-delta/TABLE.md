### Deliberate-abort message (shims with no error channel)

```
verified-decoders: <shim>: out of memory: could not allocate <N> bytes for <site>; <API> cannot report allocation failure, aborting
```

`<shim>`, `<site>` and `<API>` are `'static` strings, and `<N>` is formatted into a stack buffer. The message goes to fd 2 with one `write(2)` per piece, then the shim calls `std::process::abort()`. `panic!` is not used: the panic machinery boxes its payload and formats the message, so under genuine exhaustion it ends in std's generic `memory allocation of … failed` abort and hides the shim's message.

### When "graceful" actually happens

An `OutOfMemory` result needs a reservation to fail. Under the delta's size caps that means the allocator returned null (`SPEC.md` §3, A-STD-3), which happens under:

- glycin's sandbox: it sets `RLIMIT_AS` to 0.8 × (min(MemAvailable + SwapFree, 20 GiB) − 200 MiB) (`glycin-core/src/sandbox.rs:552–618`), so a large request fails cleanly.
- `ulimit -v`.
- `vm.overcommit_memory=2`.
- 32-bit address-space exhaustion.

In-process gdk-pixbuf on default Linux overcommit almost never sees null for a request of at most 64 MiB. Real exhaustion there arrives as the kernel OOM killer, which no library can report.

## README text: "Allocation failure"

> ### Allocation failure
>
> **Verified decoders do not abort on allocation failure.** Each decoder crate exports only `try_` functions. Each decoder's heap allocations are a few reservations whose sizes the image header determines and the 64 MiB caps bound. If a reservation fails, the decoder returns `OutOfMemory`, separate from the format errors. Nothing is leaked, and no partial image is returned. Errors detected before the first reservation are reported as format errors, never as `OutOfMemory`; an error detected later can be displaced by `OutOfMemory` (for example, an ICNS file with one complete entry and a truncated second entry header). The proofs show that every `OutOfMemory` follows a reservation that actually failed, and that when every reservation succeeds the result is exactly the specified one. They assume that the allocation guard's reviewed, hash-checked body returns an error exactly when Rust's `try_reserve_exact` does, and Rust's documented `Vec` capacity guarantees; tests check both. An audit of the compiled call graph shows that every call path to an allocating standard-library function passes through the guard, in release builds on the audited targets (64-bit x86 Linux; 32-bit x86 is listed as not yet audited). The audit assumes a hand-reviewed allowlist of the standard-library functions the decoders call, signed by a named reviewer and tied to the compiler version, the verification library version, the target and the build profile, and by hash to the text of the decoder's own source files. That hash does not cover files pulled in with `include_bytes!`/`include_str!`, environment and build settings, build-script or procedural-macro output, or dependencies. The proof report therefore lists every build input with a hash of its content. That list is checked against an inventory captured independently while the build runs: the compiler's record of the files and environment variables it tracks, plus a trace of every file and environment variable read by build scripts and procedural macros, which may read nothing they have not declared; the build steps actually run and their outputs; and hashes of every dependency's built artifact and of local dependencies' source. Any input that cannot be accounted for fails the report; the audit tool also fails on any build script, procedural-macro crate or included file that it detects and that the allowlist does not name exactly. The audit checks the decoder crate's own call sites; the standard library's internals are fixed by the pinned compiler version, not checked by the audit. A call graph too large for the audit to enumerate fails the audit rather than passing it.
>
> **The older function names (`decode`, `parse`, `combine`, …) are gone from the decoder crates.** Optional separate `<core>_abort_shim` crates provide them as thin unverified wrappers that abort the process on allocation failure, for callers who don't care about recovery and don't need API stability. The decoder APIs are unstable and may change without notice.
>
> **gdk-pixbuf module:** an allocation failure inside the decoder, the input buffer or the pixel buffer is reported as `GDK_PIXBUF_ERROR_INSUFFICIENT_MEMORY`. GLib itself still aborts if it cannot allocate its own small objects (an error record or the `GdkPixbuf` object), with GLib's `failed to allocate N bytes` message. That is GLib's policy and the module cannot change it.
>
> **glycin loaders:** a decoder allocation failure is returned to the application as glycin's out-of-memory error (`Error::is_out_of_memory()`). Through libglycin's C API it arrives as `GLY_LOADER_ERROR_FAILED`, since that enum has no out-of-memory code. Small error-message allocations and the PNG path inside ICNS files can still abort the loader process. The application then sees "Loader process exited early", and the loader's stderr says `memory allocation of N bytes failed`. Only that sandboxed loader process dies, not the application.
>
> **C-API shims** whose API cannot report an error abort deliberately with
> `verified-decoders: <shim>: out of memory: could not allocate <N> bytes for <site>; <API> cannot report allocation failure, aborting`.
>
> On Linux with default memory overcommit, large allocations rarely fail outright; real exhaustion usually ends in the kernel OOM killer, which no library can turn into an error. `OutOfMemory` is reliably observable under an address-space limit (`ulimit -v`; glycin's sandbox sets one) or with overcommit disabled.
>
> **no_std.** The decoder crates are `#![no_std]` and use only `core` and `alloc`; their one dependency is `vstd` built with `default-features = false, features = ["alloc"]`. Checked on each release: `cargo tree -e normal,no-proc-macro` lists only `vstd [alloc]` and `verus_builtin`; the built library's crate-dependency list (`rustc -Zls=root`) contains no `std`; and the library compiles for `x86_64-unknown-none` and `thumbv7m-none-eabi`, which have no `std`, and for `i686-unknown-linux-gnu`. Those three targets are compile evidence only: the verifier and the tests ran on 64-bit x86 Linux, and no binary was linked or run elsewhere. The production call-graph allocation audit has not run on these crates on any target. An embedding program supplies a `#[global_allocator]` and a panic handler. If your build depends on `vstd` elsewhere, set `default-features = false` there too, or cargo re-enables `vstd`'s `std` feature for the whole build. The abort-shim crates, the gdk-pixbuf module and the glycin loaders use `std` and are not part of this claim, nor are tests and examples.

The first paragraph's "proofs show" and "audit shows" sentences may be published for a core only once that core's proof report exists, which requires the prerequisites in `SPEC.md` §8, none of which holds: the production audit tool, keeping the prototype's every-path authorisation and profile refusal and fixing its known defects (`Instance`/`DefId` node identity with ambiguous allowlist names rejected; compiler-resolved build-input detection; exact build-input declarations with no `*`; Verus macro crates bound by identity, not a `verus` name prefix; an absent allowlist failing; vstd bound to the linked artifact with the override refused); a proof report whose build-input list is checked against an independently captured inventory (rustc dep-info for rustc-tracked dependencies only; sandboxed tracing of every file and environment read by build scripts and proc macros, with unrecorded reads denied; the actual build-unit command lines and outputs; artifact hashes and source-tree hashes for `path`/`git` dependencies; failure on any input not accounted for), where the comparison checks the report against that inventory and does not by itself prove completeness, and controls `x9`/`x10` (an undeclared file read and an undeclared environment read by a real build script and by a real proc macro) block the report; a post-change allowlist signed by a named human reviewer, passing without `--prototype`; production `try_zeroed` with `#[inline(never)]`.
