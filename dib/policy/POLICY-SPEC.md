# BMP/DIB policy specification (frozen)

This document defines a proposed byte-only extension of frozen DIB-CORE-SPEC 1.1. The 1.1 R1–R20 order, RGBA8 layout, limits and first-error names remain the default. The stable `decode(bytes, mode)` keeps all four modes and its original result type. A separate `decode_with_policy(bytes, bmp_mode, profile)` accepts only `BmpFile` or `BareDib` and one of four named profiles; it returns RGBA8 plus `recovered: bool`. Neither ICO mode has a policy argument or a fallback to Strict inside the profiled entry point. `Policy::default()` is Strict; the profile selector and any future enum are `#[non_exhaustive]`. The record of individual field values is internal and experimental, not a public constructor. This draft does not authorize a freeze or select glycin's default profile.

**Non-negotiable for every policy value:** `MAX_INPUT=MAX_OUTPUT=67,108,864`, `MAX_DIMENSION=8192`, exactly one output allocation of `4N` bytes on success, zero header-error allocations and no other input-dependent allocations; no read beyond the slice, integer overflow, panic or nontermination on any bytes. The actual decoder's charged work must remain `steps <= 16*(|b|+N)` with `N=0` on failed header validation. T1, T3, T11, T12 and all resource bounds are universally quantified over Policy; T2 and T5–T10/T13 compare against the **selected** model. Allocation failure and ordinary stack assumptions remain as in R17. The Python oracle is a reference model and allocates Python temporaries; its memory behavior is **not** evidence that a future Rust implementation meets R17/T3. A native library's acceptance above these limits is not part of any profile.

All entries below are deterministic functions of bytes under those caps and safe *when implemented with guarded reads and checked arithmetic*. An `Ignore` field suppresses only its named check; it never relaxes the input/output caps or silently enables unsupported codecs. The oracle rejects bad modes/policies as typed-API errors, not format errors. Where a library has no byte-determined equivalent, the table names a safe surrogate rather than claiming exact native equivalence.

The universal bounds apply to every **retained internal field combination**, including test-only records, even though callers can select only named profiles. Rust custom-record constructors exist only under `#[cfg(test)]` and are absent from release builds; the Python oracle's `EXPERIMENTAL_OPTIONS` switch controls reference-model probes. Metadata-only `Recommended` equals Strict except `file_size=Ignore` and `image_size=Ignore`; because ignored `bfSize` can be an inflated truncated-download signal, applications must opt in deliberately. A successful profiled Blank result may amplify a tiny metadata stub to the 64 MiB output cap, with exactly one capped output allocation.

`recovered` reports **only** the following data-affecting events; no unlisted tolerance sets it:

- An invalid BMP pixel offset selects a different guarded pixel start or initialized blank output: Gdk indexed invalid offset, Gdk BI_RGB clamp below metadata end, or an `AllowAny`/Gdk BITFIELDS offset outside `[18,|b|]` that still yields output.
- `bitfield_offset=MetadataEnd` reads BITFIELDS pixels from the metadata end rather than a different, otherwise valid declared `bfOffBits` (including a gap, optimal colour table or V4/V5 profile bytes).
- `ParsedFields` accepts a declared header end beyond EOF, making the input header structurally incomplete.
- `incomplete_metadata=Blank` returns initialized pixels for missing external masks or nonempty palette/table bytes.
- `short_indexed_gap=Blank` returns initialized pixels in place of source pixels.
- `masks=DefaultRGB` substitutes default RGB/alpha masks for a missing RGB mask.
- `short_pixels=ZeroFill` leaves at least one incomplete or absent source row initialized instead of decoding it.
- `palette_index=Black` substitutes an out-of-range palette index during a pixel write.
- `rle_overrun=Clip|Image` discards positions of an over-long encoded run; `Clip` also discards positions of an over-long absolute run.
- `rle_delta=ClampStop` changes a destination coordinate only when it exceeds width or height; an exact destination equal to width/height is accepted but does not itself set the flag.
- A non-`Palette0` RLE initialization leaves at least one output pixel unpainted when decoding stops (the early-end fill event).

The flag remains false for ignored `bfSize`/`biSizeImage`, reserved words or planes, ignored BMP trailing bytes, a complete image ending in EOL then EOB under StopAtHeight, and a non-`Palette0` prefill that is completely overwritten. Consequently `recovered=false` does **not** imply that Strict accepts the file: Recommended may accept a metadata-only mismatch. The old `decode` result remains byte-identical to 1.1 and exposes no flag.

| `unsupported` | **`Reject`**: R4 keeps six depths and four compression codes; `Rgb2`: add 2-bpp only for H>=40. | `reserved` | **`Zero`**: R1 requires both LE16 reserved fields zero; `Ignore`: suppress only these checks. | image-rs/GDK accept some random-bitflip metadata (`07-random-bitflip.bmp`); independent of bfSize, deterministic/safe. |

R14's operational order is unchanged wherever a check still exists: input cap; BMP header, magic/size/reserved/basic offset; DIB size/header, planes, dimensions, depth/compression, colour count/output cap, masks, palette end and availability; source row/RLE command; image size; ICO mask; exact BareDib tail. Recovery checks occur at their old sites, never before a preceding error. A recovered short row must not read or parse absent bytes. Use checked u64 arithmetic for metadata ends and logical row cursors even on 32-bit targets: repeated logical stride advancement after a truncated 8,192-pixel image can pass 2^32. An RLE cursor never moves backwards; `Clip` consumes the complete encoded/absolute packet but iterates **only** over painted positions (`min(quantity, width-x)`), with zero iterations for clipped positions. RLE EOB ignores BMP suffix; BareDib rejects a surplus suffix and allows the logical cursor past exhausted input only for `short_pixels=ZeroFill`. No policy may accept an invalid profile selector by defaulting it to Strict.

## Named profiles

These are proposals measured against installed gdk-pixbuf **2.42.12** and image **0.25.10**, not assertions of complete equivalence. `S/G/I/R` denote Strict/GdkCompat-2.42.12/ImageCrateCompat-0.25.10/Recommended. The table gives **every selectable field assignment**; profile names and their tables must remain immutable after a future freeze, with a new name for each changed version. The oracle checks all 302 byte-identical frozen 1.1 vectors on every run; `cmp` checks the copied vector file, not the decoder. Independently, Strict's accept/reject and successful RGBA SHA-256 agree with the shipped verified runner on all 10,000 seed-731 inputs. These are regression checks, not a proof. `POLICY-VECTORS.json` and `CUSTOM-VECTORS.json` use records `{name,mode,input_hex,expected}` and internal custom rows add a `policy` object; successful profiled expectations add `recovered: bool`. Format errors retain `{error: name}`; the unchanged strict vectors have no recovery field. Custom records are not accepted by `decode_with_policy`.

`ImageCrateCompat-0.25.10` and glycin's in-tree image-rs path represent one BMP implementation, not two votes. `GdkCompat-2.42.12` targets the stream/whole/incremental **byte** paths; filename magic sniffing cannot be included in its bytes-only claim. Neither compatibility profile's BareDib behavior has native differential validation: the measurement harness feeds BMP files only. Ties and residuals are counted by `validate.py`; errors are compared as accept/reject, successes by dimensions and SHA-256 of every normalized RGBA byte, never by native error string. The JSON report groups by input provenance and candidate option family; provenance is an input-generation label, not proof of a mismatch's cause. The first reviewer fuzz pass compared accept/reject and pixels, **not error names**; the second pass included exact first-error names and found the depth-2 ambiguity resolved by D15 above.

## Not reproducible, explicitly excluded

- Filename extension and loader dispatch change GDK's result for identical **valid-`BM` but otherwise damaged** bytes (#2345/#2451); a byte-only API cannot inspect a path. This is not evidence that GDK accepts a bad signature; every named profile requires `BM`.
- C pixbuf state, chunk timing and callbacks can expose a partially decoded image and its previous allocation contents on short input; only initialized ZeroFill is allowed, even when a particular run's bytes happen to match.
- Out-of-range GDK pointer arithmetic and invalid shifts for malformed masks/deltas have no safe semantics; reject, clip or substitute by explicitly selected bounded rules instead.
- Any result dependent on current allocator contents, hidden library state, filesystem I/O, embedded profile renderer or caller-provided filename is excluded from pure bytes. Native renderer path differences must be reported rather than merged into one vote.

## Recorded decisions and remaining boundary

- D1/D7/D10/D14: The unchanged `decode` serves all four modes; `decode_with_policy` serves only BMP/BareDib with a named profile. Rust custom-record construction is `#[cfg(test)]`-only and absent from release builds; the Python switch only controls test probes.
- D2/D3: `Recommended` differs from Strict only by ignoring `bfSize` and `biSizeImage`; short pixels, malformed RLE and noncanonical palette/mask data retain Strict checks.
- D4/D11/D13: ZeroFill and Blank appear only in opt-in compatibility profiles; profiled successes carry the closed-list `recovered` flag, including early initialized Blank output but excluding metadata-only tolerance and complete RLE images.
- D5/D6: Indexed count and declared BMP pixel offset remain authoritative in Strict/Recommended. Unknown compression and damaged magic remain errors in every profile.
- D8: Glycin's default remains an integration decision, not an implicit choice made by this specification.
- D9/D12/D15: Profile names are versioned and immutable once frozen; R14 and the closed error set fix first-error names, including `InvalidPixelOffset` for Gdk BI_RGB past EOF, `TruncatedPixels` after a short Gdk BITFIELDS raw offset, `InvalidColorCount` for BareDib high-depth count, `InvalidCompressionDepth` for H>=40 depth-2 compressed data, and `TruncatedMasks` for absent internal masks.

No policy changes ICO directory-range recovery, PNG selection or the exact-versus-slack R12/R19 distinction; review an ICO-specific API separately.
