# DIB policy/profile design: report (coordinator, after the first review fixes, 2026-11-09)

Status: unfrozen draft; third independent review done, final recheck pending. 22 selectable internal fields (named, versioned profiles are the only public selectors; custom records are internal/experimental and disabled by `EXPERIMENTAL_OPTIONS=False`), 4 profiles: Strict (shipped 1.1 behaviour; 302 frozen vectors pass; STRICT-VECTORS.json byte-identical to the frozen file), GdkCompat-2.42.12, ImageCrateCompat-0.25.10, Recommended (= Strict + ignored bfSize and biSizeImage only). 102 vectors per profile, 66 internal custom probes, all pass. `decode(bytes, mode)` stays policy-free for all four modes (ICO modes are Strict forever); `decode_with_policy` is BMP/BareDib only and returns a `recovered` flag (true whenever a fill/clip/recovery option fired; always false for Strict).
Hard invariant (reviewer-confirmed): resource limits, totality, safety and the work bound hold for every option; output is bounded by 4N <= 64 MiB before allocation; Clip is accounted with zero iterations over clipped positions.

Do not present GdkCompat as exact parity: on novel accepted inputs it agrees on 97.1%. 'All inputs' counts both-reject as agreement (GDK accepts about 52% of inputs, image-rs about 32%). The earlier 'held-out seed 81573' claim was overstated (~71% of its inputs had been seen) and is withdrawn; the novel seed-4242 set replaces it. BareDib parity against native libraries is unvalidated (no library decodes bare DIBs): profile behaviour there is spec-only.
Not reproducible from bytes: truncated-pixbuf/allocator behaviour, GDK filename dispatch, progressive-state outputs. The loaded GDK module also accepts some biClrUsed values at high depth that the checked-out C source does not explain (flagged in the spec).
Recommended first implementation step: typed policy + spec-level Strict bridge under the existing API, then metadata-only file_size/image_size Ignore.
