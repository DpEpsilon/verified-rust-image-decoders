# Design notes — draft 2, not frozen

The core accepts `(bytes, mode)` for `BmpFile`, `BareDib`, or `IcoEntryDib`. A later ICO/CUR container validates directory entries, chooses DIB versus PNG, and passes exactly one selected entry slice; ANI/RIFF framing is another layer. `tools/run_corpus.py`'s first-DIB selection and two malformed-CUR workarounds are diagnostics, not that container contract. Differences below are deliberate; `RECALLED` identifies producer behavior not established by reading a primary format specification.

- **BmpFile tolerates stale short file-size metadata and suffixes (D1).** Accept `bfSize=0` or any `bfSize<=|b|`; reject a nonzero value larger than the slice, and still require both reserved words zero. After fully decoding pixels, ignore all remaining BmpFile bytes. `io-bmp.c:269–286,799–803` does not require the declaration to equal the available slice and discards unused data. A BMP with a complete raster and extra bytes now succeeds; a truncated raster still fails. `BareDib` and `IcoEntryDib` remain exact-slice decoders and reject suffix bytes. The low bound `bfOffBits>=18` only guarantees room for the four-byte DIB size word; the table-end check is separate.
- **The V5 profile choice needs no extra parser fields (D3).** D1 already accepts every BMP with a complete pixel array followed by exactly its profile span, including both sampled profile BMPs. It also tolerates other BMP suffixes, which is broader than validating the three V5 profile-offset/length fields. Adding those fields cannot improve acceptance under D1 and would contradict its ignore-suffix policy if used as a rejection condition. The core never reads, transforms or authenticates a colour profile. BareDib and ICO still reject profile-like suffixes.
- **Indexed short palettes are strict; optional high-depth BMP palettes are accepted (D2).** `biClrUsed<=2^depth` for 1/4/8 bpp; a short palette is real and an absent indexed colour yields `PaletteIndexOutOfRange`. At 16/24/32 bpp BmpFile alone skips `4*biClrUsed` optimal-colour bytes after masks and requires `bfOffBits` beyond them. BareDib/ICO reject nonzero high-depth `biClrUsed`; they have no file offset to distinguish an optimal table from pixels. `io-bmp.c:353–375,535–546,604–610` treats high-depth metadata more liberally. Three corpus files previously failed this high-depth rule; D2 accepts `rgb16-565pal.bmp`, `rgb24pal.bmp`, and `rgb24largepal.bmp` without treating table RGB as alpha. Compute the four-byte-table length and end in `u64` before converting to `usize`: `biClrUsed=0x40000000` cannot wrap to a zero-length table on a 32-bit decoder. The malformed `badpalettesize.bmp` remains rejected.
- **The palette and row rules remain explicit.** CORE uses three-byte entries; INFO/OS2-short use four, ignoring reserved bytes. Raw 1 bpp reads MSB first; raw 4 bpp reads high nibble first at even x; every row has four-byte alignment. The last row must include padding too: producers omitting final pad fail `TruncatedPixels`. At 1 bpp ICO the core honours the declared palette, unlike the black/white hardcoding at `io-ico.c:790–815`; a custom monochrome palette changes colours.
- **Header and resource choices remain bounded.** Supported headers: 12,16,40,52,56,64,108,124; the local baseline `io-bmp.c:292–342` omits 16, while `io-ico.c:421–428` compares selected directory dimensions, unavailable to this core. CORE is unsigned 16-bit; OS/2 2.x signed 16/64 interpretation is a strict choice against RECALLED unsigned format semantics. Depth 2 (`pal2.bmp`), BI_ALPHABITFIELDS 6 (`rgba32abf.bmp`), JPEG/PNG BMP, OS/2 Huffman/RLE24, and unknown headers stay unsupported. The 8192-per-side and 64 MiB input/output limits reject otherwise parseable oversized images; a roughly 35-million-pixel 600-dpi A4 scan would exceed the 16,777,216-pixel output cap. A successful implementation requests exactly one `4N` allocation; stack size/allocator overhead are not purported Verus-proven constants.
- **BITFIELDS rejects guessed or ambiguous masks.** Require RGB masks nonzero, contiguous, disjoint and inside the pixel word; valid A may be zero or disjoint. `io-bmp.c:688–711` invents defaults for missing RGB masks and `:633–647` counts bits without checking contiguity. Exact rounded scaling differs from `io-bmp.c:956–975`'s five-bit replication: input value 3 rounds to 25 rather than 24. BI_RGB16 ignores bit 15 and applies the same rounded 555 scaling. Top-down BITFIELDS are accepted outside ICO. `io-ico.c:366–388` **skips all compressed ICO entries, including BI_BITFIELDS=3**, so accepting ICO BITFIELDS is an extension, not a claim that the baseline would misrender those entries.
- **BMP BI_RGB32 ignores its stored alpha byte** (`io-bmp.c:884–892`); meaningful producer alpha stored without a mask is lost, consistent with the baseline. V4/V5 masks are ignored when compression is BI_RGB. ICO BI_RGB32 reads A initially, then applies the global rule below. Output always uses tightly packed, non-premultiplied, top-first RGBA instead of progressive pixbuf callbacks (`io-bmp.c:499–523,1092–1101`; `io-ico.c:543–547,893–905`).
- **ICO 32-bpp alpha uses the owner's Windows-style whole-image policy (D4).** When *any* XOR alpha is nonzero, ignore AND and keep every XOR alpha (including zero pixels); when all XOR alpha is zero, AND=1 becomes transparent and AND=0 opaque. A 32-bit BITFIELDS entry with no alpha mask uses AND as a veto instead. `io-ico.c:823–825` skips AND at 32 bpp without the zero-alpha fallback. Files that relied on all-zero A to mean transparent despite an all-zero AND mask become opaque here; a writer that marked AND=1 beside meaningful A now retains the XOR A. At 1/4/8/16/24 bpp AND=1 forces alpha zero; an AND=0 leaves a BITFIELDS alpha unchanged.
- **ICO image length accepts both common declarations (B1).** For a complete XOR image of `X` bytes and AND mask of `A` bytes, `biSizeImage` may be zero, X, or X+A. Calculate A before checking this metadata, then check mask availability. `python.ico`, `deerstalker.cur`, and two malformed-directory CUR corpus samples use X+A. Neither an arbitrary value nor entry slack is accepted.
- **The AND plane remains structurally mandatory even when ignored for 32-bit alpha.** It is 1 bpp, MSB-first, four-byte padded and bottom-up; an absent byte fails. `hopper_mask.ico` has 64 bytes beyond a complete mask; `pillow.ico` includes too-wide AND strides. Both fail `TrailingBytes` (D5) because the selected directory slice is supposed to delimit one entry. D1's BMP suffix tolerance does not leak into ICO.
- **RLE remains intentionally strict (D6).** EOB is mandatory; EOL after the last row may precede EOB; an early EOB leaves gaps filled by palette index zero rather than the baseline's transparent black (`io-bmp.c:515–522`). A run cannot cross a row, an absolute packet must include its word-alignment byte even when nonzero, and full-packet availability precedes index lookup. Delta must land at `x<width,y<height`, even if a run has just reached `x=width`; EOL has the distinct permission to set `y=height`. The baseline `io-bmp.c:1117–1268` clips runs and tolerates some out-of-range data; strict rejection costs two corpus files.
- **Nonzero `biSizeImage` remains exact outside ICO.** BMP/BareDib require exactly the consumed padded raw raster or RLE bytes through EOB. `io-bmp.c:292–342` does not enforce equality. `badbitssize.bmp` remains `InvalidImageSize`; malformed declarations do not get repaired by ignored BMP trailing bytes.

## Measured corpus cost

A shallow sparse clone of [Pillow's `Tests/images`](https://github.com/python-pillow/Pillow) at `aa60851e1f0f00a82560a553cbad4429d9233b86` provided **84** local `.bmp/.ico/.cur` files totalling **1,365,291 bytes**, each at most 1 MiB. The repository `LICENSE` states MIT-CMU terms; individual images may have independent rights. These files are **local test material, not for redistribution**. `python3 -I tools/run_corpus.py` prints each file and the exact result. The shim uses the first DIB entry, and for `mask_1.cur`/`mask_L.cur` alone corrects an obviously wrong eight-byte directory length by measuring offset-to-EOF; those container defects must be addressed separately when specifying a real ICO/CUR parser.

Under draft 2, **58 accepted, 24 rejected by the core, 2 outside core scope** (`hopper_draw.ico` PNG-only and `no_cursors.cur` invalid directory). Core errors: `InvalidFileSize` 5, `UnsupportedPixelDepth` 4, `InvalidColorCount` 2, `InvalidDimensions` 2, `RleBounds` 2, `TrailingBytes` 2, and one each of `InvalidImageSize`, `InvalidPixelOffset`, `InvalidPlanes`, `PaletteIndexOutOfRange`, `UnsupportedCompression`, `UnsupportedHeaderSize`, `UnsupportedOrientation`. This test corpus intentionally contains malformed inputs; the rejection fraction is **not** an estimate of user-file compatibility. An independent reviewer matched the draft-two oracle on all 200 then-current vectors and the 82 decodable corpus files, pixel for pixel; the 14 draft-2b additions still need independent oracle and mutation review before freeze.
