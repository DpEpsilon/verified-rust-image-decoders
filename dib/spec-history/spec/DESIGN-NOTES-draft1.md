# Design notes — draft, not frozen

The pure core accepts `(bytes, mode)` for `BmpFile`, `BareDib`, or `IcoEntryDib`. A later ICO/CUR container must validate its directory, entry offsets and lengths, compare directory dimensions if desired, select PNG versus DIB, and call this core with exactly the selected DIB entry bytes. ANI/RIFF framing is outside scope. The local corpus runner's first-DIB selection does not specify that future behavior.

Each policy below names what changes relative to the read gdk-pixbuf BMP/ICO baselines and the compatibility risk. `RECALLED` means the producer claim has no verified primary-source support.

- Require `bfSize=|b|`, zero reserved fields and a bounded `bfOffBits`; `io-bmp.c:269–286,535–566,799–815` checks BM but does not enforce full-size equality or reserved-zero. BMPs with stale sizes or appended bytes fail (`InvalidFileSize`); in the corpus five files do. BareDib has no file header, so callers must select its mode explicitly.
- Reject all post-raster bytes, including V5 embedded/linked colour-profile data, rather than letting the baseline ignore unused bytes (`io-bmp.c:799–803`; `io-ico.c:619–623`). This costs four corpus files. Profile-aware producers are particularly exposed: two profile BMPs fail, and the strict core intentionally does no colour management. Consider a future separately bounded profile-aware wrapper rather than silently ignoring the profile.
- Allow a gap **only** in BmpFile between the table and `bfOffBits`, not in BareDib/ICO. `io-bmp.c:535–546` skips a gap; `io-ico.c:399–468` uses its computed palette boundary. This rejects noncanonical stand-alone DIBs with private alignment bytes; BMP with a correct pixel offset remains accepted.
- Accept OS/2 CORE 12, truncated OS/2 2.x 16 and full OS/2 2.x 64 plus Windows 40/52/56/108/124. `io-bmp.c:292–342` accepts 12,40,52,56,64,108,124, not 16; `io-ico.c:346–430` assumes a 40-byte INFO header. Size 16 support adds one Pillow corpus acceptance after correcting its distinct field widths; size 52/56 are observed baseline extensions, not claimed Microsoft-standard headers. Other OS/2 shortened sizes, OS/2 Huffman 1D and OS/2 RLE24 remain unsupported even if real producers emitted them (RECALLED).
- Require planes=1, dimensions at most 8192 each, 64 MiB input/output caps and exact no-panic allocation/work bounds. `io-bmp.c:464–510` uses pixbuf/allocator limits and progressive callbacks; `io-ico.c:401–429,524–534` compares its selected directory entry, which this core never sees. Two corpus files hit dimension constraints; this is resource policy, not format validity.
- Require `biClrUsed<=2^depth` for indexed images, and **zero** for 16/24/32 bpp. The baseline `io-bmp.c:353–375` rejects values above `2^depth` and treats high-depth colours as metadata; Microsoft permits an optional high-depth optimal colour table. Rejecting it costs five corpus files, including `rgb16-565pal.bmp`, `rgb24pal.bmp`, `rgb24largepal.bmp`; files with a nonzero high-depth table cannot be fixed merely by skipping palette bytes because its byte count and pixel offset must be reconciled. For indexed short palettes, reject an index outside the declared table instead of reading a zero-filled unprovided entry (`io-bmp.c:604–610,981–1067`); one corpus file hits `PaletteIndexOutOfRange`.
- Require 16/32-bit BITFIELDS RGB masks nonzero, contiguous, nonoverlapping and within pixel width, and use a zero alpha mask for opaque output. `io-bmp.c:688–711` substitutes default masks if RGB masks are absent; `:633–647` counts set bits without checking contiguity or overlap, and `:713–728` truncates channels above eight bits. Old writers with zero or discontiguous masks fail rather than receiving guessed colours. The `H=64` external mask choice follows this baseline (`:553–567`), not a verified IBM rule.
- Scale a valid contiguous component to eight bits by `floor((255*c+floor(max/2))/max)`; `io-bmp.c:874–880,956–975` instead replicates or shifts bits according to its `r_bits` arithmetic, and for raw BI_RGB 16 uses exact five-bit replication `(c<<3)|(c>>2)`. For `c=3` the latter yields 24 while the rounding rule yields 25. Colour values can differ by a few levels; acceptance does not change. The 32-bit BI_RGB fourth byte remains ignored/opaque outside ICO, as `io-bmp.c:884–892` does, even if producers stored meaningful alpha there.
- In ICO 32-bit BI_RGB, always preserve XOR A including an all-zero alpha plane and additionally force alpha zero wherever AND bit is one. `io-ico.c:637–658` preserves A but `:817–850` **skips the AND mask entirely for depth 32**. This core treats the mask as an additional transparency veto, not as a fallback or a substitute. Writers using all-zero XOR A but meaningful AND bits render fully transparent here; no hidden all-zero-alpha heuristic is applied (RECALLED common producer practice). For 1/4/8/16/24-bit ICO, AND bit one forces alpha zero as in the baseline; mask bit zero leaves alpha 255 or an explicit bitfield alpha rather than overwriting it to 255. ICO entries missing the mandatory padded AND plane fail (`TruncatedAndMask`).
- At 1 bpp in ICO, use the declared two-entry palette; `io-ico.c:790–815` instead maps a clear bit to black and a set bit to white without consulting the palette. An icon with a custom or reversed monochrome palette changes colour under this core, although the AND mask still controls transparency separately. At 4/8 bpp both decoders use the palette, but this core rejects missing entries rather than relying on unchecked access.
- Reject ICO RLE outright, even though standalone BMP RLE4/RLE8 is implemented; `io-ico.c:366–388` skips compressed entries in its selection. A future container can try a different entry; a standalone `IcoEntryDib` cannot. ICO BITFIELDS 16/32 is accepted here whereas the baseline's ICO converter uses 5:5:5 or BGRA without its BMP mask logic (`io-ico.c:637–719`): well-formed ICO with bitfields may render different channels.
- Require RLE EOB, keep skipped pixels at palette entry zero, reject runs/deltas outside visible bounds, check complete absolute packet including alignment before palette indices, and reject trailing bytes. `io-bmp.c:1117–1268` initializes skipped RLE pixels to transparent zero, clips run writes beyond width, can ignore bytes after reaching the last row, and does not apply this exact error precedence. A producer that omits EOB or pads after it, or relies on transparent gaps, loses compatibility; the corpus has two `RleBounds` rejections (including `hopper_rle8_row_overflow.bmp`). A nonzero absolute pad byte remains accepted and ignored.
- Require nonzero `biSizeImage` to equal consumed XOR bytes. Microsoft permits zero for BI_RGB; `io-bmp.c:292–342` reads the field but does not enforce exact equality. Three corpus files fail `InvalidImageSize`, including one CUR entry. RLE size counts bytes through EOB rather than bytes after EOB or the ICO AND mask; producers with stale size metadata fail even if pixels are complete.
- The core emits one non-premultiplied top-first RGBA buffer or one error, unlike progressive prepared/updated pixbuf callbacks (`io-bmp.c:499–523,1092–1101`; `io-ico.c:543–547,893–905`). No partial image is returned on truncation, and source orientation never escapes into the API. Palette fourth bytes are ignored, not treated as transparency.

## Local compatibility measurement

The [Pillow `Tests/images` corpus](https://github.com/python-pillow/Pillow) at commit `aa60851e1f0f00a82560a553cbad4429d9233b86` supplied **84** small `.bmp/.ico/.cur` files (1,365,291 bytes total; every file at most 1 MiB). A sparse shallow clone was used; 84 files were copied without history to `corpus/` for local tests only. Pillow's repository `LICENSE` carries MIT-CMU terms; individual test assets may carry further rights, so **do not redistribute** this corpus. `python3 -I tools/run_corpus.py` reports each filename and exact result. The measurement shim selects the first DIB ICO/CUR entry, does not validate directory dimensions and reports PNG-only/container-invalid inputs separately.

The strict core accepts **49**, rejects **33** with named format/policy errors, and cannot assess **2** at the core boundary (one PNG-only ICO, one invalid container). Rejections by error: `InvalidColorCount` 5, `InvalidFileSize` 5, `TrailingBytes` 4, `UnsupportedPixelDepth` 4, `InvalidImageSize` 3, `InvalidDimensions` 2, `RleBounds` 2, `TruncatedHeader` 2, and one each of `InvalidPixelOffset`, `InvalidPlanes`, `PaletteIndexOutOfRange`, `UnsupportedCompression`, `UnsupportedHeaderSize`, `UnsupportedOrientation`. **This is a decoder test corpus deliberately containing malformed fixtures, not a representative sample of user images**; the 33 rejections do not estimate population failure rates. The unverified container choices and ICO-specific conventions need independent review before any contract freeze.
