# DIB decoder core

DIB-CORE-SPEC 1.0 (frozen). `decode(bytes, mode)` is total for `mode ∈ {BmpFile, BareDib, IcoEntryDib}` and every representable caller-owned immutable byte slice. Its result is `Ok({width:u32,height:u32,rgba:bytes})` or `Err(error)`. The output is tightly packed, non-premultiplied RGBA8, left-to-right, top row first. Offsets are zero-based; byte ranges are half-open. LE16/LE32 read unsigned little-endian words; S32 reads a signed little-endian two's-complement word. All formulae use mathematical integers before checked conversion to `usize`. Invalid `mode` is impossible for the typed API, not an input-byte error. No I/O, resizing, profile conversion, gamma correction, cursor hotspot, directory selection, or PNG decoding occurs.

R1. `MAX_INPUT=67,108,864`, `MAX_OUTPUT=67,108,864`, `MAX_DIMENSION=8,192`. Test `|b|>MAX_INPUT` first and return `FileTooLarge`. For `BmpFile`, require 14 bytes (`TruncatedFileHeader`), bytes `[0:2]="BM"` (`BadMagic`), `bfSize=LE32(2)` either zero or at most `|b|`, and both reserved LE16 fields at 6 and 8 zero (`InvalidFileSize`); then require `18<=bfOffBits=LE32(10)<=|b|` (`InvalidPixelOffset`). The lower bound 18 guarantees only that the four-byte DIB size word can exist; R7 checks the actual palette/mask end. The DIB starts at `s=14`. In the other modes, it starts at `s=0` and no file header is inferred. A BMP's `bfOffBits` addresses the beginning of XOR/pixel bytes, measured from the beginning of the full BMP. The BMP decoder does not use `bfSize` as a read bound: a nonzero `bfSize<=|b|` is accepted even when it is smaller than `bfOffBits` or the end of the complete pixel array. It ignores bytes after complete pixel data; it still rejects `bfSize>|b|` and nonzero reserved words. No other metadata constraint is relaxed by this file-size exception.

R2. Require four bytes from `s` or return `TruncatedDibHeader`. Let `H=LE32(s)`; accept only `{12,16,40,52,56,64,108,124}`, else `UnsupportedHeaderSize`. Require all `H` bytes or return `TruncatedHeader`. Size 12 uses the OS/2 CORE layout: unsigned LE16 width at `s+4`, unsigned LE16 height at `s+6`, planes at `s+8`, bit depth at `s+10`, and three-byte BGR palette entries. Size 16 uses the truncated OS/2 2.x layout: signed S32 width and height at `s+4,+8`, planes LE16 at `s+12`, depth LE16 at `s+14`, and four-byte BGR-reserved palette entries; this layout is RECALLED from third-party documentation and a real corpus file, not confirmed against IBM's primary specification. Both imply compression, `biClrUsed`, and `biSizeImage` zero. Sizes 40/52/56/64/108/124 have signed S32 width and height at `s+4,+8`, planes LE16 at `s+12`, depth LE16 at `s+14`, compression LE32 at `s+16`, declared image length LE32 at `s+20`, and `biClrUsed` LE32 at `s+32`. Ignore resolution, important-colours count, V4/V5 colour-space/profile metadata, and OS/2 extension fields. Header size 64 is the OS/2 2.x extended header; sizes 52 and 56 are nonstandard mask-bearing Windows derivatives (RECALLED, not Microsoft-standard header sizes).

R3. Require planes exactly one (`InvalidPlanes`). Then require positive width, nonzero height other than `S32_MIN`, and, for `IcoEntryDib`, positive **even** stored height. ICO's visible height is `stored_height/2`; other modes use `abs(stored_height)`. The 16/64-byte OS/2 width/height fields may be unsigned in IBM's format (RECALLED); this core deliberately interprets their high bit as a negative signed value, rejecting such widths and using top-down semantics for negative heights outside ICO. CORE heights are unsigned. Both resulting dimensions must lie in `[1,MAX_DIMENSION]`, else `InvalidDimensions`. ICO top-down and odd-height entries are rejected here, without looking at an outer directory's dimensions. A negative height in BMP/BareDib means top-down.

R4. Accept bit depth in `{1,4,8,16,24,32}` or `UnsupportedPixelDepth`. Compression values are `BI_RGB=0`, `BI_RLE8=1`, `BI_RLE4=2`, `BI_BITFIELDS=3`; all other values return `UnsupportedCompression`, including JPEG/PNG and BI_ALPHABITFIELDS=6. Require `RLE8↔8 bpp`, `RLE4↔4 bpp`, and BITFIELDS only with 16/32 bpp, else `InvalidCompressionDepth`. Negative-height RLE and all ICO RLE return `UnsupportedOrientation`; CORE implies bottom-up. A negative-height BITFIELDS or RGB is permitted outside ICO.

R5. For 1/4/8 bpp, `biClrUsed` must be at most `2^depth`; zero means exactly `2^depth` entries, otherwise exactly `biClrUsed` entries (including a palette with only one entry). For 16/24/32 bpp, `biClrUsed>0` is permitted **only** in BmpFile: it declares that many optional four-byte BGR-reserved optimal-table entries to skip after the masks, without using them for pixels. In BareDib/ICO require `biClrUsed=0` or `InvalidColorCount`. Indexed `biClrUsed>2^depth` returns `InvalidColorCount` in every mode. Check `N=width*height` and `4N<=MAX_OUTPUT` or return `OutputTooLarge`; at the limit `N=16,777,216`. Perform R5 checks before reading masks, palettes or pixel bytes. Dimension cap makes `stride` at most 32,768 bytes and `4N` at most 268,435,456 before the output check; compute in checked wide arithmetic nonetheless.

R6. After the `H`-byte header at `p=s+H`, BITFIELDS with `H=40` or `H=64` reads three successive LE32 R,G,B masks from `[p:p+12)`, or `TruncatedMasks`, and advances `p` by 12. BITFIELDS with `H=52` reads three masks at offsets `s+40,+44,+48`, with alpha zero; `H∈{56,108,124}` reads a fourth at `s+52`. Ignore mask-looking fields in any header when compression is not BITFIELDS. For BITFIELDS, require R,G,B nonzero, every nonzero mask a single contiguous set-bit run wholly within the `depth` low bits, and all four masks pairwise disjoint; zero A means opaque. Violations return `InvalidBitfields`. `H=64` uses the external-three-mask rule, not its extension bytes. Interpret a component mask `m≠0` by `shift=trailing_zeros(m)`, `max=m>>shift`, `component=((word&m)>>shift)`, and `scale(component,m)=floor((255*component+floor(max/2))/max)`; absent alpha yields 255. No signed shifts or floating point.

R7. Palette begins at current `p`, has `table_count*(3 if CORE else 4)` bytes, with `table_count=biClrUsed or 2^depth` for indexed pixels, `table_count=biClrUsed` for high-depth BmpFile optimal tables, and zero otherwise; each entry is B,G,R[,reserved]. Compute `palette_length` and `p+palette_length` in `u64` (or mathematical integers in the model) before comparing against `bfOffBits` and `|b|`; in particular `4*biClrUsed` may exceed 32-bit `usize` although the input length cannot exceed 67,108,864. Convert to `usize` only after proving the computed end is within the input slice. For indexed pixels, `count=table_count`; a high-depth table is skipped, not indexed. In `BmpFile`, test `bfOffBits>=p+palette_length` **before** checking palette availability, else `InvalidPixelOffset`. If insufficient bytes for the palette return `TruncatedPalette`. Ignore the fourth palette byte, including in ICO. For BMP set pixel cursor `p=bfOffBits`; gap bytes between palette and `bfOffBits` are opaque. For BareDib/ICO set `p` immediately after palette; there is no inferred gap. Require index `<count` at each consumed pixel or return `PaletteIndexOutOfRange`. No fallback to entry zero for invalid indices.

R8. Allocate one zero-initialized `4N`-byte output only after R1–R7 checks. A decoder may delay allocation until after cheap payload-size checks if it retains the stated precedence. Palette-backed RLE begins with **every** output pixel equal to palette entry zero with alpha 255; later writes replace individual pixels. For raw 1/4/8 bpp pixels, choose the high-order bit/nibble first, indexed by `byte=floor(x*depth/8)`, `shift=8-depth-(x*depth mod 8)`; check the palette for each pixel. For 16-bit BI_RGB apply R6's exact rounded `scale` to 5:5:5 masks `(0x7c00,0x03e0,0x001f)` and use opaque alpha, ignoring bit 15. Thus a five-bit value 3 yields 25, not bit replication's 24. For 24-bit BI_RGB read B,G,R, opaque alpha. For 32-bit BI_RGB in BmpFile/BareDib read B,G,R and **ignore the fourth byte**, yielding opaque alpha. For 32-bit BI_RGB in ICO initially read B,G,R,A into the XOR pixel; R12 then applies the whole-image XOR-alpha/AND fallback, including the all-zero case. BITFIELDS uses R6 on the unsigned LE16/LE32 pixel word; no alpha mask means opaque. No premultiplication.

R9. `row_stride=4*ceil(width*depth/32)` for raw/BITFIELDS, including padding to a four-byte boundary. For row `r∈[0,height)`, require a whole stride before examining its first pixel, else `TruncatedPixels`; consume every byte of that row, but ignore unused pixel bits and pad bytes. Map source `(x,r)` to output `(x, r if stored_height<0 else height-1-r)`; CORE/ICO always take the bottom-up branch. A complete earlier row's invalid palette index precedes a later row's truncation. For ICO, these rows are the XOR bitmap and use visible height, not doubled stored height.

R10. For RLE4/RLE8 start `(x,y)=(0,0)` in **bottom-up source coordinates**, cursor `p` after palette, output prefilled per R8. Process commands until explicit `00 01` EOB. If fewer than two command bytes exist return `RleTruncated`. Nonzero count `q` followed by code byte paints `q` pixels starting at `(x,y)`; RLE8 repeats index `code`, RLE4 alternates high and low nibbles, high first. Before any index lookup require `y<height` and `x+q<=width` or `RleBounds`; then check each index in order and advance `x` by `q`. Do not wrap a run across a row. A command always consumes both bytes before bounds/index checks.

R11. On `00 00` EOL require `y<height` or `RleBounds`, then set `(x,y)=(0,y+1)`; EOL after the final row may set `y=height`, and only EOB may follow. On `00 02` delta require two more bytes `dx,dy` or `RleTruncated`, then require `x+dx<width` and `y+dy<height` or `RleBounds`; advance both coordinates. On `00 q` with `3<=q<=255`, require `y<height` and `x+q<=width` before reading absolute data, else `RleBounds`. Require `k=q` bytes for RLE8 or `k=ceil(q/2)` bytes for RLE4 plus one pad byte when `k` is odd; otherwise `RleTruncated`. The pad byte's value is ignored. Check the **whole padded packet** before inspecting its first palette index; then decode high nibble first for RLE4, check each index in order and advance `x` by `q`. An EOB may arrive early, leaving unspecified pixels as palette zero. No EOB yields `RleTruncated`; there is no implicit end at width×height.

R12. Let `X` be the exact number of consumed XOR/pixel bytes, including raw row padding or all RLE bytes through EOB. For ICO compute `A=height*4*ceil(width/32)` **before** validating `biSizeImage`; elsewhere `A=0`. If `biSizeImage≠0`, accept only `biSizeImage=X` in BmpFile/BareDib and `biSizeImage∈{X,X+A}` in ICO; otherwise `InvalidImageSize`. This check follows all XOR/pixel failures and precedes ICO AND availability. In ICO require `A` AND bytes or `TruncatedAndMask`, then interpret its bottom-up rows, bit `0x80>>(x mod 8)` in byte `floor(x/8)` at x, ignoring unused bits/pad bytes. For 32-bpp ICO pixels with an explicit XOR alpha channel (BI_RGB A byte or nonzero BITFIELDS A mask), scan the complete XOR alpha plane: if **any** XOR alpha is nonzero, retain every XOR alpha byte and ignore all AND bits; if **all** XOR alpha is zero, AND bit one yields alpha 0 and bit zero yields alpha 255. For other ICO pixels, AND bit one sets alpha zero and bit zero leaves XOR alpha unchanged; this includes 32-bit BITFIELDS without an alpha mask. This is the chosen Windows-style fallback, not a per-pixel alpha heuristic. Consume the entire mask even when ignored for alpha. BareDib and IcoEntryDib require cursor `=|b|` after the raster/mask, else `TrailingBytes`. BmpFile ignores any remaining bytes once its pixel array completes; this subsumes V5 profile spans without interpreting them or performing colour management. On every error discard partial output.

R13. The total reference model `MH(b,mode)` applies R1–R7 in order and returns either the exact first error or checked header record `(s,H,width,height,signed_height,depth,compression,count,palette_start,pixel_start,masks,N,stride,declared_image)`. It does not inspect any pixel. The total pixel model `MP(b,mode)` calls `MH`, performs R8–R12 in their exact command/row order, and returns `Ok(width,height,rgba)` or the first error; all reads have prior length checks. EOB/row processing terminates because each RLE command consumes at least two bytes or returns. The model defines bytes, not only dimensions, and no parsing helper from an eventual implementation is part of the mathematical definition.

R14. **Total operational error precedence** (not a sorting of latent defects): `FileTooLarge`; in BmpFile only `TruncatedFileHeader`, `BadMagic`, `InvalidFileSize`, `InvalidPixelOffset` for basic offset bounds; then `TruncatedDibHeader`, `UnsupportedHeaderSize`, `TruncatedHeader`, `InvalidPlanes`, `InvalidDimensions`, `UnsupportedPixelDepth`, `UnsupportedCompression`, `InvalidCompressionDepth`, `UnsupportedOrientation`, `InvalidColorCount`, `OutputTooLarge`, `TruncatedMasks`, `InvalidBitfields`, `InvalidPixelOffset` for offset before mask/palette end, `TruncatedPalette`; then the first pixel/packet error in stream order (`TruncatedPixels`, `PaletteIndexOutOfRange`, `RleTruncated`, `RleBounds`), then `InvalidImageSize`, `TruncatedAndMask` in ICO, and `TrailingBytes` in BareDib/ICO only. For ICO compute AND span before `InvalidImageSize` but do not inspect AND bytes until afterward; BmpFile has no trailing check. Within RLE a two-byte command precedes bounds; in absolute packets, bounds precede whole padded packet presence, which precedes first palette index. EOB takes precedence over unprocessed trailing bytes. No partial result or second error is exposed.

R15. The closed case-sensitive error set is exactly `FileTooLarge`, `TruncatedFileHeader`, `BadMagic`, `InvalidFileSize`, `InvalidPixelOffset`, `TruncatedDibHeader`, `UnsupportedHeaderSize`, `TruncatedHeader`, `InvalidPlanes`, `InvalidDimensions`, `UnsupportedPixelDepth`, `UnsupportedCompression`, `InvalidCompressionDepth`, `UnsupportedOrientation`, `InvalidColorCount`, `OutputTooLarge`, `TruncatedMasks`, `InvalidBitfields`, `TruncatedPalette`, `TruncatedPixels`, `PaletteIndexOutOfRange`, `RleTruncated`, `RleBounds`, `InvalidImageSize`, `TruncatedAndMask`, `TrailingBytes`. InvalidPixelOffset has two check sites but one error. `TruncatedDibHeader` and `TruncatedPalette` are unreachable specifically in BmpFile because `bfOffBits∈[18,|b|]` and the later offset check establishes the complete palette; they remain reachable in BareDib/ICO. `TrailingBytes` is unreachable in BmpFile by policy. Error ordering never compares defects in mutually exclusive branches (for example invalid compression versus a depth/compression mismatch). Allocation failure is outside this set.

R16. `VECTORS.json` is an array of `{name,mode,input_hex,expected}`, optionally `input_repeat` (positive integer, default 1), and for a repeated **suffix** both `repeat_from` (a byte offset strictly below length of decoded `input_hex`) and `input_suffix_hex` (lowercase hex). Without `repeat_from`, repeat the entire `input_hex` byte sequence. With it, form `b=input_hex[:repeat_from]+input_hex[repeat_from:]^input_repeat+input_suffix_hex`; all slicing here is byte slicing. Check expanded length symbolically against R1 before materializing a too-large fixture. An error expectation is exactly `{error:name}`; success is `{width,height,rgba_runs:[{count,hex}]}`, where runs are maximal RGBA8 pixels in top-first order, hex has exactly eight lowercase digits, and counts sum to `N`. Fixture encoding is not a format accepted by decode. All 214 fixtures are frozen.

R17. Resource/safety contract for an implementation: input, palette and masks are borrowed; after calculating/checking `4N<=MAX_OUTPUT`, perform **exactly one allocating call requesting `4N` output bytes** on the successful decoding path, and no allocating calls inside any pixel, RLE or AND loop. Header-error paths allocate nothing. Do not clone/grow the output, create input-dependent scratch collections, format diagnostic strings or recurse on input; thus the decoder's own allocation requests never exceed `4N` bytes, although allocator overhead and compiler stack layout are outside the contract. Error after the output request may discard it. Allocator exhaustion is not a byte error; assuming the requested allocation succeeds and an ordinary stack, decode cannot panic, overflow, narrow unchecked or read/write out of bounds. A source-level implementation review checks absence of recursion and input-sized stack locals; no numeric stack/allocator-resident-byte claim is made.

R18. The decoder work counter `steps` increments on **each decoder-controlled loop-body iteration**, including header-mask/palette iteration, output initialization, raw row/pixel iteration, RLE command and emitted-pixel iteration, AND row/pixel iteration and the ICO 32-bpp whole-image alpha-presence scan; library bulk fills must be modeled by the number of bytes touched, and no hidden input-dependent loop is exempt. With `N=0` if header validation fails, otherwise the validated width×visible-height, prove `steps<=16*(|b|+N)` for every input including rejected streams. Every RLE command costs at least two consumed input bytes; every painted pixel belongs to a command with at most `N` total writes on accepted row bounds, and the AND pass visits `N` pixels. No quadratic rescanning of a growing output or remaining suffix is permitted. Termination and this bound are separate obligations.
