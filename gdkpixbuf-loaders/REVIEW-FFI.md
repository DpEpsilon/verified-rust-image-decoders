# Sol review of the loader FFI glue (condensed by coordinator)

Verdict at review time: do not ship into a process whose loader-signal handlers can close or write to their own loader. Both findings have since been addressed (see the resolution lines).

1. High, callback reentrancy: `stop_load` took ownership of the context and then `emit` called `size_func`, `prepared_func` and `updated_func` while holding a reference to it. gdk-pixbuf emits those signals synchronously and only sets `priv->closed` and clears `priv->context` after `stop_load` returns, so an application's `size-prepared` handler calling `gdk_pixbuf_loader_close` re-entered `stop_load` with the same context pointer: double free; a handler writing more bytes re-entered `load_increment` and aliased `&mut` with `&`. Resolved: the context now carries a state byte (Active, Stopping, Dead) read and written through a raw pointer; no Rust reference is alive across a C callback; only the outermost `stop_load` frees, once; nested `load_increment` is refused with `GDK_PIXBUF_ERROR_FAILED`. `tests/reentrancy.c` and `tests/reentrancy.rs` run 12 cases under AddressSanitizer plus LeakSanitizer (nine of them aborted with a double free on the original code; disabling the guard makes the test fail again).

2. Medium, allocation failure: the 64 MiB input cap bounds buffered bytes, not process survival under allocation failure. Several image-controlled allocations were infallible Rust allocations (context `Box::new`, error-message `String`s, metadata vectors), and Rust aborts the host on allocation failure. Partly resolved: context allocation is fallible, error messages are `&'static CStr` passed to `g_set_error_literal`, no `format!` on rejection paths. Still infallible: the verified core's output `Vec` (up to 64 MiB), the `GdkPixbuf` object, GLib's own `g_set_error_literal` allocation, and the leaked `fill_info` vectors (96 bytes per module per process for BMP; to become static arrays). The README states the 64 MiB cap is a correctness limit, not an OOM safety net. See `../alloc-delta/` for the plan.

Checked and fine: ABI declarations match the installed gdk-pixbuf 2.42 headers (callback signatures, vtable order, format/pattern layouts, flags, stop-load transfer-full contract); `gdk_pixbuf_new` is used (not `new_from_data`, so no destroy-notify ownership trap); positive-size rowstride and last-row byte length semantics; `shim::finish` validates nonzero dimensions, checked RGBA length and opacity before the three-channel copy; no image-controlled integer overflow or alpha-guard bypass found; null callbacks checked; `fill_info`/`fill_vtable` exports resolve from a `G_MODULE_BIND_LOCAL` module, so no cross-loader symbol collision; `panic=unwind` is set and the main Rust bodies are caught, so uncaught panics in `extern "C"` abort rather than unwinding into C.
