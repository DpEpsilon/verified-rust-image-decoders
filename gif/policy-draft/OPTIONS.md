# GIF policy option catalogue (draft 0.2, not frozen)

Draft 0.2 applies the owner's decisions on `QUESTIONS.md` (changelog: `../DECISIONS.md`). This draft extends GIF-CORE-SPEC draft 0.2 (`../spec-draft/SPEC.md`, G1–G20) the way the frozen DIB and TGA policy specs extend their cores. The stable entry points `decode_still`/`decode_frames` stay Strict. Profiled entry points take one of four named profiles (`Strict`, `RecommendedBeta`, `GdkCompat-2.42.12`, `ImageCrateCompat-0.25.10`) and add `recovered: bool` to every returned frame (and to the still result). `RecommendedBeta` is the provisional recommended profile; it keeps the `Beta` suffix until the real-corpus pass of Q9 is recorded. The compatibility profiles are opt-in and versioned, never glycin's default, and not frozen before a held-out comparison on the real corpus (Q17). `Policy::default()` is Strict; the profile selector is `#[non_exhaustive]`; the 22-field record below, plus the metadata field `loop_scan` (which changes only `Info.loop_count`), is internal and constructible only under `#[cfg(test)]`. The reference model is `policy_oracle.py`; `validate.py` checks the Strict bridge, obligation R and agreement with the incumbents; `necessity.py` reverts one field at a time.

**Non-negotiable for every policy value**, including test-only records: the caps of G1's limits table (`MAX_INPUT` 64 MiB, `MAX_DIMENSION` 65,535, the wire limit, `MAX_OUTPUT` 64 MiB of canvas = 16.7 megapixels, `MAX_FRAMES` 65,536, `MAX_TOTAL_PIXELS` 2^30) with their check order, referred to by name in every theorem; G18's three reservation sites and no other input-dependent allocation; no read beyond the slice, unchecked overflow or narrowing, panic or nontermination; work `steps ≤ c·(|b| + N + P)` with `P ≤ MAX_TOTAL_PIXELS`. Clipped pixel positions are still produced by the LZW loop (they cost one step each and are counted in `P`), but are never written; disposal and restore of a clipped rectangle cost at most its area and are charged to the same frame's `w·h`. A native decoder's acceptance beyond these caps is not part of any profile. The Python oracle allocates freely; its memory behaviour is not evidence about a Rust implementation.

## The `recovered` flag

For every retained record, a returned frame's `recovered` is true **iff** at least one of these data-affecting events occurred while decoding that frame (the still result's flag is its frame's flag):

- **E1 clip:** under `frame_bounds=Clip`, the frame's rectangle is not inside the logical screen.
- **E2 index substitution:** under `index_range ∈ {Transparent, Black, GdkTable}`, a non-transparent index `≥ C` (the declared table size) was drawn by substitution.
- **E3 short frame:** under `short_frame=KeepCanvas`, `lzw_invalid=StopFrame` or `truncation=KeepPartial`, the frame ended with fewer than `w·h` indices and the rest of its rectangle kept the canvas.
- **E4 string overrun:** under `lzw_tail=StopAtRaster`, the code that completed the raster carried indices past position `w·h`, and they were discarded.

No other tolerance sets the flag: ignored trailing bytes, a missing trailer, undefined disposal treated as 1, a duplicate or wrongly sized Graphic Control, a missing End of Information code or bytes after it, extension block sizes, skipped stray bytes, a lenient minimum code size, a Graphic Control applied to the next image across Plain Text or an unknown graphic block (`gce_consumers=ImageOnly`). Strict never sets it. So `recovered=false` does not imply that Strict accepts the file.

## Option fields

Values in **bold** are Strict. Evidence: gdk-pixbuf 2.42.12 source copies in `../sources/gdk-pixbuf-2.42.12/` (cited as `io-gif.c:N`, `io-gif-animation.c:N`, `lzw.c:N`), gif 0.14.2 and image 0.25.10 from `~/.cargo/registry` (cited `gif decoder.rs:N`, `image gif.rs:N`); probe and vector names refer to `probes/results.json` (runner outputs) and `../spec-draft/VECTORS.json`; `wit:` names are the leniency harness's 75 witness files (67 distinct inputs) in `~/projects/leniency/gif/witnesses/` (see the hold-out caveat under Named profiles). **Strict** is GIF-CORE-SPEC draft 0.2, the supported GIF subset: `validate.py` finds `policy_oracle(Strict)` equal to `gif_oracle` on all 355 distinct vector, probe and witness inputs (frames, still and loop count).

**RecommendedBeta** changes only error sites. Each of its ten non-Strict fields replaces a branch on which Strict returns an error: the eight of Q1 (`FrameOutsideScreen`, `UndefinedDisposal`, `DuplicateGraphicControl`, `GraphicControlWithoutGraphic`, `InvalidApplicationExtension`/`InvalidPlainText`, `MissingEndOfInformation`/`DataAfterEndOfInformation`/`TooManyPixels`, `MissingTrailer`, `TrailingBytes`), `gce_consumers=ImageOnly` (`UnsupportedGraphicControlTarget`, Q7) and `lzw_min=Range1to11Checked` (`InvalidLzwMinCodeSize` for sizes 1 and 9–11, Q6). Each is inert on every other branch: `Clip` never fires for a frame inside the screen, `Keep` never sees disposal ≤ 3, `StopAtRaster` stops exactly where Strict's EOI check succeeds, `ImageOnly` differs only where Strict has rejected, the checked literal test cannot fire for `m ≤ 8`, and so on. Therefore obligation R holds for both meanings of Strict-accepted (SPEC G14, G15): every still Strict accepts is returned identically with `recovered=false`, and every stream Strict accepts is returned with the same info and frame records, `recovered=false` on each, ending at the Trailer; frames Strict returns before an error are also returned identically. `validate.py`: 163 Strict-accepted still inputs, 114 Strict-accepted streams and 131,270 Strict frames, 0 violations. Of the 89 probe and witness inputs whose still Strict rejects and at least one of image or the GDK loader accepts, RecommendedBeta accepts 42 (33 under the draft-0.1 field set; the 9 added are the three Graphic Control target probes and six minimum-code-size inputs). Truncations, short frames and invalid codes stay errors (Q4); out-of-range colour indices stay errors (Q5). `missing_trailer=AtEof` has no measured support (GDK rejects; image's iterator cannot show it) and is kept by design (Q1). The inputs are synthetic; the real-corpus pass that the freeze needs (Q9) is a to-do in `../PLAN.md`.

**GdkCompat-2.42.12** and **ImageCrateCompat-0.25.10** are opt-in byte-semantics proposals. Agreement on the 329 probe, vector and witness inputs (accept/reject, dimensions, frame count and SHA-256 of the composited frames): ImageCrateCompat vs image 327/329 and vs glycin 327/329; GdkCompat vs the GDK loader 327/329 and vs gdk-anim 326/329. The witnesses were added after all other fields were fixed; on that first run GdkCompat missed 1 witness and ImageCrateCompat 5. Three of the five (`wit:18`, `wit:anim-14`, `wit:anim-07`) then motivated `empty_first_subblock` and `image_data`, so the witness figures are not a clean hold-out for ImageCrateCompat; it now misses 2. These figures are unchanged by draft 0.2: both profiles already used `gce_consumers=ImageOnly`, and Strict's new `Reject` value only makes that field's reversion fail on the same inputs as before (GdkCompat 7, ImageCrateCompat 2). `necessity.py` shows that reverting any listed field to Strict breaks at least one agreeing input, except ImageCrateCompat's `gce_orphan`, `missing_trailer` and `trailing`, which the iterator comparison cannot observe (image reports the frames and then an error), and its `loop_scan`, which no runner exposes; they are kept because the gif crate's own decoder behaves so (source reading). Sufficiency and uniqueness are not shown. Neither profile is frozen before a held-out comparison on the real corpus (Q17).

## Residuals (measured, not reproduced)

- **gif crate, interlaced frames:** `wit:anim-12-field-image_flags` (7×33, interlaced, valid stream) is rejected by gif 0.14.2 with "image truncated", while the same bytes with the interlace bit cleared decode. Strict accepts it. A gif-crate defect in the row-wise fill (`converter.rs:200–211`); root cause UNVERIFIED.
- **gif crate, image data without terminator:** `wit:19-lzw-no-block-terminator` (see `image_data`).
- **GDK, minimum code size 0:** `lzw-min-0`, `wit:anim-08-field-lzw_min`.
- **GDK, loop sources:** NETSCAPE2.0 after the first image and `ANIMEXTS1.0` (`loop_source=GdkAnywhere`, Q15) are not modelled; the core reports `None`.
- **Minimum code size 1, widening rule (open):** with `m = 1` the table starts with `2^(m+1) = 4` entries, so G10.2 step 7's test `next = 2^width` never fires and the width stays 2. gdk-pixbuf behaves the same (`lzw.c:204`); weezl widens after the first added entry (`decode.rs:1097–1101`, `next_code >= max_code`). The oracle follows gdk-pixbuf. The corpus's size-1 files are 1×1 and do not distinguish the two; vector `lzw-min-code-1-1x1@RecommendedBeta` is chosen not to depend on it.
- **GDK crash:** `clip-dispose2-x-beyond` (a disposal-2 frame whose left edge lies beyond the screen, followed by another frame) kills `gdk_pixbuf_animation_new_from_file` with a signal. `io-gif-animation.c:452–456` computes `x_end = MIN(x_offset + width, anim->width)` and passes `(x_end − x_offset)·4`, which is negative, to `memset`. Triage: `GDK-GIF-CRASH-TRIAGE.md`. The verified decoder clips with checked arithmetic (Q18); regression vectors `clip-dispose2-left-edge-beyond-screen-5` and `-65535` (RecommendedBeta) require no write and a correct next frame.

## Not reproducible, explicitly excluded

- GDK's path dependence: `gdk_pixbuf_new_from_file` returns a partially decoded first frame on truncation but rejects corruption; the loader rejects both; the animation path keeps earlier frames on corruption (`frame-zero-width-second`, `no-table-second-frame`) and rejects truncation. A bytes-only profile describes per-frame semantics; which frames a caller keeps after an error is decided by the iterator consumer (G15), not by a field.
- GDK's one-byte-write loader differs from whole-buffer writes (XMP application extension rejected, `xmp-app-extension-skipped`); stale context bytes in a short Graphic Control.
- Any behaviour depending on allocator contents (GDK's uninitialised `index_buffer` at the 2.42.12 tag, `gdk_pixbuf_new` without zeroing for the revert buffer), I/O chunking or callbacks.
- Acceptance above the G1 caps (gdk-pixbuf accepts any 65,535×65,535 screen; G1 accepts every side up to 65,535 but caps the canvas at 16.7 megapixels; the gif crate's default per-frame memory limit is 50,000,000 bytes, `reader/mod.rs:125`, which rejects a 12.5-megapixel frame that G1 accepts — UNVERIFIED by measurement).
- giflib/libnsgif-only behaviours: any version string (Q12: rejected in every profile), a default colour table (Q11: rejected in every profile) when none is present (`no-table-at-all`), zero-area frames accepted as empty, libnsgif's canvas growth for out-of-screen frames and zero screens.

## Resource caps and the corpus (Q8)

The caps are G1's limits table. Per side, the cap is the GIF wire limit (65,535), so only the area cap (`4·W·H ≤ 64 MiB`, 16.7 megapixels) bounds a screen. In the real corpus 81 files have a side above 8,192, 12 of them not fuzzer-derived. 68 of the 81 are within the area cap, including 7 of the 12 non-fuzzer files (gdk-pixbuf's `max-width.gif` 65,535×1 and `max-height.gif` 1×65,535, Firefox's 32,768×100 and 100×32,768 reftests, an 18×8,888 sprite, libnsgif's two 4×13,060 LZW tests), so the 8,192 cap of draft 0.1 rejected well-formed files for no memory saving. The other 13 (8 fuzzer-derived) exceed the area cap and stay rejected as `OutputTooLarge`; the 5 non-fuzzer ones are failure, stall or size-limit tests (`size-failure.gif`, `invalid.1.gif`, `issue-101-infinite-empty-loop.gif`, `php_bug_75571.gif`, and gdk-pixbuf's `max-size.gif` at 65,535×65,535, which would need 16 GiB of canvas). (Counted from `../../leniency/corpora/gif-stats.json`; the decision text said all 81 were within the area cap.) Vectors `screen-65535x1`, `screen-1x65535-interlaced`, `screen-32768x100`, `screen-65535x256-area-cap-exact`, `screen-65535x257-output-too-large` and `frame-left-65535-width-65535` (a coordinate sum of 131,070) exercise the arithmetic at 65,535.

Extreme-case data point: a full-film GIF of 60×60 pixels with 37,239 frames, under 64 MiB, fits within every cap: 37,239 × 3,600 = 134,060,400 frame pixels is 12.5% of `MAX_TOTAL_PIXELS`, 37,239 frames is 57% of `MAX_FRAMES`, and peak working memory is `8·W·H + 20,480` = 49,280 bytes. A synthetic stream of that shape is a stress and performance test candidate (`../PLAN.md`).
