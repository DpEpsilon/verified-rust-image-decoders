# GIF core and policy: owner decisions and places the spec guessed

Each item names the decision, the options and a recommendation, and can be read on its own. Q1–Q10 block a freeze of GIF-CORE-SPEC and its policy record; Q11–Q18 can be settled later without changing RecommendedBeta. **All eighteen were decided by the owner on 2026-11-14** (each item ends with its decision; the question text is kept as asked, with the profile renamed and one factual correction in Q1; changelog in `../DECISIONS.md`). "Strict" is the core spec (`../spec-draft/SPEC.md`); "RecommendedBeta" (formerly "RecommendedBeta", renamed until its corpus pass, Q9) is the profile that may only turn Strict errors into successes and must decode every Strict-accepted image identically (obligation R). Evidence names (`probe:…`, `vec:…`, `wit:…`) refer to `OPTIONS.md` and `probes/results.json`.

## Decisions that block a freeze

**Q1. RecommendedBeta's field set.** RecommendedBeta = Strict plus eight relaxations, each replacing an error Strict returns: clip frames that cross the screen edge (`frame_bounds=Clip`), treat disposal values 4–7 as "do not dispose", let a second Graphic Control replace the first, ignore a Graphic Control with no image after it, ignore wrong block sizes in Application and Plain Text extensions, stop LZW decoding once the frame is full (ignore a missing End of Information code, bytes after it and surplus pixels), accept a missing trailer, and ignore bytes after the trailer. gdk-pixbuf and image-rs agree on seven of the eight; *correction (2026-11-14):* gdk-pixbuf's loader and animation paths reject a missing trailer (`io-gif.c:923`), so `missing_trailer=AtEof` is a design choice, not incumbent agreement. Only frame clipping and surplus pixels set `recovered`. *Recommendation: accept.* On the 86 synthetic inputs that Strict rejects and image-rs or the gdk-pixbuf loader accepts, this set accepts 33; the remainder are truncations, short frames, bad indices and other cases decided in Q4–Q6.

**Decided (2026-11-14).** Accept the eight relaxations. Two clarifications: `missing_trailer=AtEof` is a design choice (gdk-pixbuf rejects a missing trailer); stopping LZW at the raster (`lzw_tail=StopAtRaster`) never excuses broken sub-block structure, which is still read and checked in full first (vector `image-data-no-terminator@RecommendedBeta`). With Q6 and Q7, RecommendedBeta now has ten non-Strict fields; on the probe and witness inputs it accepts 42 of the 89 whose still Strict rejects and an incumbent accepts.

**Q2. API shape.** Options: (a) `decode_still(bytes)` for the first frame, plus a frame iterator whose `next()` returns a borrowed view of the whole canvas after each frame with its delay, disposal, rectangle and `recovered` flag; (b) a single call returning every composited frame as an owned buffer; (c) the iterator returning an owned copy per frame. gdk-pixbuf (`GdkPixbufAnimationIter`), image-rs (`Frames`) and glycin (`specific_frame`) all hand out one composited, screen-sized RGBA frame at a time. Option (b) multiplies memory by the frame count (a 500×500 canvas is 1 MB per frame, so 64 MiB holds 64 frames). Option (c) adds one reservation per frame to the proof. *Recommendation: (a)*, with the iterator fused after its first error; glue that needs owned frames copies them outside the verified crate.

**Decided (2026-11-14).** (a). `decode_still`, plus a frame iterator that returns a view of the whole canvas borrowed from the decoder (one canvas reused, no per-frame allocation, no `Iterator` trait: `while let Some(f) = dec.next_frame()`), fused after its first error. The constructor `try_new` parses up to the first image descriptor, because `info()` promises the loop count found before the first image; an error in that prefix is the constructor's error (SPEC G15).

**Q3. What `decode_still` validates.** Options: (a) only the bytes up to the end of the first image (image-rs's `read_image` behaviour), so a damaged second frame, a missing trailer or trailing garbage do not affect the still image; (b) the whole stream, as the gdk-pixbuf loader does (it rejects the file when any later frame is corrupt or the trailer is missing). Option (b) costs a full decode of every frame to show one. *Recommendation: (a).* A caller wanting (b) runs the iterator to its end first.

**Decided (2026-11-14).** (a). `decode_still` validates only through the end of the first image. "Strict-accepted" is defined separately for the still entry point (`decode_still` is `Ok`) and for the whole stream (`decode_frames` ends at the Trailer), and obligation R is stated for each (SPEC G14, G15; `OPTIONS.md`).

**Q4. Truncated and short frames in RecommendedBeta.** gdk-pixbuf draws whatever pixels a frame's data produced and leaves the rest of the frame showing what was beneath (often transparent); image-rs rejects the frame. Options: keep these as errors in RecommendedBeta (Strict's behaviour), or add `short_frame=KeepCanvas` and `lzw_invalid=StopFrame`, which would show partial downloads and corrupt frames with holes. *Recommendation: keep them errors*, as DIB and TGA did for truncated pixel data; GdkCompat-2.42.12 offers the partial behaviour for callers that want it. Revisit if a real corpus (Q9) shows many such files.

**Decided (2026-11-14).** Truncated and short frames and invalid LZW codes stay errors in RecommendedBeta; partial frames exist only in GdkCompat-2.42.12.

**Q5. Colour indices beyond the colour table in RecommendedBeta.** The two incumbents disagree: image-rs leaves such pixels transparent, gdk-pixbuf paints them black or with leftover colours from an earlier frame's larger table (`probe:index-oob-stale-local`). Options: Reject (Strict), Transparent, Black. *Recommendation: Reject in RecommendedBeta*; each compatibility profile keeps its library's rule. If the corpus (Q9) shows encoders that write undersized tables, prefer Transparent, which matches image-rs and browsers' usual handling (browser behaviour UNVERIFIED).

**Decided (2026-11-14).** Reject in RecommendedBeta; each compatibility profile keeps its library's rule; a transparent index beyond the table stays legal. Corpus: 9 files, all test or crash inputs. Browsers differ (source reading): Firefox masks the index and paints entries beyond the table white, WebKit paints transparent, Chromium black.

**Q6. LZW minimum code sizes 1 and 9–11.** The GIF spec implies 2–8. image-rs accepts 1–11 and gdk-pixbuf 0–11; both decode sizes 1 and 9–11 normally (`probe:lzw-min-1`, `-9`, `-10`, `-11`). Options: (a) RecommendedBeta keeps 2–8; (b) RecommendedBeta accepts 1–11 and rejects any literal code above 255 as `ColorIndexOutOfRange`; (c) accept 1–11 and reduce literals modulo 256, as both libraries do. *Recommendation: (b)*: it accepts every file the incumbents decode identically and refuses only the ones where they would silently wrap. This needs a third `lzw_min` value in the record.

**Decided (2026-11-14).** (b), from the corpus analysis `../../leniency/corpora/gif-LZWMIN-ANALYSIS.md`. Strict keeps sizes 2–8; RecommendedBeta takes the new value `lzw_min=Range1to11Checked` (sizes 1–11, a literal code above 255 is `ColorIndexOutOfRange`); compatibility profiles keep their library's rule. Evidence: 15 non-fuzzer corpus files have a size outside 2–8; 5 are decodable images (size 1 in two files sharing one 42-byte 1×1 GIF and in image-gif `set_hsts.gif`; size 10 in libnsgif `lzw-code-three-subblocks.gif`; size 11 in gdk-pixbuf `max-codes.gif` and Pillow `issue_2811.gif`), which gdk-pixbuf (both paths) and image 0.25.10/gif 0.14.2 all accept with identical first frames, while all three reject the other ten; checked and mod-256 decoders differ on 0 of 99 examined files, and all three incumbents wrap a size-9 literal above 255; widening flips exactly those five of 1,407 files from reject to accept; none of the 303 incidental assets uses such a size. Caveat: a test-suite corpus (23% fuzzer-derived) shows the sizes exist, not how common they are on the web. Obligation R is unaffected (Strict-accepted sizes are 2–8). Open detail: the widening rule for `m = 1` (`OPTIONS.md`, Residuals).

**Q7. Graphic Control scope across Plain Text and unknown blocks.** The GIF spec says a Graphic Control applies to the next graphic block, and a Plain Text Extension (or an unknown label in 0x00–0x7F) is such a block. No measured decoder follows this: all apply the Graphic Control to the next image (`vec:gce-consumed-by-plain-text`, `probe:gce-before-plaintext`). Because Strict accepts these files, RecommendedBeta cannot differ from Strict on them. Options: (a) keep the spec reading in Strict (then Strict and RecommendedBeta disagree with every library on such files); (b) change Strict before freezing so that only an image consumes a Graphic Control, recording the deviation from §23. Plain Text is not rendered under either option: its font is left to the decoder by the spec, so its pixels cannot be specified. *Recommendation: (b)*, because Plain Text is never rendered and the spec reading therefore changes only which image gets the transparency, against every implementation.

**Decided (2026-11-14).** (c), a third option: Strict rejects a stream in which a pending Graphic Control meets a Plain Text Extension or an unknown label 0x00–0x7F before the next image descriptor, with the new closed error `UnsupportedGraphicControlTarget` (an unsupported construct, not a malformed file; Strict is documented as the supported GIF subset, not complete GIF89a). Unknown extensions without a pending Graphic Control stay skippable. RecommendedBeta and the compatibility profiles accept such files and apply the Graphic Control to the next image without setting `recovered` (`gce_consumers = Reject | ImageOnly`). Obligation R is vacuous for these files. No Pedantic or NearStrict profile. Alternatives (a) and (b) are recorded in `../spec-draft/DESIGN-NOTES.md` N16.

**Q8. Resource caps.** Proposed: input at most 64 MiB; screen at most 8,192 pixels per side and 64 MiB of RGBA (16.7 megapixels); at most 65,536 frames; at most 2^30 decoded frame pixels in total (about one billion, a few seconds of work). For scale: a 480×270 animation could have 8,285 full-size frames before the pixel budget stops it, and a 1920×1080 one 517. gdk-pixbuf has no frame or total cap; image-rs limits each frame to 50,000,000 bytes (12.5 megapixels) by default. *Recommendation: accept these numbers*; raise the pixel budget only with a measured corpus need.

**Decided (2026-11-14).** Per-side cap raised to the GIF wire limit (65,535: no separate per-side cap); keep the area cap (`4·W·H ≤ 64 MiB`, 16.7 megapixels), input 64 MiB, 65,536 frames and 2^30 total frame pixels. All caps are named constants in one limits table (SPEC G1) and theorems are stated over the names; coordinate arithmetic is specified at 65,535; clipped pixels and disposal/restore work count against the work bound. Corpus: 81 files have a side above 8,192 (12 not fuzzer-derived); 68 are within the area cap (7 of the 12 non-fuzzer files), and 13 are not (5 non-fuzzer: failure, stall and size-limit tests, including the 65,535×65,535 `max-size.gif`) (the decision text said all 81; see `OPTIONS.md`). Extreme case: a 60×60 full-film GIF with 37,239 frames fits every cap (12.5% of the pixel budget, 57% of the frame cap, about 49 KB of working memory).

**Q9. Real-world corpus before freeze.** All measurements so far use 329 synthetic inputs: 181 distinct spec-vector inputs, 81 targeted probes and 67 distinct witnesses (75 files) from the earlier leniency run. TGA's RecommendedBeta was justified on 300 real files. *Recommendation: block the freeze of RecommendedBeta (not of Strict) on a pass over a pinned real GIF corpus*, recording which Strict errors real files hit (missing End of Information codes, out-of-range indices and frames crossing the screen edge are the likely ones).

**Decided (2026-11-14).** Keep the rule: freezing RecommendedBeta needs a real-corpus pass. The pinned 1,407-file corpus (`../../leniency/corpora/manifests/gif.MANIFEST.tsv`) can satisfy it once RecommendedBeta's end-to-end outcomes on it are recorded per field; that is a to-do in `../PLAN.md`, not done.

**Q10. One crate or two for the animation compositor.** Options: (a) one crate holding the LZW decoder, block parser, compositor and policy layer, proved in stages; (b) a parser+LZW crate that returns index frames and a separate compositor crate. The compositor is small (disposal, restore, clipping, transparency), shares the canvas with the drawing loop (indices are written straight to the canvas, so no index buffer is allocated), and the policy fields cut across both halves (`frame_bounds`, `index_range`, `short_frame`). A split would add an index buffer of up to 16.7 megapixels per frame and a cross-crate allocation log as ICO needed. *Recommendation: (a)*, with the compositor in its own module and model, proved after the LZW and parser milestones (`../PLAN.md`).

**Decided (2026-11-14).** (a). One crate; parser, LZW, compositor and policy layer are separate modules with separate models proved in stages. A streaming callback interface could allow a split later.

## Decisions that can wait

**Q11. No colour table at all.** gdk-pixbuf and image-rs reject; giflib and libnsgif substitute a default table. *Recommendation: reject in every profile.*

**Decided (2026-11-14).** Reject in every profile.

**Q12. Unknown version strings (`GIF88a`, `GIF89b`).** §17 suggests decoders try anyway; gdk-pixbuf and image-rs reject, giflib and libnsgif accept. *Recommendation: reject in every profile.*

**Decided (2026-11-14).** Accept only GIF87a and GIF89a in every profile (89a blocks allowed under an 87a header); the value `version=Any` is removed.

**Q13. Disposal values 4–7 in Strict.** The spec says "to be defined"; every measured decoder treats them as "do not dispose". Options: Strict rejects (current draft) and RecommendedBeta keeps; or Strict itself treats them as 1. *Recommendation: keep the draft*, consistent with DIB's handling of undefined fields.

**Decided (2026-11-14).** Strict rejects disposal 4–7 (`UndefinedDisposal`); RecommendedBeta treats them as 1 (do not dispose), reports the raw value and does not set `recovered`.

**Q14. Metadata exposure.** image-rs exposes XMP and ICC application extensions; gdk-pixbuf exposes neither; nobody exposes comments. Exposing them needs new allocation sites and a model of the XMP sub-block stitching. *Recommendation: expose nothing in 0.1*; add a separately verified metadata call if glycin needs the ICC profile.

**Decided (2026-11-14).** Expose no extension payloads (XMP, ICC, comments) in 0.1; the output is documented as untransformed RGBA (SPEC G13).

**Q15. Loop count.** The draft reports the raw NETSCAPE2.0 value found before the first image (image-rs's rule). gdk-pixbuf also reads it after images, accepts ANIMEXTS1.0 and adds one to nonzero values. *Recommendation: report the raw value only; let each glue layer translate it.* (UNVERIFIED by measurement: no runner exposes the loop count.)

**Decided (2026-11-14).** Keep `loop_count: Option<u16>` raw, found before the first image descriptor, as the normative field, and add the documented pure function `plays(loop_count) -> Plays` with `Plays = Once | Forever | Repeats(u16)` and `total_plays(Repeats(n)) = n + 1` in `u32` (`None` → Once, `Some(0)` → Forever, `Some(n>0)` → `Repeats(n)`), the browser convention (7 of 12 implementations, `LOOP-COUNT-EXPLAINER.md`); checked exhaustively over all 65,537 inputs (`check_plays.py`), vectors `plays-*`. Strict's sub-block rule is A: every sub-block of the NETSCAPE2.0 extension is scanned and the last 3-byte id-1 sub-block wins. ImageCrateCompat opts into `loop_scan=FirstSubBlockOnly` (gif crate, Pillow, libnsgif, Wuffs). gdk-pixbuf's other loop sources stay in GdkCompat's `loop_source` field as residuals; Strict and RecommendedBeta report `None` for them.

**Q16. Delay mapping.** gdk-pixbuf turns 0 into 100 ms and anything below 20 ms into 20 ms; glycin turns 0 into 100 ms and keeps 10 ms; image-rs reports raw values. *Recommendation: the core reports raw hundredths; each glue layer applies its library's mapping (`delay_map` in OPTIONS.md).*

**Decided (2026-11-14).** Raw hundredths in the core; each glue layer applies its mapping.

**Q17. Compatibility profiles.** GdkCompat-2.42.12 and ImageCrateCompat-0.25.10 each match their library on 326–327 of 329 measured inputs, including behaviours the spec forbids (gdk-pixbuf's Graphic Control persisting across frames, partial frames, leftover table colours; image-rs's rejection of unknown extensions). *Recommendation: freeze them only as opt-in, versioned names, never as glycin's default; ship Strict and RecommendedBeta first if proof effort is short.*

**Decided (2026-11-14).** Compatibility profiles are opt-in and versioned, never glycin's default, and not frozen before a held-out comparison on the real corpus.

**Q18. The gdk-pixbuf crash.** `probe:clip-dispose2-x-beyond` crashes `gdk_pixbuf_animation_new_from_file` in 2.42.12: a negative length reaches `memset` when a disposal-2 frame starts right of the screen. *Recommendation: route through the coordinator for a disclosure decision; the verified decoder is unaffected (it clips with checked arithmetic).*

**Decided (2026-11-14).** The verified decoder clips with checked arithmetic; regression vectors `clip-dispose2-left-edge-beyond-screen-5` and `-65535` (RecommendedBeta; the incumbent is not named) require that a disposal-2 frame whose left edge lies entirely beyond the screen writes nothing and that the next frame decodes.

## Places the spec had to guess

- **Version 87a with 89a blocks**: applied as in 89a (N3); every library agrees.
- **Unknown labels 0x00–0x7F consume a Graphic Control**: from §12's label ranges; no library to confirm. Superseded by Q7: Strict now rejects a pending Graphic Control at such a label (`UnsupportedGraphicControlTarget`).
- **`GdkFirstBlock` missing bytes read as 0**: gdk-pixbuf reads stale buffer bytes; the surrogate matches the measured probes only because that buffer was zero.
- **`image_data=Streaming` emission rule**: fitted to four gif-crate observations; misses one witness.
- **`lzw_min=Range0to11` for size 0**: gdk-pixbuf's output for size 0 is not reproduced.
- **Error names on new paths**: compatibility profiles reuse core names (for example `UnknownBlock` for image-rs's unknown-extension rejection). Native error strings are never compared.
- **Installed gdk-pixbuf is patched**: its invalid-code behaviour equals upstream's post-2.42.12 fix, not the tag's source; inferred from one probe, Debian patch list not obtained.
