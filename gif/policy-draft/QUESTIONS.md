# GIF core and policy: owner decisions and places the spec guessed

Each item names the decision, the options and a recommendation, and can be read on its own. Q1–Q10 block a freeze of GIF-CORE-SPEC 0.1 and its policy record; Q11–Q18 can be settled later without changing Recommended. Nothing here is decided. "Strict" is the core spec (`../spec-draft/SPEC.md`); "Recommended" is the profile that may only turn Strict errors into successes and must decode every Strict-accepted image identically (obligation R). Evidence names (`probe:…`, `vec:…`, `wit:…`) refer to `OPTIONS.md` and `probes/results.json`.

## Decisions that block a freeze

**Q1. Recommended's field set.** Recommended = Strict plus eight relaxations, each replacing an error Strict returns: clip frames that cross the screen edge (`frame_bounds=Clip`), treat disposal values 4–7 as "do not dispose", let a second Graphic Control replace the first, ignore a Graphic Control with no image after it, ignore wrong block sizes in Application and Plain Text extensions, stop LZW decoding once the frame is full (ignore a missing End of Information code, bytes after it and surplus pixels), accept a missing trailer, and ignore bytes after the trailer. gdk-pixbuf and image-rs agree on all eight. Only frame clipping and surplus pixels set `recovered`. *Recommendation: accept.* On the 86 synthetic inputs that Strict rejects and image-rs or the gdk-pixbuf loader accepts, this set accepts 33; the remainder are truncations, short frames, bad indices and other cases decided in Q4–Q6.

**Q2. API shape.** Options: (a) `decode_still(bytes)` for the first frame, plus a frame iterator whose `next()` returns a borrowed view of the whole canvas after each frame with its delay, disposal, rectangle and `recovered` flag; (b) a single call returning every composited frame as an owned buffer; (c) the iterator returning an owned copy per frame. gdk-pixbuf (`GdkPixbufAnimationIter`), image-rs (`Frames`) and glycin (`specific_frame`) all hand out one composited, screen-sized RGBA frame at a time. Option (b) multiplies memory by the frame count (a 500×500 canvas is 1 MB per frame, so 64 MiB holds 64 frames). Option (c) adds one reservation per frame to the proof. *Recommendation: (a)*, with the iterator fused after its first error; glue that needs owned frames copies them outside the verified crate.

**Q3. What `decode_still` validates.** Options: (a) only the bytes up to the end of the first image (image-rs's `read_image` behaviour), so a damaged second frame, a missing trailer or trailing garbage do not affect the still image; (b) the whole stream, as the gdk-pixbuf loader does (it rejects the file when any later frame is corrupt or the trailer is missing). Option (b) costs a full decode of every frame to show one. *Recommendation: (a).* A caller wanting (b) runs the iterator to its end first.

**Q4. Truncated and short frames in Recommended.** gdk-pixbuf draws whatever pixels a frame's data produced and leaves the rest of the frame showing what was beneath (often transparent); image-rs rejects the frame. Options: keep these as errors in Recommended (Strict's behaviour), or add `short_frame=KeepCanvas` and `lzw_invalid=StopFrame`, which would show partial downloads and corrupt frames with holes. *Recommendation: keep them errors*, as DIB and TGA did for truncated pixel data; GdkCompat-2.42.12 offers the partial behaviour for callers that want it. Revisit if a real corpus (Q9) shows many such files.

**Q5. Colour indices beyond the colour table in Recommended.** The two incumbents disagree: image-rs leaves such pixels transparent, gdk-pixbuf paints them black or with leftover colours from an earlier frame's larger table (`probe:index-oob-stale-local`). Options: Reject (Strict), Transparent, Black. *Recommendation: Reject in Recommended*; each compatibility profile keeps its library's rule. If the corpus (Q9) shows encoders that write undersized tables, prefer Transparent, which matches image-rs and browsers' usual handling (browser behaviour UNVERIFIED).

**Q6. LZW minimum code sizes 1 and 9–11.** The GIF spec implies 2–8. image-rs accepts 1–11 and gdk-pixbuf 0–11; both decode sizes 1 and 9–11 normally (`probe:lzw-min-1`, `-9`, `-10`, `-11`). Options: (a) Recommended keeps 2–8; (b) Recommended accepts 1–11 and rejects any literal code above 255 as `ColorIndexOutOfRange`; (c) accept 1–11 and reduce literals modulo 256, as both libraries do. *Recommendation: (b)*: it accepts every file the incumbents decode identically and refuses only the ones where they would silently wrap. This needs a third `lzw_min` value in the record.

**Q7. Graphic Control scope across Plain Text and unknown blocks.** The GIF spec says a Graphic Control applies to the next graphic block, and a Plain Text Extension (or an unknown label in 0x00–0x7F) is such a block. No measured decoder follows this: all apply the Graphic Control to the next image (`vec:gce-consumed-by-plain-text`, `probe:gce-before-plaintext`). Because Strict accepts these files, Recommended cannot differ from Strict on them. Options: (a) keep the spec reading in Strict (then Strict and Recommended disagree with every library on such files); (b) change Strict before freezing so that only an image consumes a Graphic Control, recording the deviation from §23. Plain Text is not rendered under either option: its font is left to the decoder by the spec, so its pixels cannot be specified. *Recommendation: (b)*, because Plain Text is never rendered and the spec reading therefore changes only which image gets the transparency, against every implementation.

**Q8. Resource caps.** Proposed: input at most 64 MiB; screen at most 8,192 pixels per side and 64 MiB of RGBA (16.7 megapixels); at most 65,536 frames; at most 2^30 decoded frame pixels in total (about one billion, a few seconds of work). For scale: a 480×270 animation could have 8,285 full-size frames before the pixel budget stops it, and a 1920×1080 one 517. gdk-pixbuf has no frame or total cap; image-rs limits each frame to 50,000,000 bytes (12.5 megapixels) by default. *Recommendation: accept these numbers*; raise the pixel budget only with a measured corpus need.

**Q9. Real-world corpus before freeze.** All measurements so far use 329 synthetic inputs: 181 distinct spec-vector inputs, 81 targeted probes and 67 distinct witnesses (75 files) from the earlier leniency run. TGA's Recommended was justified on 300 real files. *Recommendation: block the freeze of Recommended (not of Strict) on a pass over a pinned real GIF corpus*, recording which Strict errors real files hit (missing End of Information codes, out-of-range indices and frames crossing the screen edge are the likely ones).

**Q10. One crate or two for the animation compositor.** Options: (a) one crate holding the LZW decoder, block parser, compositor and policy layer, proved in stages; (b) a parser+LZW crate that returns index frames and a separate compositor crate. The compositor is small (disposal, restore, clipping, transparency), shares the canvas with the drawing loop (indices are written straight to the canvas, so no index buffer is allocated), and the policy fields cut across both halves (`frame_bounds`, `index_range`, `short_frame`). A split would add an index buffer of up to 16.7 megapixels per frame and a cross-crate allocation log as ICO needed. *Recommendation: (a)*, with the compositor in its own module and model, proved after the LZW and parser milestones (`../PLAN.md`).

## Decisions that can wait

**Q11. No colour table at all.** gdk-pixbuf and image-rs reject; giflib and libnsgif substitute a default table. *Recommendation: reject in every profile.*

**Q12. Unknown version strings (`GIF88a`, `GIF89b`).** §17 suggests decoders try anyway; gdk-pixbuf and image-rs reject, giflib and libnsgif accept. *Recommendation: reject in every profile.*

**Q13. Disposal values 4–7 in Strict.** The spec says "to be defined"; every measured decoder treats them as "do not dispose". Options: Strict rejects (current draft) and Recommended keeps; or Strict itself treats them as 1. *Recommendation: keep the draft*, consistent with DIB's handling of undefined fields.

**Q14. Metadata exposure.** image-rs exposes XMP and ICC application extensions; gdk-pixbuf exposes neither; nobody exposes comments. Exposing them needs new allocation sites and a model of the XMP sub-block stitching. *Recommendation: expose nothing in 0.1*; add a separately verified metadata call if glycin needs the ICC profile.

**Q15. Loop count.** The draft reports the raw NETSCAPE2.0 value found before the first image (image-rs's rule). gdk-pixbuf also reads it after images, accepts ANIMEXTS1.0 and adds one to nonzero values. *Recommendation: report the raw value only; let each glue layer translate it.* (UNVERIFIED by measurement: no runner exposes the loop count.)

**Q16. Delay mapping.** gdk-pixbuf turns 0 into 100 ms and anything below 20 ms into 20 ms; glycin turns 0 into 100 ms and keeps 10 ms; image-rs reports raw values. *Recommendation: the core reports raw hundredths; each glue layer applies its library's mapping (`delay_map` in OPTIONS.md).*

**Q17. Compatibility profiles.** GdkCompat-2.42.12 and ImageCrateCompat-0.25.10 each match their library on 326–327 of 329 measured inputs, including behaviours the spec forbids (gdk-pixbuf's Graphic Control persisting across frames, partial frames, leftover table colours; image-rs's rejection of unknown extensions). *Recommendation: freeze them only as opt-in, versioned names, never as glycin's default; ship Strict and Recommended first if proof effort is short.*

**Q18. The gdk-pixbuf crash.** `probe:clip-dispose2-x-beyond` crashes `gdk_pixbuf_animation_new_from_file` in 2.42.12: a negative length reaches `memset` when a disposal-2 frame starts right of the screen. *Recommendation: route through the coordinator for a disclosure decision; the verified decoder is unaffected (it clips with checked arithmetic).*

## Places the spec had to guess

- **Version 87a with 89a blocks**: applied as in 89a (N3); every library agrees.
- **Unknown labels 0x00–0x7F consume a Graphic Control**: from §12's label ranges; no library to confirm (Q7).
- **`GdkFirstBlock` missing bytes read as 0**: gdk-pixbuf reads stale buffer bytes; the surrogate matches the measured probes only because that buffer was zero.
- **`image_data=Streaming` emission rule**: fitted to four gif-crate observations; misses one witness.
- **`lzw_min=Range0to11` for size 0**: gdk-pixbuf's output for size 0 is not reproduced.
- **Error names on new paths**: compatibility profiles reuse core names (for example `UnknownBlock` for image-rs's unknown-extension rejection). Native error strings are never compared.
- **Installed gdk-pixbuf is patched**: its invalid-code behaviour equals upstream's post-2.42.12 fix, not the tag's source; inferred from one probe, Debian patch list not obtained.
