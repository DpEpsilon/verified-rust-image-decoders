# Design notes for GIF-CORE-SPEC draft 0.2

Each note records a place where the strict core chose one reading of GIF89a, and what the incumbents do. "Measured" means the probe harness (`../policy-draft/probes/`) ran gdk-pixbuf 2.42.12 (Debian `2.42.12+dfsg-4+deb13u1`), image 0.25.10 with gif 0.14.2, glycin's in-tree image-rs loader, giflib 5.1.4 and libnsgif c26c7aa on the input named.

- **N1. Ignored fields.** Colour resolution, both sort flags, the reserved bits of the Image Descriptor and of the Graphic Control packed byte, and the pixel aspect ratio change no pixel. §7 tells *encoders* to zero reserved bits and states no decoder obligation, so the core neither checks nor uses them. All measured decoders ignore them (`gce-reserved-bits-ignored`, `flags-ignored-colour-resolution-sort-aspect-bg`, probe `reserved-bits`).
- **N2. Background colour.** §18.c.vii says the background colour fills screen pixels no image covers, and disposal 2 restores "to background color". gdk-pixbuf (`io-gif-animation.c` memsets the canvas and the disposed rectangle to 0), image-rs (`gif.rs`: "intentionally ignore the background color for web compatibility") and glycin all use transparent black for both; so do browsers. The core follows them: canvas and disposal 2 are `(0,0,0,0)`, and `background_index` is exposed raw. Measured: probe `background-index-5`, vector `anim-dispose-background-then-inset`. A background-filling option exists in no incumbent profile and is not catalogued.
- **N3. Version does not gate blocks.** A GIF87a stream with a Graphic Control Extension is decoded as if it were 89a (§17.d.ii asks decoders to process what they can). All measured decoders apply the extension (probe `gce-87a`).
- **N4. Plain Text is parsed, not rendered.** §25 leaves font and size to the decoder, so the pixels are not specifiable; no measured decoder renders it. Without a pending Graphic Control it is skipped; with one, Strict returns `UnsupportedGraphicControlTarget` (G7, N16).
- **N5. Unknown labels in 0x00–0x7F.** §12 defines this range as graphic-rendering labels "so that decoders can handle block scope … even when the block itself cannot be processed". Without a pending Graphic Control such a block is skipped (`unknown-graphic-label-without-gce-skipped`); with one, its scope question arises and Strict returns `UnsupportedGraphicControlTarget` (N16). gdk-pixbuf, giflib and libnsgif skip the block and apply the Graphic Control to the next image, as RecommendedBeta does; image-rs rejects any unknown label (`gce-consumed-by-unknown-graphic-label`, probe `unknown-ext-graphic-label`).
- **N6. Local table size.** §20.c.ix says "raise 2 to the value of the field"; §21.a and §19 give `3×2^(size+1)` bytes. Every decoder uses `2^(size+1)` entries for both tables, as does this core.
- **N7. Image data is read structurally before it is decoded.** G9 reads all sub-blocks first, so `TruncatedImageData` precedes an LZW or colour error in the same image (`truncation-before-lzw-error`). This keeps the model a pure function of the concatenated payload. image-rs decodes while reading; the difference is visible only through which error is reported, except that the gif crate can complete a frame before a structural error (option `image_data=Streaming` in `../policy-draft/OPTIONS.md`).
- **N8. No leading Clear.** Appendix F says encoders *should* emit Clear first; a decoder starting in the post-Clear state loses nothing. Accepted (`lzw-no-leading-clear`); all measured decoders except stb_image agree (leniency matrix).
- **N9. Full table.** When the table holds 4096 entries the core keeps decoding 12-bit codes without adding entries until a Clear ("deferred clear"). This is how giflib, gdk-pixbuf (`lzw.c:197`, `code_table_size < MAX_CODES`) and weezl behave (`lzw-table-full-deferred-clear` accepted by all).
- **N10. A zero size byte always terminates.** §15–§16: the empty sub-block is the terminator. The gif crate instead treats a zero-length *first* image-data sub-block as empty and keeps reading (`gif/src/reader/decoder.rs` `LzwInit` → `DecodeSubBlock(0)`; witness `18-lzw-first-subblock-zero`); option `empty_first_subblock`.
- **N11. Loop count.** Only a `NETSCAPE2.0` loop sub-block before the first image descriptor sets `loop_count` (the gif crate reads application extensions only while reading the header, `reader/mod.rs` `init`). Every data sub-block of the extension is scanned and the last 3-byte sub-block with id 1 wins (rule A, Q15), as gdk-pixbuf does; the gif crate, Pillow, libnsgif and Wuffs examine only the first sub-block after the identifier, so a buffering sub-block placed first hides the count (`netscape-buffering-subblock-ignored`; `loop_scan=FirstSubBlockOnly` in ImageCrateCompat). gdk-pixbuf reads it anywhere and also accepts `ANIMEXTS1.0` (`io-gif.c:317–331`), and stores `n+1` for nonzero `n`; those sources stay in GdkCompat's `loop_source` field. The raw value stays normative; `plays` (G20) documents its meaning in the browser convention (`../policy-draft/LOOP-COUNT-EXPLAINER.md`). Pixels are unaffected.
- **N12. Transparent index outside the table.** Accepted: transparent pixels are never looked up, so the index needs no colour (§23.c.viii says nothing about its range). `index-out-of-range-but-transparent`.
- **N13. End of Information is required.** §22/Appendix F: EOI "must be the last code output by the encoder for an image". The core requires it directly after the last pixel (Clear codes may intervene) and rejects whole bytes after it. Every measured decoder stops at the full raster and ignores the rest (option `lzw_tail`); zero padding bits that form a complete code are a `MissingEndOfInformation`, not extra pixels (`lzw-missing-eoi-short-padding`).
- **N14. Frame rectangles must lie inside the screen.** §20.a. Every measured decoder accepts and clips, libnsgif grows the canvas; RecommendedBeta clips (option `frame_bounds`). Clipping uses checked arithmetic on the unnarrowed sums (up to 131,070): a disposal-2 frame whose left edge lies at or beyond the screen's right edge writes nothing and the next frame decodes (Q18; vectors `clip-dispose2-left-edge-beyond-screen-5` and `-65535`).
- **N15. `decode_still` reads a prefix.** It stops after the first image (G14), as image-rs's `read_image` does (Q3, decided). gdk-pixbuf's loader rejects a file whose later frames are corrupt or whose trailer is missing (`stop_load` requires `GIF_DONE`, `io-gif.c:923`). "Strict-accepted" is therefore defined separately for the still entry point and for the whole stream (G14, G15), and obligation R is stated for each.
- **N16. A Graphic Control aimed at Plain Text or an unknown graphic block is unsupported (Q7, decided).** §23.d applies a Graphic Control to the next graphic-rendering block, which may be a Plain Text Extension or an unknown label 0x00–0x7F. No measured decoder follows that: gdk-pixbuf, image-rs, giflib and libnsgif all apply it to the next image (`probe:gce-before-plaintext`, `probe:unknown-ext-graphic-label`). In the real corpus, 45 files have a Graphic Control before Plain Text and all 45 are fuzzer-derived (`../../leniency/corpora/gif-STATS-interpretation.md`). Decision: Strict returns `UnsupportedGraphicControlTarget` at the label of the first such block, and documents itself as the supported GIF subset, not complete GIF89a; RecommendedBeta and the compatibility profiles accept the file and apply the Graphic Control to the next image without setting `recovered` (`gce_consumers=ImageOnly`). Obligation R is vacuous on these files because Strict rejects them. Unknown extensions without a pending Graphic Control remain skippable. Alternatives considered: (a) keep the spec reading in Strict, letting the Plain Text block consume the Graphic Control; Strict and every profile bound by obligation R would then disagree with every library on these files, for a block whose pixels the core never draws. (b) Strict accepts and applies the Graphic Control to the next image as a fallback; this silently departs from §23.d inside the profile that claims to be the specification, and would make the deviation invisible to a caller. Refusing the construct keeps Strict truthful to the text it does implement and leaves the lenient reading to the profiles. No Pedantic or NearStrict profile is added.
