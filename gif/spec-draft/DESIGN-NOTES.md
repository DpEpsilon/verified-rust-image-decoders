# Design notes for GIF-CORE-SPEC draft 0.1

Each note records a place where the strict core chose one reading of GIF89a, and what the incumbents do. "Measured" means the probe harness (`../policy-draft/probes/`) ran gdk-pixbuf 2.42.12 (Debian `2.42.12+dfsg-4+deb13u1`), image 0.25.10 with gif 0.14.2, glycin's in-tree image-rs loader, giflib 5.1.4 and libnsgif c26c7aa on the input named.

- **N1. Ignored fields.** Colour resolution, both sort flags, the reserved bits of the Image Descriptor and of the Graphic Control packed byte, and the pixel aspect ratio change no pixel. §7 tells *encoders* to zero reserved bits and states no decoder obligation, so the core neither checks nor uses them. All measured decoders ignore them (`gce-reserved-bits-ignored`, `flags-ignored-colour-resolution-sort-aspect-bg`, probe `reserved-bits`).
- **N2. Background colour.** §18.c.vii says the background colour fills screen pixels no image covers, and disposal 2 restores "to background color". gdk-pixbuf (`io-gif-animation.c` memsets the canvas and the disposed rectangle to 0), image-rs (`gif.rs`: "intentionally ignore the background color for web compatibility") and glycin all use transparent black for both; so do browsers. The core follows them: canvas and disposal 2 are `(0,0,0,0)`, and `background_index` is exposed raw. Measured: probe `background-index-5`, vector `anim-dispose-background-then-inset`. A background-filling option exists in no incumbent profile and is not catalogued.
- **N3. Version does not gate blocks.** A GIF87a stream with a Graphic Control Extension is decoded as if it were 89a (§17.d.ii asks decoders to process what they can). All measured decoders apply the extension (probe `gce-87a`).
- **N4. Plain Text is parsed, not rendered.** §25 leaves font and size to the decoder, so the pixels are not specifiable; no measured decoder renders it. The block still delimits a Graphic Control's scope (G7), which no measured decoder does (`gce-consumed-by-plain-text`; QUESTIONS Q7).
- **N5. Unknown labels in 0x00–0x7F.** §12 defines this range as graphic-rendering labels "so that decoders can handle block scope … even when the block itself cannot be processed". The core therefore lets such a block consume a pending Graphic Control. gdk-pixbuf, giflib and libnsgif skip the block and apply the Graphic Control to the next image; image-rs rejects any unknown label (`gce-consumed-by-unknown-graphic-label`, probe `unknown-ext-graphic-label`). No incumbent supports the spec's reading; it is kept in Strict because obligation R forbids Recommended from changing a Strict-accepted image (Q7).
- **N6. Local table size.** §20.c.ix says "raise 2 to the value of the field"; §21.a and §19 give `3×2^(size+1)` bytes. Every decoder uses `2^(size+1)` entries for both tables, as does this core.
- **N7. Image data is read structurally before it is decoded.** G9 reads all sub-blocks first, so `TruncatedImageData` precedes an LZW or colour error in the same image (`truncation-before-lzw-error`). This keeps the model a pure function of the concatenated payload. image-rs decodes while reading; the difference is visible only through which error is reported, except that the gif crate can complete a frame before a structural error (option `image_data=Streaming` in `../policy-draft/OPTIONS.md`).
- **N8. No leading Clear.** Appendix F says encoders *should* emit Clear first; a decoder starting in the post-Clear state loses nothing. Accepted (`lzw-no-leading-clear`); all measured decoders except stb_image agree (leniency matrix).
- **N9. Full table.** When the table holds 4096 entries the core keeps decoding 12-bit codes without adding entries until a Clear ("deferred clear"). This is how giflib, gdk-pixbuf (`lzw.c:197`, `code_table_size < MAX_CODES`) and weezl behave (`lzw-table-full-deferred-clear` accepted by all).
- **N10. A zero size byte always terminates.** §15–§16: the empty sub-block is the terminator. The gif crate instead treats a zero-length *first* image-data sub-block as empty and keeps reading (`gif/src/reader/decoder.rs` `LzwInit` → `DecodeSubBlock(0)`; witness `18-lzw-first-subblock-zero`); option `empty_first_subblock`.
- **N11. Loop count.** Only a `NETSCAPE2.0` loop sub-block before the first image descriptor sets `loop_count` (the gif crate reads application extensions only while reading the header, `reader/mod.rs` `init`). gdk-pixbuf reads it anywhere and also accepts `ANIMEXTS1.0` (`io-gif.c:317–331`), and stores `n+1` for nonzero `n`. Pixels are unaffected; QUESTIONS Q15.
- **N12. Transparent index outside the table.** Accepted: transparent pixels are never looked up, so the index needs no colour (§23.c.viii says nothing about its range). `index-out-of-range-but-transparent`.
- **N13. End of Information is required.** §22/Appendix F: EOI "must be the last code output by the encoder for an image". The core requires it directly after the last pixel (Clear codes may intervene) and rejects whole bytes after it. Every measured decoder stops at the full raster and ignores the rest (option `lzw_tail`); zero padding bits that form a complete code are a `MissingEndOfInformation`, not extra pixels (`lzw-missing-eoi-short-padding`).
- **N14. Frame rectangles must lie inside the screen.** §20.a. Every measured decoder accepts and clips, libnsgif grows the canvas; Recommended clips (option `frame_bounds`).
- **N15. `decode_still` reads a prefix.** It stops after the first image (G14), as image-rs's `read_image` does. gdk-pixbuf's loader rejects a file whose later frames are corrupt or whose trailer is missing (`stop_load` requires `GIF_DONE`, `io-gif.c:923`); QUESTIONS Q3.
