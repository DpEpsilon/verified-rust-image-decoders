# ICNS container and legacy-pixel core

This is a byte-slice contract, not a rendering policy. Offsets are zero-based, byte ranges are half-open `[start,end)`, and successful parsing preserves entry order. `parse(bytes)` returns entries; `decode_rgb(bytes, entries, color_index)` returns width, height and interleaved RGB bytes; `decode_mask(bytes, entries, mask_index)` returns width, height and alpha bytes; `combine(bytes, entries, color_index?, mask_index?)` returns interleaved RGBA bytes. Every decoding function requires entries returned by a successful `parse` of the same immutable byte slice; supplying forged entries or a different slice violates the API precondition, not an error result. Each function returns either its specified result or one exact error name below. An application chooses which entries to combine; the core never guesses.

R1. Interpret each length field as an unsigned 32-bit big-endian integer. Interpret the four-byte type as four uninterpreted bytes (not a terminated string). The returned entry record has exactly `{type_hex: string, payload: [u32,u32], opaque_candidate: bool, nominal_side: Option<u32>}`: `type_hex` is the lowercase, eight-digit hexadecimal encoding of the four type bytes; `payload` is `[start,end)` with `start <= end <= len(bytes)`; `nominal_side` is a pixel side length from R9 exactly when the type belongs to its fourteen-code table, even if its payload also has a recognised signature, and is `None` otherwise. Width and height are `u32`; an entry index is `u32`, and only `combine` accepts an absent index, represented by `None` (otherwise `Some(u32)`). A successful decoder returns its width and height as equal `u32` values. Calculate offsets and products using `u64`, checking sums/products and `offset <= len(bytes)` before narrowing to `u32` or platform `usize`; on 32-bit targets never narrow an offset before this check. The R2 input limit makes every successful offset representable as `u32`.

R2. `parse` checks input length first, without reading its bytes: reject `len(bytes) > 67,108,864` with `FileTooLarge`; otherwise reject fewer than eight bytes with `TruncatedHeader`, before examining magic or declared length.

R3. `parse` requires `bytes[0:4] == 69 63 6e 73` (`icns`), else `BadMagic`. The length at `[4:8]` includes this eight-byte header; reject lengths below eight with `InvalidFileLength`.

R4. Require declared length to equal `len(bytes)`. A declaration larger than the slice returns `TruncatedFile`; one smaller returns `TrailingFileBytes`. Apply this comparison before scanning entries. **DECISION:** both gdk-pixbuf (io-icns.c:91–96) and the independent rust-icns reader (family.rs:138–151) stop at a shorter declaration without checking later bytes; this core rejects those bytes. We found no evidence that macOS tools actually write such suffixes, and no evidence that they never do. A caller intentionally accepting a suffix can pass only the declared-length slice to `parse`, after independently checking that the declared length is within the available input.

R5. Starting at offset eight, parse entries until `offset == declared_length`. If one to seven bytes remain, return `TruncatedEntryHeader`. Each entry has a four-byte type and a four-byte unsigned big-endian length that includes its eight-byte header. If length is below eight return `InvalidEntryLength`; if `length > declared_length − offset`, measured from the **first byte of this entry's header**, return `EntryOutOfBounds`. Compute `end=offset+length` as a checked `u64` sum. The payload range is `[offset+8,end)`; advance to `end`. In particular, an empty payload is valid structurally. **DECISION:** gdk-pixbuf stops scanning when fewer than eight bytes remain (io-icns.c:95–104,175–183); this core rejects that suffix. We found no evidence whether actual macOS producers emit these incomplete-entry suffixes.

R6. Reject a 4,097th entry with `TooManyEntries` after validating that entry's header and length but before adding it to the result; 4,096 entries are permitted. The empty container (`icns` plus length eight) returns an empty list. Do not require any particular entry type in `parse`.

R7. Retain unknown types as ordinary entries, including arbitrary non-ASCII four-byte codes. Retain duplicates, empty payloads and ordering without deduplication. **DECISION:** gdk-pixbuf chooses the last matching picture and mask while scanning (io-icns.c:106–175), whereas this core leaves selection to its caller.

R8. Assign legacy colour/mask pairs and pixel dimensions exactly as follows: `is32`/`s8mk` = 16×16; `il32`/`l8mk` = 32×32; `ih32`/`h8mk` = 48×48; `it32`/`t8mk` = 128×128. An entry of any other type passed to either decoding function, or a colour type passed to `decode_mask` or mask type passed to `decode_rgb`, returns `UnsupportedType`. In particular, older resource types such as `ICON`, `ICN#`, `ics#`, `ics4`, `ics8`, `icl4`, `icl8`, `ich#`, `ich4`, `ich8`, `icm#`, `icm4`, `icm8`, `TOC `, `icnV`, `name`, and `info` are retained by `parse` but not decoded. A file with no R8 colour/mask pair can still be parsed, but cannot produce RGBA through this core.

R9. Classify `icp4`, `icp5`, `icp6`, `ic07`, `ic08`, `ic09`, `ic10`, `ic11`, `ic12`, `ic13`, `ic14`, `icsB`, `sb24`, `SB24` as `opaque_candidate` by type alone, with `nominal_side` respectively 16, 32, 64, 128, 256, 512, 1024, 32, 64, 256, 512, 36, 24, 48 (all square). For any type **other than the eight R8 legacy colour/mask codes**, also classify an entry as `opaque_candidate` if its payload starts with the complete eight-byte PNG signature `89504e470d0a1a0a` or twelve-byte JP2 file signature `0000000c6a5020200d0a870a`. Every R8 entry is never an `opaque_candidate`, even if its payload starts with those bytes. For `ic04`, `ic05`, and `icsb`, classify as opaque only if one of these signatures matches; otherwise retain as ordinary unsupported entries (their ARGB variant is outside scope). `nominal_side` for those three types is `None` whether signature-recognised or not; a signature-only match on any other unlisted type likewise has `nominal_side=None`. A listed type with matching signature keeps its table-defined nominal side. A listed type with a nonmatching or short payload remains opaque: this core neither promises the bytes are a valid image nor validates claimed dimensions. Raw JPEG 2000 codestreams lacking the JP2 signature are not signature-recognised; only listed type codes identify them. `icp4` and `icp5` remain opaque even if their payloads could represent another encoding; `decode_rgb` rejects them with `UnsupportedType`. **DECISION:** neither filename extension nor a prefix such as `ic1` suffices; only these exact full-code/full-signature matches classify opaque candidates. `parse` returns the same payload range for opaque and ordinary entries and never decodes PNG/JPEG 2000.

R10. `decode_rgb` requires a valid colour index into `entries` (`IndexOutOfRange` otherwise) and a legacy colour type (`UnsupportedType` otherwise). Let `N=width×height`; allocate exactly `3N` bytes and return `out[3i..3i+3] = [R[i],G[i],B[i]]` where `i=y×width+x`, x increases left to right and y increases top to bottom. The maximum `3N` for the four allowed colour types is 49,152 bytes (a derived bound, not a second rejection condition). The payload is *only* planar RLE streams R, then G, then B. **DECISION:** gdk-pixbuf treats a payload of exactly `4N` bytes as uncompressed ARGB (io-icns.c:291–298); this deliberately narrower core does not support that representation and interprets it as RLE, returning the applicable RLE error if invalid.

R11. For `it32` only, if its payload starts with four zero bytes, remove exactly those four bytes before RLE decoding; otherwise consume the entire payload as RLE. No other R8 type has a removable four-byte prefix under this contract. **DECISION:** this follows gdk-pixbuf's `it32` special case (io-icns.c:119–127), whereas rust-icns removes four leading zeros for all four RLE24 colour types (element.rs:550–565). Four leading zeros could also represent **two** one-byte literal runs, each with value zero; for `it32` this contract always interprets them as a prefix. A nonzero four-byte leading field is *not* treated as a prefix here; whether real producers use one has not been verified.

R12. RLE is byte-oriented. Decode each of the three channels separately with a fresh `produced=0`, retaining one shared input cursor. While `produced<N`: read one control byte or return `RleTruncated` if absent. For control `<128`, set `count=control+1`; for control `>=128`, set `count=control−125` (3 through 130). If `count>N−produced`, return `RleOverrun` **before** reading run data. For a literal control, require at least `count` remaining payload bytes or return `RleTruncated`, then copy them to positions `produced..produced+count` of this channel and advance the cursor by `count`. For a repeat control, require one remaining byte or return `RleTruncated`, repeat its value `count` times, and advance by one. Increase `produced` by `count`. On `produced=N`, immediately begin the next channel; after the blue channel, require the cursor at the payload end or return `RleTrailingBytes`. There is no channel delimiter or zero-length run. This is the complete termination condition; never read a byte before checking its presence. **DECISION:** gdk-pixbuf's `uncompress` checks output count but reads control and run bytes without input bounds and does not check for trailing compressed bytes (io-icns.c:193–245,300–312); this core rejects both conditions.

The normative R12 procedure, after R11's optional prefix removal, is:

```text
cursor := 0
for channel in [R, G, B]:
    produced := 0
    while produced < N:
        if cursor == payload.length: return RleTruncated
        control := payload[cursor]; cursor := cursor + 1
        if control < 128: count := control + 1; literal := true
        else:             count := control - 125; literal := false
        if count > N - produced: return RleOverrun
        needed := count if literal else 1
        if payload.length - cursor < needed: return RleTruncated
        for j in 0 .. count-1:
            channel[produced+j] := payload[cursor+j] if literal else payload[cursor]
        cursor := cursor + needed
        produced := produced + count
if cursor != payload.length: return RleTrailingBytes
return interleave(R, G, B) as specified in R10
```

R13. `decode_mask` requires an in-range index (`IndexOutOfRange` otherwise) and a legacy mask type (`UnsupportedType` otherwise); require payload length exactly `N`, returning `InvalidMaskLength` otherwise. Return `alpha[i]=payload[i]`, where `i=y×width+x`, x increases left to right and y increases top to bottom. The loader also requires exactly `N` bytes (io-icns.c:281–284).

R14. `combine` returns `MissingColor` when its colour index is absent, then `MissingMask` when its mask index is absent. For both present, call `decode_rgb`, then `decode_mask`, in that order and propagate their exact errors. Require the decoded sides to match, else return `TypeMismatch`; because R8 maps each side to exactly one colour and mask type, this is equivalent to requiring the corresponding pair, without an additional pairing error for equal-sized entries. The caller's selected entries may occur in either order and need not be adjacent. Interleave `R[i],G[i],B[i],A[i]` in row-major order (`i=y×width+x`), with no premultiplication and no rescaling. Allocate exactly `4N` RGBA bytes. **DECISION:** set a 4,194,304-byte defensive output ceiling for this core; every permitted output is at most 65,536 bytes, so the ceiling is provably unreachable and this version does not define `OutputTooLarge` as an error. Extending supported raster types requires revising this ceiling and the closed error set. **DECISION:** no implicit white/opaque mask and no first/last duplicate winner; the loader requires both picture and mask (io-icns.c:178–183), then copies mask to alpha (io-icns.c:314–315).

R15. `parse` checks `FileTooLarge`, `TruncatedHeader`, `BadMagic`, `InvalidFileLength`, then the declared-length mismatch in that order, and scans entries **in file order**, stopping at the first error. For each entry test `TruncatedEntryHeader`, `InvalidEntryLength`, `EntryOutOfBounds`, then `TooManyEntries` when 4,096 entries have already been accepted; never inspect later bytes after an error, including a malformed entry following a valid 4,097th entry. In `combine`, test absent arguments in R14 order, then decode colour, then decode mask, then compare sides. Error names are case-sensitive. No function returns partial entries or pixels on error.

R16. The byte slice remains owned by the caller; ranges never include an entry header, never cross the declared file end and remain valid only while the same input bytes remain available. `parse` allocates only its entry list, not decoded-pixel buffers.

R17. The complete, closed error set is exactly `FileTooLarge`, `TruncatedHeader`, `BadMagic`, `InvalidFileLength`, `TruncatedFile`, `TrailingFileBytes`, `TruncatedEntryHeader`, `InvalidEntryLength`, `EntryOutOfBounds`, `TooManyEntries`, `IndexOutOfRange`, `UnsupportedType`, `RleTruncated`, `RleOverrun`, `RleTrailingBytes`, `InvalidMaskLength`, `MissingColor`, `MissingMask`, `TypeMismatch`. In particular, missing RLE control or data bytes both return `RleTruncated`; no separate underrun error exists. No implementation may return a different named error for a case covered by this version.

R18. `VECTORS.json` is a JSON array of `{name, input_hex, operation, expected}` objects, optionally with `color_index` and/or `mask_index`. `input_hex` is lowercase contiguous hex bytes; optional `input_repeat` (positive integer, default one) means concatenate that entire hex byte sequence that many times before parsing; this compact form exists for the `FileTooLarge` boundary vector. Every vector runs `parse` first, including those with a decoding operation, and reports any parse error before decoding. Operations are `parse`, `rgb`, `mask`, `combine`. A missing index in a `combine` vector encodes `None`; present indices are nonnegative `u32`. On success, `parse` expects `entries` with exactly the R1 fields: `nominal_side` uses JSON `null` for `None`, and `payload` holds the two numeric offsets. A successful pixel operation expects `side` and one of `rgb_runs`, `alpha_runs`, `rgba_runs`: each is a maximal sequence of runs `{count: positive integer, hex: lowercase fixed-width pixel bytes}`, where `hex` represents respectively one RGB pixel (3 bytes), alpha sample (1 byte), or RGBA pixel (4 bytes), and the sum of `count` values equals `side×side`. An error result is exactly `{error: name}`. This fixture format specifies test expectations, not extra input accepted by `parse`.
