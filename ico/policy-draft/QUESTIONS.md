# ICO policy: owner decisions and places the draft guessed

Each item names the decision, the options and a recommendation, and can be read on its own. Q1–Q5 block a freeze; Q6–Q11 can wait without changing Recommended. Nothing here is decided. Field names refer to `OPTIONS.md` in this directory; "probe `x`" is a case in `/home/ws/projects/leniency/policy-probe/probe_cases.py` with results in `results-ico.json` there.

## Decisions that block a freeze

**Q1. How ICO's policy reaches DIB.** Today ICO decodes a selected DIB entry by calling `dib_verus::try_decode_with_steps_logged(slice, IcoEntryDibSlack)` and importing its allocation log through `import_dib` (`ico_verus/src/ico.rs:1516–1528`, `alloc_guard/sites.rs:1310`). That call has no policy argument. DIB's policy entry point `try_decode_with_policy(bytes, BmpMode, BmpProfile)` accepts only `BmpFile` and `BareDib`, and the frozen DIB policy says ICO modes stay policy-free (DIB `policy/POLICY-SPEC.md`, D1/D7/D10/D14). So ICO **cannot** pass a policy to DIB without a DIB change. Options:
- (a) **Container-only.** ICO profiles change only the 9 directory fields; every entry still decodes under DIB Strict slack mode. No DIB change. Recommended then equals Strict on this corpus (none of the 9 fields has corpus support).
- (b) **Coupled pass-through.** Add to DIB a logged policy entry for the ICO slack mode, `try_decode_with_policy_logged(bytes, IcoMode::Slack, Policy) -> (Result, recovered, Tracked<AllocLog>)`, satisfying the same `g_logged`/`log_tied` shape that `import_dib` requires, plus the six ICO-only DIB fields (`ico_height`, `alpha32`, `and_mask`, `ico_rle`, `ico_compression`, `mono_palette`). Each ICO profile names exactly one DIB record (Strict→Strict, Recommended→Recommended, GdkCompat→GdkCompat+ICO fields, ImageCrateCompat→ImageCrateCompat+ICO fields). This needs a new, separately versioned DIB policy spec, because the frozen one forbids an ICO policy.
- (c) **Independent parameters.** `decode_entry_with_policy(bytes, entries, i, IcoProfile, DibProfile)`. Mixed pairs multiply the named combinations (4×4) and their vectors; the DIB layer still needs (b)'s entry point.

*Recommendation: (a) now, (b) as a second stage.* (a) ships with no DIB proof work and no spec revision; (b) is required for the only corpus gain on offer (Q2). Reject (c): it multiplies the frozen profile tables without a user who needs a mixed pair.

**Q2. Recommended's contents.** Under Q1(b), Recommended = Strict at the ICO level, plus DIB Recommended's `image_size=Ignore` applied in ICO mode (`biSizeImage` outside `{0, X, X+A}` accepted). On the 433-file corpus 10 files fail Strict only at `Dib(InvalidImageSize)` and gdk-pixbuf, `image` and the `ico` crate decode all 10; whether each then passes Strict's later AND-mask check is not yet computed. This relaxes an error site only, so obligation R (no Strict-accepted file changes) holds. *Recommendation: accept, conditional on Q1(b); under Q1(a) Recommended equals Strict.*

**Q3. What "ICO Recommended" means when DIB's policy is not passed (Q1(a)).** Either ship an ICO `Recommended` name identical to Strict, so that the name exists and later gains `image_size=Ignore` under a **new** versioned name, or ship only `Strict` until Q1(b). Profile names are immutable once frozen (DIB D9, TGA D5), so a Recommended that later changes must be renamed. *Recommendation: ship only Strict in stage (a); introduce `Recommended` together with Q1(b).*

**Q4. Short or missing entry declarations (`entry_range`).** D11 (settled) keeps the exact declared slice; a short declaration fails with DIB's truncation error. gdk-pixbuf ignores the size field entirely and reads from the offset to EOF: probes `entry-size-0`, `entry-size-short-header`, `entry-size-xor-only`, `entry-size-beyond-eof` all decode in gdk; on the corpus 2 files fail Strict with `Dib(TruncatedHeader)` (the `mask_1.cur` pattern) and gdk decodes both. `image` reads unbounded from the offset and uses the size only to decide whether an AND mask exists. `ToEof` can let one entry consume the next entry's bytes. *Recommendation: keep `Exact` in Strict and Recommended; offer `ToEof` only in GdkCompat, with `recovered=true` whenever the decoded slice extends past the declared end.*

**Q5. A missing AND mask (`and_mask`).** Strict requires the mask (`TruncatedAndMask`). `image` accepts an entry that ends exactly at the end of the XOR raster and leaves it opaque (probes `dib24-no-and`, `dib32-no-and`, `entry-size-xor-only`); gdk-pixbuf accepts any truncation after the header. One corpus file fails Strict here; the `ico` crate and gdk decode it. The candidate relaxation `OptionalAtEnd` accepts only when **zero** bytes follow the XOR raster and treats the mask as all zeros. Interaction: with Strict's 32-bit rule (`alpha32=WindowsFallback`) an all-zero mask makes an all-zero-alpha 32-bit entry opaque, while `image` and gdk make it transparent. *Recommendation: keep `Required` in Recommended until a corpus shows producers that omit the mask; offer `OptionalAtEnd` (and `recovered=true` when it fires) in the compatibility profiles.*

## Decisions that can wait

**Q6. The 32-bit alpha rule (`alpha32`).** For a 32-bit entry whose XOR alpha is all zero, Strict (DIB 1.1 R12) falls back to the AND mask; **all three libraries** instead show the XOR alpha, which makes the icon fully transparent (probe `dib32-zero-alpha-and`: Strict `102030ff…`, gdk/`image`/`ico` `10203000…`). For 32-bit entries with alpha, `image` additionally clears alpha where the AND bit is set (probe `dib32-alpha-and-set`); this explains 30 of its 32 corpus pixel differences. No corpus file has an all-zero alpha plane. Strict cannot change (frozen DIB R12 and its vectors), and Recommended cannot either (obligation R: these files are Strict-accepted). *Recommendation: keep WindowsFallback; reproduce XorOnly/XorThenAnd only in the compatibility profiles.* This is the one rule where Strict disagrees with every incumbent; the Windows behaviour the spec cites as its source is RECALLED, not measured here.

**Q7. A verified selector.** The core never selects (R1, D9). gdk-pixbuf ranks by area × a depth derived from the colour-count byte and takes the later record on ties (probes `tie-two-equal`, `bpp-vs-area`), skips compressed and PNG records, and does not fall back after the chosen record fails (`largest-broken-smaller-ok`). `image` ranks by bit-count word first, then area, ties to the last record. The bench uses area then bit count. *Recommendation: no selector in this policy layer; if glycin needs one, specify it separately as a pure function over the parsed entry list (it reads no payload bytes, so it adds no safety obligation beyond its own termination).*

**Q8. More than 1,024 entries (`entry_cap`).** Every library accepts 1,025 (probe `count-1025`); no corpus file has more than 1,024. Raising the cap to the u16 limit multiplies the one entry-list reservation by 64 (from 1,024 to 65,535 records). *Recommendation: keep 1,024 everywhere, including the compatibility profiles, and list it as a known residual.*

**Q9. Reproducing `image` defects in ImageCrateCompat.** `image` ignores the directory reserved word and type (`dir_type=Any`), rejects a whole cursor file when any hotspot exceeds 256 (`dir_field_limit=Image256`, probe `cur-hotspot-300`), and decodes RLE in ICO but returns every alpha as 0 (probe `rle8-in-ico`). *Recommendation: include `Any` and `Image256` (cheap, header-only) only if ImageCrateCompat is meant as an exact migration aid; leave `ico_rle=Decode` out (it reproduces a transparency bug and needs RLE plus AND accounting in ICO mode).*

**Q10. The `recovered` flag for ICO.** DIB's closed event list applies to the DIB pass-through. Proposed ICO additions, each data-affecting: `entry_range=ToEof|ImageSize` decoding bytes outside the declared range; `and_mask` treating a missing or partial mask as zeros or opaque. Metadata-only tolerances (`dir_reserved`, `dir_type`, `entry_reserved`, `entry_overlap`, `image_size`) do not set it. *Recommendation: accept this closed list; Strict and Recommended never set it.*

**Q11. An `ico`-crate profile.** The crate's acceptances beyond Strict are a subset of gdk-pixbuf's, and its other deviations are narrowing defects (whole-directory failure on any bad record, 40-byte headers only, full palette always read, compression ignored). *Recommendation: no profile.*

## Places the draft had to guess

- **gdk-pixbuf's tie rule** comes from GLib's `g_list_insert_sorted`, which inserts a new element before the first element that does not compare greater; one probe (`tie-two-equal`) confirms "later record wins" for a two-way tie.
- **Two gdk-pixbuf four-bit corpus differences** have no identified cause (UNVERIFIED); they are counted, not explained.
- **`entry_overlap`** is from source reading only: no probe builds a decodable DIB that starts inside the directory.
- **`ico_height=GdkZero256`** (stored height 0 or 1 means 256 rows) is from `io-ico.c:401–409` only.
- **The corpus gain of Recommended** (up to 10 files) assumes those files pass every later Strict check; an ICO-mode oracle with `image_size=Ignore` must confirm it before a freeze.
- **The format template.** The brief named `dib/policy/QUESTIONS.md`; that file does not exist (DIB's decisions are inline in its POLICY-SPEC). This file follows `tga/policy/QUESTIONS.md`.
