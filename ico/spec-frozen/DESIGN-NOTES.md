# Design notes — revised draft, not frozen

The core parses every complete directory record into either a bounded `Valid` candidate or an `Invalid` status with its first record defect. An application chooses which candidate to decode; the core never picks a “best” image. A pure caller-side ranker may use nominal dimensions and stable directory order, but cannot certify DIB/PNG validity. No ranker belongs in this verified core.

## Deliberate baseline differences

The inspected `/home/ws/projects/spec/gdk-pixbuf/gdk-pixbuf/io-ico.c` sorts by nominal pixel area times derived colour depth and chooses the first uncompressed DIB (`:278–394`). This core retains **every** record, in original order, including invalid and duplicate records; neither parse nor decode falls back. PNG-signature candidates become untouched ranges, not false DIB interpretations. The baseline has no PNG signature choice in this loader and skips nonzero BIH compression (`:366–388`), including BITFIELDS; the proposed DIB dependency permits the frozen DIB-supported headers, BITFIELDS and palette behaviour. Its hard-coded 1-bpp colours (`:790–815`) and unconditional 32-bpp AND skip (`:817–825`) differ from the already frozen DIB pixel semantics; those differences are owned by DIB, not by the container.

The baseline ignores entry byte 3, `data_size` and many out-of-bounds offsets (`:282–328,334–375`). This core preserves a nonzero reserved byte, zero size, overlap with the **whole** directory or out-of-file range as an **invalid entry status** and returns that error if the caller selects it. Unlike the original all-or-nothing draft, an unselected bad entry no longer blocks a valid candidate: installed gdk-pixbuf 2.42.12 loads constructed two-entry files with a bad second reserved byte, zero size, out-of-file offset or oversized length (as measured in `/home/ws/projects/ico/REVIEW.md`). An incomplete table remains a file-level `TruncatedEntries`, so an intact first image in a truncated directory cannot be decoded through this core. The baseline's progressive buffering (`:258–275,916–988`) does not constrain our complete-slice requirement.

The baseline checks selected directory width/height against the DIB header (`:399–428`); we use directory dimensions only as nominal metadata. The corpus's `hopper_unexpected.ico` consequently decodes here but baseline rejects it. A zero directory dimension means 256 (`:321–324` and writer `:1205–1211`); DIB itself still rejects zero header dimensions. The baseline stores CUR hotspots as raw options (`:391–394,535–540`), while its **writer** validates hotspots (`:1074–1084`); our decoder retains raw words and expects the caller to compare against decoded dimensions. The colour-count byte is metadata, not the baseline's approximate depth score (`:294–313`). PNG classification requires all eight bytes **inside the declared entry** and does not read IHDR, so only a downstream PNG decoder can validate image length, IHDR, CRCs and actual dimensions. No streaming callbacks, save path (`:990–1364`), resizing hook, MIME registration or selection policy is imported.

D5 changes only **surplus** DIB bytes inside a bounded entry. Proposed DIB 1.1 `IcoEntryDibSlack` consumes a complete XOR raster and AND mask, checks `biSizeImage` in the old order, then ignores surplus bytes. Its frozen 1.0 predecessor still rejects that suffix. The installed baseline loads `hopper_mask.ico` and `pillow.ico` with their slack-bearing DIBs; our new-mode oracle now also decodes those four candidate images. It does **not** fix directory sizes that declare **too few** bytes: `mask_1.cur` and `mask_L.cur` still pass an eight-byte slice to DIB and return `Dib(TruncatedHeader)`, although the installed baseline loads both by reading from offset beyond the declared size. Extending a selected range to EOF would accept these two but risks reading the next image as part of this one. We keep exact short-side delimitation under settled D11. A caller that explicitly elects truncation recovery may, after suitable offset/range checks, retry `dib_verus::decode_with_steps(&bytes[e.raw_offset as usize..], IcoEntryDibSlack)` when `decode_entry` returns a DIB truncation error; this offset-to-EOF retry is not part of the core, can consume another entry's bytes, and needs a separately chosen caller policy. A consumed-length DIB API is unnecessary for accepting surplus entry bytes and would not itself resolve a short declaration.

Bounded overlapping ranges need no quadratic rejection. A caller that decodes every one of 1,024 aliases can perform 1,024 separate DIB decodes; the per-call work theorem does not cover that caller loop. Gaps and bytes after the last entry remain accepted. Parse's 64 MiB input cap aligns with DIB; 1,024 records is a pure policy choice, despite the wire count allowing 65,535. A zero-count CUR is rejected by both our core and installed baseline, so its corpus rejection is not a regression.

## Corpus under the revised policy

`python3 -I /home/ws/projects/ico/tools/run_corpus.py` reads but never copies the **13** local `.ico/.cur` files. **12 parse successfully, one (`no_cursors.cur`) fails `EmptyDirectory`.** Successful files hold **18 entries**, two PNG candidates and 16 DIB candidates; all are structurally valid on this corpus, so per-entry invalid statuses are exercised by synthetic vectors rather than real files. The 16 DIB slices produce **13 RGBA successes and three DIB errors**: `decompression_bomb.ico` is `Dib(InvalidDimensions)`; `mask_1.cur` and `mask_L.cur` are `Dib(TruncatedHeader)` because of their eight-byte declarations. The new slack mode adds `hopper_mask.ico` and three `pillow.ico` DIB successes versus the prior nine-success corpus result. Every result agrees with the **hash-pinned DIB 1.1 Python oracle** on exactly the declared slice. The sample consists of deliberately odd Pillow fixtures, so its rejection fraction is not a user-file compatibility estimate. Three of the 12 parsed files still cannot yield DIB pixels; a fourth parsed file, `hopper_draw.ico`, is PNG-only and requires a separate PNG decoder. The installed baseline loads the two short-size CUR files, `hopper_mask.ico` and `pillow.ico`; this measured compatibility cost motivates D11 without silently changing its policy.

## Proof composition and unfinished dependencies

A disposable two-crate Verus probe at `/tmp/ico-cross-crate/` proved that the **shipped 1.0** DIB crate's public `decode_mp_eq` postcondition can be applied to a checked `bytes[start..end]` slice across crate boundaries: the shipped dependency's reported 1,367 obligations verified in that run, and the dependent slice probe verified one obligation with zero errors. This does **not** report 1,367 new 1.1 or ICO proofs. The probe did **not** include the new slack mode, per-entry ICO parser or total forged-record checks. DIB 1.1 must first add the mode and re-prove its public `decode_mp_eq`/`model::mp` statement. A future ICO crate then checks directory/range bounds, reconstructs the selected record for totality, calls the new DIB mode on that exact slice and uses the public DIB model-equality contract for every output byte/error.

The shipped DIB crate's T12 linear-work witness is private (`dib.rs:5388`); its public `decode` exposes no ghost work trace. ICO can prove its own parse/wrapper work bound separately. For the proposed combined bound, DIB 1.1 should export the existing tracked witness body as public `decode_with_steps` with both `decode_mp_eq` and the step bound, and ICO must call **that function** on its exact slice. The ghost result erases without changing executable decoding. This is a proposed implementation and proof task, not a proved 1.1 contract. Likewise a ghost allocation count does not detect an added, uncharged `vec!`; review allocation sites in source.

No Verus ICO implementation or DIB 1.1 proof exists. `/home/ws/projects/ico/REVIEW.md` independently agreed with the earlier 153-vector suite; `/home/ws/projects/ico/REVIEW2.md` independently agreed with 200 revised vectors and identified the 17 additional cases now present, which need independent recheck before freeze. The ICO checker and generator share one **draft** DIB oracle pin in `spec/dib_oracle_pin.py`; retake that pin after the DIB 1.1 amendment freezes, then rerun both ICO tools before reviewing/freezing ICO. The frozen 1.0 DIB oracle hash is not this dependency's identity. Expected ICO parse records in the fixture generator are constructed from wire fields without asking the ICO oracle; expected DIB pixels intentionally use the pinned DIB oracle. A changed byte slice can produce `InvalidEntryRecord`, a directory error, or another legitimate decode result when the reconstructed selected record remains field-for-field equal: DIB decodes the current payload bytes, not a previous snapshot.

## Owner decisions

- **D1–D4 (settled):** reject count zero; permit bounded overlaps; accept directory/DIB dimension mismatch; retain raw CUR hotspots.
- **D5 (settled):** accept surplus bytes inside a complete DIB entry using a **new DIB 1.1 mode**, while retaining exact directory range bounds.
- **D6–D8 (settled):** classify full PNG signature without IHDR; cap at 64 MiB/1,024 records; permit file-level gaps/suffixes.
- **D9 (settled):** keep bad complete records as per-entry invalid statuses; directory-wide structural defects still reject the whole file.
- **D10 (settled):** make `decode_entry` total by checking directory, selected index, list length and selected wire record before any slice.
- **D11 (settled):** keep an under-declared entry's exact slice and report DIB truncation. The optional offset-to-EOF retry belongs to callers; it is not a core recovery policy.
