## What this shows and what it cannot show

Conclusion for the owner questions, then the limits of the sample.

**Q9 (freeze gate).** The gate can be met: a pinned real corpus now exists (1,407 files, 33 MiB, 32 repos, 1,318 with a GIF signature). Among 303 incidental assets (documentation, website and demo images, identified by a path heuristic; the nearest thing here to files made for a purpose other than testing a decoder) Strict accepts 283 (93%). The 20 it rejects hit five errors: `DataAfterEndOfInformation` 12, `TrailingBytes` 4, `MissingEndOfInformation` 2, `FrameOutsideScreen` 1, `UndefinedDisposal` 1. Recommended therefore has to forgive at least data after End of Information and bytes after the trailer. Of the 23 files whose first error is `DataAfterEndOfInformation`, 12 have exactly one `0x00` byte after the code in the first frame, inside the sub-blocks; in 9 the first frame is clean and a later frame is the offender (not examined); 2 have 15 or 115 extra bytes. Over all files Strict accepts 910 of 1,407 (65%); 326 files are fuzzer-derived (path contains afl, fuzz or crash; mostly libnsgif's `ns-afl-gif` mutants) and only 11 of those are accepted, so the headline rate measures how adversarial the test suites are, not how broken real files are.

**Q5 (colour index beyond the table).** Nine files contain such an index (transparent index excluded); none of the 303 incidental assets does. All nine are test or crash inputs (a Skia resource, gdk-pixbuf's `invalid-colors.gif`, imageflow's `gif_oob_palette_index.gif`, libgd's `unitialized_memory_read.gif`, two Firefox crash tests, three libnsgif mutants). No sampled encoder writes undersized tables, so the corpus shows no demand for accepting them. It shows nothing about prevalence on the web, and browsers do render such files, each differently (next section): Firefox wraps the index, WebKit and image-rs paint transparent, Chromium paints opaque black. The Q5 note that Transparent "matches browsers' usual handling" holds for WebKit only. Among the 1,014 files both gdk-pixbuf and `image` accept, they differ on the first frame in exactly 2, and both are index-out-of-range files (`invalid-colors.gif`, `unitialized_memory_read.gif`). A transparent index beyond the table (legal under Strict, never looked up) occurs in 14 files, 11 not fuzzer-derived, so Strict must keep accepting it.

**Q7 (Graphic Control before Plain Text).** 45 files have the pattern and all 45 are fuzzer-derived. A Plain Text Extension appears in 49 files; the 2 that are not fuzzer-derived (`gif-test-suite/plain-text.gif`, `gif-conformance/edge-cases/plain_text_ext.gif`) have no Graphic Control before it. The corpus gives no real-world demand either way. The decoder sources (next section) all skip Plain Text without clearing the pending Graphic Control, which supports option (b).

**Q8 (resource caps).** Nothing in the corpus approaches the frame or pixel budgets, and no file reached `TooManyFrames` or `PixelBudgetExceeded`. Among the 910 Strict-accepted files: most frames 183 (cap 65,536), p99 48 frames; largest canvas 3720x2584 = 9.6 Mpx (cap 16.8 Mpx); sum of frame areas at most 14.6 Mpx (1.4% of 2^30), p99 4.9 Mpx; composited output (frames x canvas) at most 94.4 Mpx, p99 12.5 Mpx. The one cap the corpus argues against is the per-side limit of 8,192: 81 files have a side above it, 12 of them not fuzzer-derived, and several are well-formed: `treeview-sprite.gif` (18x8888, a YUI sprite from bugs.webkit.org), Firefox's `100x32768.gif` and `32768x100.gif` reftests, gdk-pixbuf's `max-width.gif` (65535x1) and `max-height.gif` (1x65535). All of these are under the 16.8 Mpx area cap. A per-side cap of 65,535 with the area cap kept would accept them; the area cap alone already rejects the 65535x65535, 46565x23539, 14489x34615, 6727x65351 and 12352x12418 files.

**What the corpus cannot show.**
- Sampling bias. Every file comes from a decoder or browser test suite, a documentation tree or a demo directory, not from a crawl. Test suites keep regression inputs for crashes (23% of files here are fuzzer-derived) and under-represent ordinary files; each file is counted once even where Chromium, WebKit and Skia ship the same bytes, so popularity is not weighted.
- Size. Files over 5 MiB were dropped (one: image-gif's 10 MB `photo.gif`); the largest accepted file is 3.1 MB and the longest animation has 183 frames. Web animations with thousands of frames or hundreds of megabytes of composited output are absent, so Q8's frame and pixel caps are untested from above.
- Encoder mix. There are no outputs from Giphy, Photoshop "Save for Web", ffmpeg or screen recorders in known proportion, so rates such as the 4% of incidental files with a byte after End of Information say nothing about the web.
- Gaps. SixLabors/ImageSharp's 107 GIFs (including `issue1668_invalidcolorindex.gif`) are Git LFS objects and the LFS host is not reachable from this sandbox; Wikimedia Commons, chromium.googlesource.com and wpt.live are also unreachable. The "incidental" label is a path heuristic, not a judgement of each file.
- Licences. All files are NOASSERTION; bytes are for local measurement only and stay in `~/corpora/gif/`.

## What browsers do (source evidence)

Read from source on 2026-11-14; nothing was run in a browser. The WHATWG HTML Standard and MIME Sniffing Standard hosts are not reachable from this sandbox, so what they say about GIF decoding was not checked.

Colour index beyond the table:

- Firefox: the pixel is `mColormap[aIndex & mColorMask]`, so the index wraps; the mask is widened when the transparent index needs more bits, and entries between the table and the mask are opaque white. https://github.com/mozilla/gecko-dev/blob/5836a062726f715fda621338a17b51aff30d0a8c/image/decoders/nsGIFDecoder2.cpp (`ColormapIndexToPixel` around line 324; mask around line 892; opaque-white fill around lines 930-940).
- WebKit: a pixel is drawn only when `colorIndex + 2 < colorMap.size()`; otherwise a transparent (0,0,0,0) pixel is written. https://github.com/WebKit/WebKit/blob/1021adfd541eca44c46b6f1c1e43241a6f9b4ea4/Source/WebCore/platform/image-decoders/gif/GIFImageDecoder.cpp (around line 250).
- Chromium: Blink's `gif_image_decoder.cc` calls `SkGifDecoder::Decode`, which Skia implements with Wuffs (`src/codec/SkWuffsCodec.cpp`, namespace `SkGifDecoder`); Wuffs fills palette entries after the table with opaque black (global and local tables: "Set the remaining palette entries to opaque black"). https://github.com/chromium/chromium/blob/ca8253839df0881a2b51d83641700b4adfe01acf/third_party/blink/renderer/platform/image-decoders/gif/gif_image_decoder.cc and https://github.com/google/wuffs/blob/b36a81d3352604fee1fee3661f39909706b1b966/std/gif/decode_gif.wuffs (lines 622-628 and 870).
- libnsgif (NetSurf's decoder): `colour_table[*uncompressed++]` with no bounds check against the table size, into a fixed 256-entry array in a `calloc`ed struct, so an unwritten entry reads as zero (transparent black) unless an earlier table wrote it. https://github.com/netsurf-browser/libnsgif/blob/c26c7aa4765e4a40b5f2a1e7941368286ca88e32/src/gif.c (lines 508-530, 1495). Not run.
- giflib: `DGifGetLine` returns raw indices; no colour-table bounds check was found in `lib/dgif_lib.c` (the only `ColorMap` uses are table construction and copying), so the check is the caller's job. https://github.com/mirrorer/giflib/blob/fa37672085ce4b3d62c51627ab3c8cf2dda8009a/lib/dgif_lib.c
- gdk-pixbuf and image-rs: measured here, see the incumbent comparison below.

Graphic Control before Plain Text:

- Firefox skips Plain Text with the comment "Skip over any other type of extension block, including comment and plain text blocks"; the Graphic Control fields are reset only after a frame completes (around lines 315 and 693-698 of the file above).
- WebKit: the extension switch has `case 0x01: // ignoring plain text extension`; the Graphic Control is stored in the pending frame context, not cleared by Plain Text (`GIFImageReader.cpp`, around lines 537 and 570).
- Wuffs (Chromium): "We skip over all other extensions, including 0x01 'Plain Text Label'"; `reset_gc` runs only when a frame is decoded (`decode_gif.wuffs` around lines 651 and 507).
- giflib: `DGifSavedExtensionToGCB` scans every extension block saved with an image for the Graphic Control function code, so a Plain Text block saved before the image does not hide it (`dgif_lib.c` line 600).
- libnsgif lists Plain Text as unimplemented (`gif.c` line 149 todo); how it keeps the Graphic Control was not traced.

Also relevant to the Strict rules: Firefox maps disposal 4 to 3 and treats 5-7 as 0; WebKit and Wuffs map 4 to restore-previous. Strict rejects 4-7 (`UndefinedDisposal`: 47 files carry a value of 4-7, 38 as the first Strict error, 1 of the 303 incidental assets).
