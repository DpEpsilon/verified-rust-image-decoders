# PNG core and policy: owner decisions and places the spec guessed

Each item names the decision, the options and a recommendation, and can be read on its own. PNG-Q1–Q13 block a freeze of PNG-CORE-SPEC and its policy record; PNG-Q14–Q16 can be settled later without changing RecommendedBeta. **PNG-Q1–Q15 were decided by the owner on 2026-11-16 (Q13 and Q16 as noted); nothing is frozen.** Each item ends with its decision; the question text is kept as asked, with the corrections noted in it, and the changelog is `../DECISIONS.md`. "Strict" is the core spec (`../spec-draft/SPEC.md`); "RecommendedBeta" is the provisional recommended profile, which may only turn Strict errors into successes and must decode every Strict-accepted image identically (obligation R). "image" is the `image` crate 0.25.10 with the `png` crate 0.18.1 behind it (glycin uses the same code with a newer png revision); "gdk-pixbuf" is version 2.42.12 with libpng 1.6.48. Evidence names (`probe:…`, `vec:…`, `wit:…`) refer to `OPTIONS.md` and `probes/results.json`.

## Decisions that block a freeze

**PNG-Q1. RecommendedBeta's field set.** RecommendedBeta = Strict plus fourteen relaxations (as asked; the decision below makes it thirteen full ones and a narrowed fourteenth), each replacing an error Strict returns: skip an ancillary chunk whose CRC is wrong; ignore IEND's CRC and length; treat end of file after the image data as IEND; ignore bytes after IEND; drop misplaced, duplicate (keeping the first) and invalid ancillary chunks, including an invalid tRNS; ignore a PLTE in a greyscale image or after the image data of a truecolour image; allow more palette entries than the bit depth can index; draw out-of-range palette indices black (PNG-Q6); ignore bytes after the zlib stream and surplus decompressed data (narrowed by the decision: surplus decompressed data stays an error); ignore the zlib window size declared in the header; let the still decoder ignore animation chunks. gdk-pixbuf and image agree on each of these (identical pixels), except the missing IEND, which image rejects when the file ends right after the image data (so that field is a design choice, not incumbent agreement). Only a dropped tRNS, surplus data and a black palette substitution set `recovered`. *Recommendation: accept.* On the 289 synthetic inputs that Strict rejects and image or the gdk-pixbuf loader accepts, this set accepted 231 as asked and accepts 224 after the narrowing; most of the rest are damaged image data (PNG-Q10) and animation errors (PNG-Q11).

**Decided (2026-11-16).** The council's version. RecommendedBeta = Strict plus thirteen full relaxations; the fourteenth, `zlib_tail`, is narrowed to `IgnoreTail`: compressed bytes after an Adler-32-checked end of the zlib stream are ignored, but surplus decompressed output stays `ExcessImageData`. Implemented as a new value, not a new field, so the record keeps 30 fields and inflate keeps five policy fields. With Q11's `apng_errors=Static` the non-Strict count is fifteen fields (fourteen full relaxations and the narrowed one). A later `surplus_output=Ignore` for compatibility profiles is allowed only once a bounded rule and an R2 detector are specified; that is open. The acceptance figure is recomputed: 224 of 289 (was 231; the seven lost inputs are all `ExcessImageData`). `image` rejects a missing IEND, so `missing_iend=AtEof` is a design choice. Files: `OPTIONS.md`, `policy_oracle.py`.

**PNG-Q2. CRC checking.** Strict checks the CRC of every chunk and rejects any mismatch. The PNG specification lets decoders skip CRCs, and recommends ignoring damaged ancillary chunks. libpng (so gdk-pixbuf) and image reject a bad CRC on a critical chunk (IHDR, PLTE, IDAT) and silently drop an ancillary chunk with a bad CRC; stb_image checks nothing. Options: (a) Strict checks all, RecommendedBeta drops bad ancillary chunks (current draft); (b) Strict also drops bad ancillary chunks; (c) no CRC checks at all (faster by one table lookup per byte; a damaged chunk length then misaligns the parser silently). *Recommendation: (a).* Note that dropping a damaged tRNS changes transparency (`probe:crc-trns`); RecommendedBeta reports that through `recovered`.

**Decided (2026-11-16).** (a), with the critical chunks named. Strict checks every CRC. RecommendedBeta discards a bad-CRC ancillary chunk only after its length and bounds were verified, and sets R1 when the dropped chunk is tRNS. IHDR, PLTE, IDAT and fdAT are the critical chunks whose CRC failure RecommendedBeta rejects (`iend=Lenient` exempts IEND). fdAT is critical for this purpose although its type name is ancillary; the rule is the value `crc_ancillary=SkipExceptFdat`, so png 0.18.1 (which skips a bad fdAT) is unaffected in ImageCrateCompat.

**PNG-Q3. 16-bit samples reduced to 8 bits.** Strict rounds: `(v + 128) / 257`, the PNG specification's "most accurate" rule, which image also uses. gdk-pixbuf keeps the high byte (`v >> 8`, libpng's `png_set_strip_16`). They differ by one level on about half of all values (`probe:depth16-rgba`). Options: (a) round (current draft); (b) high byte. Both are equally easy to verify. *Recommendation: (a)*, with `depth16=HighByte` in GdkCompat-2.42.12 only. A caller that needs exact samples uses the 16-bit entry point (PNG-Q13).

**Decided (2026-11-16).** (a). 16-bit samples reduce to 8 bits by rounding `(v + 128) / 257` in every profile except GdkCompat, where `depth16=HighByte`. Callers that need exact samples use the 16-bit entry point.

**PNG-Q4. Gamma and colour management.** No measured decoder applies gAMA, cHRM, sRGB, iCCP or cICP to pixels (`probe:gamma-*`: identical output everywhere); image does not even report gAMA (the png crate never fills the field it reads). Options: (a) the core returns raw samples and exposes the colour chunks' raw values plus the ICC profile through a separate call (current draft); (b) the core applies gAMA (a floating-point or table-based transform, a large new proof obligation with no incumbent to match). *Recommendation: (a)*; glycin already performs colour management outside the loader.

**Decided (2026-11-16).** (a). The core returns raw samples; the colour chunks' raw values and the ICC profile come through a separate call; a malformed ICC payload never blocks pixel decoding (only `try_icc_profile` inflates it); metadata access distinguishes absent, discarded by the profile and failed to decode (OPTIONS.md `metadata_status`).

**PNG-Q5. Resource caps.** All caps are constants in one section of the spec (P1) and the theorems are stated over their names, so each changes with one edit and a rebuild. Proposed: input at most 256 MiB; width and height at most 16,384; RGBA8 output at most 64 MiB (16.7 megapixels, the same as BMP, TGA and GIF); at most 65,536 animation frames and 2^30 frame pixels in total; a decompressed ICC profile at most 16 MiB. For scale: a 16.7-megapixel 16-bit RGBA PNG stored without compression is about 134 MB, so the input cap must exceed the output cap; a 4,000 × 4,000 photo is within the output cap, an 8,000 × 6,000 one is not. gdk-pixbuf has no cap below libpng's 1,000,000 × 1,000,000; image applies 512 MiB of allocation by default, but its PNG decoder disables limits when constructed directly (DESIGN-NOTES N16). Options: (a) these numbers; (b) a larger output cap for PNG only (for example 256 MiB, 67 megapixels), at the cost of proportionally more peak memory: output plus filtered data is twice the output size for an 8-bit RGBA image and three times for a 16-bit one, and an animation using PREVIOUS disposal adds one more output-sized buffer. *Recommendation: (a)*, revisiting (b) only if the real corpus (PNG-Q7) contains common images above 16.7 megapixels.

**Decided (2026-11-16).** The proposed numbers are the **provisional implementation baseline**: input 256 MiB, per side 16,384, RGBA8 output 64 MiB, 65,536 frames, 2^30 total frame pixels, decompressed ICC profile 16 MiB. They are held out of the freeze until the corpus pass (Q7) and stay named constants in one section (P1), theorems symbolic in the names. The corpus pass must test the 16,384 per-side cap and the 64 MiB output cap against large screenshots and long thin images. **The output cap is bounded by the shared allocation guard `MAX_BYTES` (67,108,864, frozen in `../../alloc-delta`, copied byte-identically into every core). The owner will not raise `MAX_BYTES` until it is known what to raise it to; that value is chosen after the PNG corpus pass (use case: very large multi-monitor screenshots; the owner wants bounds raised eventually).** `../../RELEASE-GATES.md` item 1 says so. Corrections to the question text: the raw-data bound `R ≤ H·(1 + 8W)` is wrong for interlaced images; the exact bound is `R ≤ 8·W·H + S(H)` with `S(H) ≤ 2H + 2` scanlines (SPEC P11, `check_bounds.py`; RGBA16 interlaced 1024 × 1024: `R = 8,390,528`, not at most 8,389,632). Peak heap per entry point is in SPEC P20: the RGBA16 output alone is 128 MiB at 16.7 megapixels; output plus filtered data is twice the output size for 8-bit RGBA and three times for 16-bit; APNG PREVIOUS disposal adds one output-sized buffer. **Open (2026-11-16):** `Raw` for 16-bit RGBA and the RGBA16 output exceed one `MAX_BYTES` reservation at the proposed caps (SPEC P20), so the effective caps under the unchanged guard are smaller; how P1 expresses that is not decided. *Resolved by the decision of 2026-11-17 below.*

**Decided 2026-11-17 (supersedes the numbers above; the 2026-11-16 text is kept as history).** Raise the caps. (1) Per-side width and height: 16,384 becomes the PNG wire limit 2^31 − 1; the output cap bounds the area. Corpus evidence (`../../leniency/corpora/png-RECOMMENDEDBETA-PASS.md`, run under the old caps with a raised-cap side run): five valid files that every incumbent decodes, 65,535 × 1, 1 × 65,535, 524,288 × 2, 2 × 524,288 and 32,768 × 100, were rejected at 16,384. (2) RGBA8 output: 64 MiB (16.7 megapixels) becomes 256 MiB (67,108,864 pixels, 8192 × 8192 equivalent); the largest real image in the corpus is 60.9 megapixels (244 MiB as RGBA8) and 256 MiB covers all 8,296 incidental files. (3) The shared guard `MAX_BYTES` (per-reservation cap, 64 MiB, frozen in `../../alloc-delta`) is being raised to 2^30 (1 GiB) by a separate change (alloc-delta erratum E16); PNG's caps now depend on it: a 67-megapixel RGBA16 output is 512 MiB and `Raw` (filtered data) is about the same, each a single reservation at most 2^30. Peak heap: output plus filtered data is twice the output for 8-bit RGBA and three times for 16-bit; a 16-bit decode peaks near 1 GiB (SPEC P20: 768 MiB for `decode_still`, 1 GiB for `decode_still16`, up to 1.125 GiB with the Adam7 scanline term of a one-pixel-wide image); APNG PREVIOUS disposal adds one output-sized buffer. Input cap stays 256 MiB: **open edge:** a stored (uncompressed) 16-bit RGBA PNG of 67 megapixels is about 537 MB and exceeds it; raising `MAX_INPUT` is a later strict widening. Lesson from GIF erratum E3 (`../../gif/ERRATA.md`: a bit count `8·len` in `u32` overflows for inputs above 512 MiB): the PNG and inflate proofs use 64-bit bit positions from the start. Frames (65,536), total frame pixels (2^30) and ICC (16 MiB) are unchanged. Applied in `DECISIONS.md` (Q5, 2026-11-17 entry) and `../spec-draft/SPEC.md` P1, P11, P20; the corpus pass should be re-run under the new caps (see `DECISIONS.md`).

**PNG-Q6. Palette indices beyond the palette in RecommendedBeta.** The PNG specification gives no rule. libpng, gdk-pixbuf and image all draw such pixels opaque black, with identical results (`probe:index-oob-*`). For GIF the incumbents disagreed and the GIF draft recommended rejecting. Options: (a) RecommendedBeta draws black and sets `recovered` (current draft); (b) RecommendedBeta rejects like Strict. *Recommendation: (a)*, because the three incumbents agree bit for bit.

**Decided (2026-11-16).** (a). Out-of-range palette indices are drawn opaque black in RecommendedBeta, and R3 is set for every substituted index, including under tRNS.

**PNG-Q7. Real-world corpus before freeze.** All measurements use 737 synthetic inputs (vectors, 177 targeted probes and 55 distinct witnesses from the earlier leniency run), plus, since GAPS-CLOSED.md gap 6, 800 synthetic held-out mutations of them; none is a real-world file. TGA's recommended profile was justified on 300 real files. *Recommendation: block the freeze of RecommendedBeta (not of Strict) on a pass over a pinned real PNG corpus* (PngSuite, the libpng, image-png and gdk-pixbuf test images, and a web or desktop-theme sample; see BRIEF.md "Corpus plan"), recording which Strict errors real files hit. Likely candidates: ancillary chunks after IDAT, iCCP profiles with non-conforming names, surplus zlib data, and APNG files with frame-count mismatches.

**Decided (2026-11-16).** The freeze of RecommendedBeta and of the cap values is blocked on a pass over a pinned real PNG corpus. Strict's decode rules may freeze independently once the surplus-output and Adam7 defects are repaired (both are repaired in this draft). The pass reports incidental assets (icons, screenshots, web images) separately from test and fuzz files, measures final outcomes per field, includes large screenshots, keeps a hold-out, and reconciles the packet's input counts: 748 is the number of records in `probes/results.json` (516 vector, 177 probe, 55 witness; 14 above 4 KiB stored by reference), 737 the number of distinct inputs the Strict bridge and obligation R checked at the time (the non-`pad_to` vectors, 536 distinct, plus the 734 inline records, de-duplicated by bytes; 740 after the three vectors added on 2026-11-16), so the question's "737 synthetic inputs" counted the bridge's inputs, not the measured ones. BRIEF.md "Corpus plan".

**PNG-Q8. Alpha blending arithmetic for APNG.** The specification asks for a "simple OVER operation" without a rounding rule. Strict uses exact integer arithmetic on 8-bit values with round-half-up (P14.4). image computes in 32-bit floating point and truncates, so its frames differ by one level on some semi-transparent pixels (`probe:apng-blend-over`). Options: (a) exact integer rounding in every profile except ImageCrateCompat (current draft); (b) match image's floating-point result everywhere (verifying 32-bit float arithmetic in Verus is impractical; it would remain a trusted surrogate). *Recommendation: (a)*; ImageCrateCompat's `blend=ImageF32` is modelled in Python only and should be dropped from that profile if no exact integer characterisation of image's results is found during P2.

**Decided (2026-11-16).** (a). Exact integer round-half-up OVER for APNG. `blend=ImageF32` enters ImageCrateCompat only if an exact integer characterisation of image's results is proved; otherwise it is dropped and recorded as a residual. Vectors for a transparent source, a transparent destination and a zero resulting alpha were added (`apng/blend-over-transparent-source`, `-transparent-destination`, `-zero-result-alpha`), and an offline exhaustive check over the whole operand domain (4,261,412,864 tuples, half a minute) is `spec-draft/check_over.py`.

**PNG-Q9. What `decode_still` validates.** Options: (a) the whole chunk stream up to IEND, including chunks after the image data, but inflating only the image data (current draft); (b) stop after the image data, as image does, so damage after the pixels (a bad CRC in a trailing text chunk, a missing IEND) never matters. For GIF the draft recommended the prefix reading, because the full alternative cost a decode of every frame; here (a) costs only a CRC pass over the rest of the file. *Recommendation: (a)* for Strict, with RecommendedBeta's relaxations covering the common post-image damage (missing IEND, trailing bytes, damaged ancillary chunks).

**Decided (2026-11-16).** (a). `decode_still` walks and validates the whole chunk stream through IEND, inflating only image data. Missing-IEND tolerance applies only at a complete chunk boundary. Strict still-success validates APNG structure, not later frames' compressed data.

**PNG-Q10. Damaged image data in RecommendedBeta.** When the zlib stream is truncated or corrupt, gdk-pixbuf's loader returns the image anyway, with the missing rows filled with a fixed grey `#979899` (and the last good row lost when zlib detects the error in the same `inflate()` call that completed it, GAPS-CLOSED.md gap 2); `gdk_pixbuf_new_from_file`, libpng, image and libspng reject. image also ignores a wrong Adler-32 checksum. Options: (a) RecommendedBeta rejects all of these (current draft; GdkCompat-2.42.12 offers the grey-fill behaviour); (b) RecommendedBeta returns the decoded rows with transparent padding and `recovered=true`; (c) RecommendedBeta ignores only the Adler-32 checksum. *Recommendation: (a)*, as DIB, TGA and GIF did for truncated pixel data; revisit with the corpus.

**Decided (2026-11-16).** (a). RecommendedBeta rejects truncated or corrupt zlib streams and a bad Adler-32. GdkCompat may offer a grey fill later.

**PNG-Q11. Animation errors.** Strict rejects an APNG with any structural error (sequence numbers, frame rectangles, frame count, missing frame data), and also rejects fcTL or fdAT chunks without acTL. Static decoders (gdk-pixbuf, libpng) show the default image of such files; image shows the frames before the error, then stops. Options for RecommendedBeta's frame iterator: (a) reject (current draft); (b) fall back to the default image as a single frame (`apng_errors=Static`, sets `recovered`); (c) return the frames before the error (`Prefix`, image's behaviour). For RecommendedBeta's still decoder the draft already ignores animation chunks entirely (PNG-Q1), so a broken animation never prevents showing the default image. *Recommendation: (b)*, because it never shows a partial animation and matches what every static viewer shows; it needs one more event (R4, already in the list).

**Decided (2026-11-16).** (b), as the council scoped it. RecommendedBeta's frame constructor falls back to the default image as a single frame with R4, limited to APNG structural errors found by its upfront walk before any frame is exposed. Allocation, resource (`TooManyFrames`, `PixelBudgetExceeded`), critical-chunk and later inflate failures are not caught and surface as errors from the iterator; the default image must itself decode. This is a design choice: no measured APNG decoder does it. Strict keeps rejecting structural errors in the constructor. `apng_errors=Static` is now in RecommendedBeta (profile table, D3, field count 15).

**PNG-Q12. Crate decomposition.** Options: (a) one crate holding inflate, the chunk parser, filters, interlacing, conversion, the APNG compositor and the policy layer; (b) a separately verified `inflate_verus` crate (zlib + DEFLATE) plus `png_verus` (everything else, compositor included). Splitting costs nothing in speed (generic, inlined calls), memory (inflate writes straight into the caller's buffer and uses it as its own window, so it allocates nothing and needs no cross-crate allocation log) or simplicity of the PNG proofs (they consume one frozen model function, `Inflate(Z, L)`). It buys reuse: ICO and ICNS embed PNG, and TIFF (Deflate compression), PDF streams, zTXt, iTXt and iCCP all use zlib. The compositor stays inside `png_verus` (the owner's preference; it shares the canvas with frame decoding and three policy fields act inside it). *Recommendation: (b)*; this is the case the GIF Q10 verdict left open, because none of the three costs it named applies.

**Decided (2026-11-16).** (b). Separate verified `inflate_verus` and `png_verus` crates. The frozen interface is `Inflate(Z, L, options)` with five policy fields acting inside inflate (`adler`, `stream_end`, `zlib_tail`, `window`, `single_code`), the `Segments` contract, the first-error order, and the distinction between output exactly full and another output byte existing.

**PNG-Q13. API and output model.** Proposed: `try_decode_still` (RGBA8), `try_decode_still16` (RGBA16 for any source; 8-bit sources scaled by 257), a frame iterator yielding a borrowed whole-canvas RGBA8 view per frame with the raw `delay_num/delay_den`, dispose and blend values and `recovered`, `try_icc_profile` (decompressed ICC profile), and an `Info` record with the IHDR fields and the raw values of gAMA, cHRM, sRGB, cICP, mDCV, cLLI, sBIT, bKGD, pHYs, tIME plus borrowed byte ranges for eXIf. Text chunks are not decoded; a borrowed iterator over chunk byte ranges lets glue code read them. gdk-pixbuf needs RGBA8, the ICC profile, pHYs and text (it exposes `tEXt::` options); glycin needs RGBA8 or 16-bit output, the ICC profile, cICP, Exif and XMP (an iTXt chunk). Options: (a) as proposed; (b) also decode text chunks in the verified crate (a new allocation site and a bounded inflate per chunk); (c) drop the 16-bit entry point. *Recommendation: (a).*

**Decided (2026-11-16).** (a), with two additions the council recommended and the owner accepted. (i) A profiled RGBA16 still entry point, `try_decode_still16_with_policy`. (ii) An explicit validation status for each chunk yielded by `chunks`, so glue cannot reinstate a chunk the profile discarded; `chunks` yields every chunk with valid framing, in file order, each `Accepted` or `Discarded(reason)`, and a chunk whose CRC did not verify is never `Accepted`. Both are in BRIEF.md and OPTIONS.md; the oracle has no API-level model for either and is unchanged.

## Decisions that can wait

**PNG-Q14. Compatibility profiles.** GdkCompat-2.42.12 matches the gdk-pixbuf loader (whole-buffer writes) on 721 of 721 compared inputs and `gdk_pixbuf_new_from_file` on 616; ImageCrateCompat-0.25.10 matches image on 718–720 of 721. Both were fitted on the same inputs they are measured on, and both include surrogate rules for undocumented library internals (the grey rows, image's frame-control and disposal quirks). *Gap closed (GAPS-CLOSED.md gaps 2, 5, 6): the grey-row rule is now derived from libpng and zlib source; image's two fcTL quirks and png 0.18.1's interlaced-subframe bug are modelled (fitted set: ImageCrateCompat 721/721 still and frames, glycin 720/721); on 395 held-out mutations frozen after these changes GdkCompat agrees on 389 and ImageCrateCompat on 395 (still) and 394 (frames); a one-field necessity check finds seven fields that break no measured input, each subsumed by another field (OPTIONS.md).* Options: (a) freeze both as opt-in, versioned names; (b) target `gdk_pixbuf_new_from_file` instead of the loader; (c) defer both until after Strict and RecommendedBeta are proved. *Recommendation: (c)*, then (a) with a held-out re-measurement on the corpus.

**Decided (2026-11-16).** (c): both compatibility profiles are deferred until Strict and RecommendedBeta are proved, then (a) after a held-out re-measurement and a per-field necessity check. Targets: libpng 1.6.48 (through gdk-pixbuf 2.42.12's loader) and png 0.18.1 (through image 0.25.10). Retargeting to `gdk_pixbuf_new_from_file` is a different contract with a different name.

**PNG-Q15. Two places where Strict is stricter than zlib.** Strict rejects a back-reference farther than the window size the zlib header declares, and accepts a Huffman code with a single one-bit code (zlib's rule; fdeflate rejects it). Every measured decoder accepts the first (`probe:zlib-window-too-small`); RecommendedBeta already ignores the window. Options: keep both (current draft) or make Strict ignore the declared window. *Recommendation: keep.*

**Decided (2026-11-16).** Keep both Strict rules (enforce the declared zlib window; accept a single one-bit Huffman code as zlib does). For callers of `inflate_verus` outside PNG, the crate documentation states that strict mode enforces a window stock zlib does not (SPEC P10.6, BRIEF.md).

**PNG-Q16. The image crash.** png 0.18.1, used by image 0.25.10, panics on a palette chunk whose length is not a multiple of 3 (a 60-byte file; `probe:plte-len-13`), and image's PNG decoder disables allocation limits, so a 69-byte file declaring 65,535 × 65,535 pixels makes the process abort on a failed 17 GB allocation (`image::load_from_memory`, with its default 512 MiB limit, rejects it instead; glycin's loader code disables the limits and aborts too). glycin's newer png revision fixes the first. *Gap closed (GAPS-CLOSED.md gap 4): the file is 69 bytes, not 100; the `load_from_memory` and glycin outcomes were measured.* *Recommendation: route through the coordinator for a disclosure decision; the verified decoder is unaffected (both are caught by P6 and P4).*

**Decided (2026-11-16).** Not relevant to the work now; the owner is considering getting help with reporting third-party bugs. Probe and crash inputs stay out of public artefacts until that is decided. The verified decoder gets regression vectors, not compatibility fields. See `../DECISIONS.md` for the tracked-file check.

## Places the spec had to guess

- **Palette index beyond PLTE**: an error in Strict; the specification gives no rule (N8).
- **bKGD values with high bits set**: range-checked in Strict, by reading the stated range as the rule (N10).
- **Huffman completeness**: zlib's rule (N5).
- **The declared CINFO window**: enforced in Strict; no incumbent does (N5, PNG-Q15).
- **fcTL or fdAT without acTL**: an error in Strict; every measured decoder ignores them.
- **OVER rounding**: exact integer round-half-up (PNG-Q8).
- **`GdkGrey` row loss**: no longer a guess. Derived from libpng 1.6.48's progressive reader and zlib 1.3.1's `inflate()` (GAPS-CLOSED.md gap 2; OPTIONS.md `image_data_error`); it gives the surrogate's result on all 748 fitted inputs and matches the loader on 10 held-out inputs the surrogate missed.
- **Error names on new paths**: compatibility profiles reuse core names (for example `InvalidBackground` for image's fatal bKGD-before-PLTE, `InvalidChunkType` for libpng's reserved-bit rejection). Native error strings are never compared.

## Guard-limit update — 2026-11-17

The owner approved alloc-delta erratum E16: `MAX_BYTES` is now 1,073,741,824
bytes (1 GiB), not 67,108,864 bytes (64 MiB). This supersedes the earlier plan
to choose the shared guard limit after the PNG corpus pass. DIB, TGA, ICNS,
ICO and GIF keep their existing 64 MiB output caps; a core may raise its cap
separately through its own erratum. PNG's owner-decided caps are now the PNG wire-limit dimensions and 256 MiB
RGBA8 output; freezing those values remains corpus-gated. The 1 GiB per-reservation guard accommodates the
512 MiB RGBA16 output for an 8192 × 8192 image and its filtered raw buffer;
the earlier statements that those proposed PNG reservations exceed the guard
limit describe the pre-E16 guard, not the current limit. Verification and
audit evidence, including pending DIB verification, is in
`alloc-delta/ERRATA.md` E16 and `RELEASE-GATES.md` item 1.
