# TGA policy: owner decisions and places the spec guessed

Each item names the decision, the options, and a recommendation. Q1–Q6 block a freeze; Q7–Q13 can be settled later without changing RecommendedBeta. Nothing here is decided or frozen: each *Reviewer (Sol)* line records the reviewer's recommendation from `REVIEW.md`, and every item awaits the owner's decision.

## Decisions that block a freeze

**Q1. RecommendedBeta's field set.** RecommendedBeta = Strict plus `trailing=Ignore`, `rle_overrun=ClipPacket`, `attribute_bits=Lenient`, `map_header=IgnoreAbsent`. Each field only replaces an error that Strict returns, so no Strict-accepted file changes (obligation R, checked on every input in `REPORT.md`). *Recommendation: accept.* The alternative of also ignoring R10 truncation was rejected: only tinytga accepts the three truncated corpus files, and it does so by inventing zero samples. *Reviewer (Sol): accept the four error-site relaxations. Awaiting owner.*

**Q2. `Lenient` alpha for an invalid attribute count.** A count R5 rejects becomes 8 when the element has an 8-bit attribute slot (32-bit colour, 16-bit grey) and 0 otherwise. The 8-bit choice keeps stored alpha, which is what gdk-pixbuf shows for the three corpus files with 32-bit pixels and count 4. The rule is a guess about producer intent: a writer that sets count 4 and fills the A byte with garbage would get a transparent image. *Recommendation: accept, because the only measured reader that accepts these files (GDK) shows the stored alpha.* Alternative: map every invalid count to 0 (always opaque), which disagrees with GDK on those three files. *Reviewer (Sol): accept as a documented guess, not as proven producer intent; the spec should say so. Awaiting owner.*

**Q3. Does a repaired attribute count set `recovered`?** The spec says no: the closed event list holds only data-affecting events (clipped RLE positions, substituted palette indices), and Lenient changes an interpretation, not data. *Recommendation: keep it off the list.* If glycin wants to warn on any non-Strict acceptance, add a separate `tolerated: bool` rather than widening `recovered`. *Reviewer (Sol): keep the closed two-event `recovered`. Awaiting owner.*

**Q4. `ClipPacket` versus `ClipSamples` in RecommendedBeta.** ClipPacket (GDK) requires every byte of the over-long final literal packet; ClipSamples (image-rs) requires only the samples it paints. They differ only on a file that is both over-long and truncated inside its last packet. *Recommendation: ClipPacket*, the stricter of the two; both corpus files with an over-long final packet carry the whole packet. *Reviewer (Sol): accept whole-packet ClipPacket. Awaiting owner.*

**Q5. Named compatibility profiles.** `GdkCompat-2.42.12` and `ImageCrateCompat-0.25.10` reproduce every measured pixel difference exactly (85 of 85 decoder/file pairs across 41 files; each listed field is necessary within the chosen record; sufficiency/uniqueness not shown) and agree with the native decoders as reported in `REPORT.md` (held out only on seed 4242; the corpus and tuned-seed figures are regressions), but they import rules the 1.0 design notes rejected on purpose: zero-based palette lookup that ignores `first` (GDK), red/blue swap without bit replication for 15/16-bit palettes (GDK), and stored alpha with attribute count 0. *Recommendation: freeze them only as opt-in, versioned names, never as glycin's default; if review effort is short, ship Strict and RecommendedBeta first and leave both compat profiles unfrozen.* *Reviewer (Sol): keep both opt-in and deferrable. Awaiting owner.*

**Q6. Glycin's default profile.** Not decided by this spec. *Recommendation: RecommendedBeta*, because it changes no pixels Strict produces and accepts 14 of the 19 real files that Strict rejects and some library decodes; the other five are three truncated files and one oversized header that only tinytga accepts, and one palette file whose `first` field only GDK and tinytga ignore (Q10). *Reviewer (Sol): an integration decision for glycin, not a spec decision; RecommendedBeta is a reasonable default, but its gain is 14 extra corpus acceptances, not a demonstrated population-wide benefit. Awaiting owner.*

## Decisions that can wait

**Q7. Stored alpha with attribute count 0 (`alpha=Stored`).** gdk-pixbuf and image-rs both show the A byte of 32-bit pixels and 32-bit palette entries when the descriptor declares no alpha (11 of the 41 corpus pixel differences). Strict makes them opaque, as the 1.0 design notes chose. Producers that write count 0 with meaningful A bytes exist in the corpus; producers that write count 0 with garbage A bytes may too, and the corpus cannot tell them apart. *Recommendation: keep Strict and RecommendedBeta opaque; consider a separate future profile only if users report invisible-versus-visible complaints in the other direction.*

**Q8. 5-bit channel expansion.** Strict and GDK true-colour replicate bits (`(c<<3)|(c>>2)`); image-rs and tinytga round (`(255c+15)/31`). The two differ in 4 of 32 channel values (c = 3, 7, 24, 28), each by 1. *Recommendation: keep Replicate in Strict;* the difference is invisible and the rule is already proved.

**Q9. 16-bit palette entries with attribute count 1.** Strict uses bit 15 as alpha; GDK, image-rs and tinytga all ignore it (2 corpus files, which every library shows opaque while Strict makes some entries transparent). This is the only Strict rule that all three libraries reject on real files. **Proposed default: defer; awaiting owner.** Strict and RecommendedBeta both stay unchanged. Strict cannot change because 1.0 R8 and the frozen vectors promise bit-15 alpha for these entries. RecommendedBeta cannot change because obligation R promises identical RGBA for every Strict-accepted image, and these files are Strict-accepted. Bit-15-opaque behaviour goes to a future, separately versioned opt-in profile (or a separately versioned core revision). If the owner instead requires the change in RecommendedBeta, the profile must be renamed and obligation R revoked and re-proved for the narrower conservativity claim. (Reviewer (Sol) concurs.)

**Q10. Colour-map `first` field.** Strict (and image-rs) treat indices as absolute (`index-first`); GDK and tinytga ignore `first` (tinytga's source carries `//TODO: use start_index`). One corpus file (`first=126`, `length=256`) is rejected by Strict as `ColorIndexOutOfRange` and accepted by GDK/tinytga; another (`first=39`) decodes differently under GDK, which paints indices at or beyond 72 black. *Recommendation: keep Absolute;* GDK's output on the second file is visibly wrong.

**Q11. Truncated raw pixel data (R10).** Left Strict-only in every profile. tinytga substitutes zero samples; no option is specified. *Recommendation: leave it out* unless a later corpus shows a producer that systematically truncates.

**Q12. image-rs defects in ImageCrateCompat.** image-rs ignores the interleave bits and decodes any unknown image type, including type 0, as raw greyscale. The profile reproduces both (`interleave=Ignore`, `image_type=GreyFallback`) because without them it disagreed with image-rs on 141 of 3,613 development mutations. *Recommendation: keep them only if ImageCrateCompat is meant as a migration aid that reproduces image-rs exactly; otherwise drop both fields and document the residual.*

**Q13. tinytga profile.** Not specified. Its 22 differences come from three rules: descriptor bit 4 ignored by `pixels()` (14 files), rounding 5-bit expansion (6), and the runner's forced alpha 255 (2). Ignoring bit 4 is a bug in tinytga, not a rule worth reproducing. *Recommendation: no profile.*

## Places the spec had to guess

- **GDK `index_range=Black` alpha.** GDK returns transparent black for a missing palette entry, but its pixbuf has an alpha channel only when the palette entry depth is 32; otherwise the harness sees opaque black. The spec encodes that coupling (`(0,0,0,0)` for 32-bit entries, else `(0,0,0,255)`) from source reading (`io-tga.c:154–164,350–352`). The coupling is confirmed by one corpus file (24-bit palette) and by the synthetic vectors `index-beyond-map24` and `index-beyond-map32`, which match gdk-pixbuf byte-exactly.
- **`map_header=Gdk` with a nonzero flag other than 1.** Taken from `io-tga.c:486` (`if (ctx->hdr->has_cmap)`), checked only by synthetic vectors, not by a real file.
- **`map_header=Image` with flag ≥ 2.** image-rs treats such a map as absent and reads the map bytes as pixels (`decoder.rs:193`); synthetic evidence only.
- **Error names on new paths.** The compatibility profiles reuse 1.0 names (for example `UnsupportedPixelDepth` for image-rs's 16-bit index over a 15-bit palette). Native error strings are never compared, so these names are spec choices, not measured.
- **GDK filename sniffing.** One corpus file decodes under `gdk-forced-whole` but not `gdk-file`; the bytes-only profile follows the forced-TGA loader.
