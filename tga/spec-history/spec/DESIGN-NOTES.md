# Design notes — draft 2, not frozen

- Output top-first RGBA8 instead of retaining source origin or the baseline's RGB output for some types; clients receive one four-channel coordinate convention.
- Honor the indexed map's absolute `first` and reject out-of-range indices; gdk-pixbuf indexes a zero-based palette and returns transparent black for missing indices.
- Support 15-bit true-colour and 16-bit indexed samples that gdk-pixbuf's image-depth table rejects.
- Accept colour-map type 1 with image type 2/3/10/11. Apply the same nonempty length, 15/16/24/32-bit depth and `first+length<=65,536` validation as for indexed maps, then skip `length*ceil(entry_depth/8)` bytes after the ID without reading their colours. gdk-pixbuf also loads and discards these maps; rejecting them would reject files it accepts without buying cursor safety. The baseline accepts a flag-one, zero-length map when the image payload is otherwise valid: `colormap_new(0)` allocates storage for one entry (`io-tga.c:139–151`), and its zero-byte queue pull succeeds (`gdk-pixbuf-buffer-queue.c:204–217,263–275`), leaving the map-load loop empty (`io-tga.c:486–526`). This decoder deliberately rejects that incoherent declaration with `InvalidColorMap`; the review found no actual producer file relying on it.
- Reject a nonzero interleave field rather than silently decoding a different scanline order; gdk-pixbuf rejects it too.
- Treat descriptor attribute count as authoritative for 32-bit true-colour, 16-bit greyscale, and map-entry alpha; do not infer alpha from an unused byte or the ignored TGA 2.0 extension metadata.
- For 16-bit **true-colour** with count one and bit 15 clear, return opaque alpha 255, as gdk-pixbuf does. Bit 15 does not control true-colour alpha even with count one; this avoids turning legacy images invisible. For 16-bit **map entries** with count one, bit 15 still controls alpha (clear gives 0), unlike gdk-pixbuf's always-opaque palette path; files that leave the bit clear may therefore become transparent. Count zero map entries are opaque regardless of bit 15.
- For 32-bit true-colour with count zero, discard the stored A byte and return opaque alpha 255; gdk-pixbuf preserves that byte. Writers that omit the descriptor count despite meaningful A bytes lose transparency here. The same count-zero rule discards 16-bit greyscale's second byte while gdk-pixbuf preserves it.
- For 24-bit true-colour with count eight, 32-bit true-colour with counts 1..7, and 8-bit greyscale with count eight, return `InvalidAttributeBits`; gdk-pixbuf ignores those count values. The review recalls, but does not establish from a real sample, 24-bit files marked with count eight; any such files are rejected rather than decoded. 15-bit true-colour with nonzero count and indexed maps with 15/24-bit entries and count one are rejected on the same descriptor policy; the baseline ignores the count on its supported paths.
- For 32-bit true-colour with count eight and all A bytes zero, return transparent pixels even if the ignored extension-area alpha-type field says alpha is absent; gdk-pixbuf also copies those zero bytes. Files relying on the extension to override the descriptor render transparent.
- Expand five-bit channels by `(c<<3)|(c>>2)`. gdk-pixbuf's 16-bit true-colour path uses the same expansion, but its 15/16-bit palette path reverses red and blue and emits five-bit values shifted left by three without replication. A non-grey map entry therefore differs in both channel order and low bits.
- Reject an RLE packet that exceeds pixels remaining **before** reading packet data; gdk-pixbuf clamps the packet count and accepts its fitting prefix. Writers that pad a last packet can fail here; whether such writers exist is recalled, not established by a sampled file. Whole-packet availability also precedes checking its first palette index.
- Accept a TGA 2.0 footer signature only after complete pixels, ignore footer offsets and preceding opaque extension bytes, and reject an unmarked suffix; gdk-pixbuf discards arbitrary trailing data.
- Cap input and output separately at 64 MiB and either dimension at 8,192; these are decoder policy, not TGA format limits. Output can be allocated lazily if the same error precedence is kept.
- Error ordering follows fixed header checks followed by byte consumption; one error is returned and no partial image is exposed. The progressive baseline can emit pixbuf data before `stop_load` reports a truncated stream, which has no analogue in this pure API.
- These choices remain draft policy. No hash, digest or freeze has been assigned.
